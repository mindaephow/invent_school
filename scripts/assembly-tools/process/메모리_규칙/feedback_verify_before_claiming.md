When claiming a change produced a visible/user-facing result ("이제 표로 보여", "이제 한눈에 보인다"), verify by actually looking at the rendered page first — don't infer from having written well-formatted source (markdown, code, config) that it renders the way you intend.

**Why:** After restructuring `plan_content` into a markdown table (콘텐츠×단계 매트릭스), the assistant told the user "이제 표로 어느 콘텐츠가 몇 번에 있는지 한눈에 보여" — implying a real visual table now existed. The user asked "어디에서 그게 보인다는거야?" and when the assistant actually opened the live HongHub plan page, it turned out to be a plain textarea with zero markdown rendering — the `##`/`|---|` syntax was showing as literal text, exactly as it always had been (the page's own subtitle even says it's a Claude-facing memo, not a rendered doc). The user reacted sharply: "뭔 개 족같은 소리를 하는거야~~ 암튼 니가 잘난척 하면 꼭 사고가 나" (whenever you act overconfident, something always goes wrong) — a pattern callout, not a one-off.

**How to apply:** Before saying a change is now "visible", "showing", "one glance", or similar to this user (or in general), actually navigate to and screenshot/read the live surface it's supposed to appear on. If checking isn't quick (e.g. requires a build, a different session, real user action), hedge explicitly ("this should render as a table if the page parses markdown — I haven't confirmed") instead of asserting completion. This generalizes beyond HongHub docs: any claim of the form "X now does Y" for something user-observable should be checked, not inferred from the correctness of the input alone. Related: [[feedback-diagnose-dont-explain]] (verify against live state), [[feedback-plan-doc-structure]] (these HongHub doc fields are plaintext notes for Claude, not rendered UI — don't conflate the two).

**Recurring pattern, confirmed again 2026-09-03:** After reading `hub_sites.plan_content` for 공학, the assistant characterized it to the user as "기획서가 잘 돼있다" / a real upfront plan, without checking whether the document was actually written *before* production (deliberate planning) or assembled *after the fact* as a log of what happened while iterating. The user corrected: "공학은 한번 진행을 해서 그런거지 기획서를 작성하고 진행한게 아닌데" — on re-reading, section 15 of that same doc ("진행 기록 로그") confirmed it: A안 tried → problem found → B/C/D안 compared → D안 confirmed, a reactive trial-and-error log, not a prospective plan. The assistant had the full text already read via `run_sql` and still asserted the stronger claim without cross-checking it against the doc's own internal evidence. Then, separately in the same conversation, the assistant tried to verify the same already-fetched `plan_content` by opening the live HongHub website in a browser (which required a password it didn't have) — verification theater on data it already held via MCP, instead of just re-reading what was already in context. User: "니가 확인도 안하고 개구랄 치는건 항상 확인된다" (every time you bullshit without checking, it always gets caught).

**How to apply (expanded):** "Verify" doesn't just mean "look at a live page" — it also means actually re-reading data already fetched before characterizing it, rather than pattern-matching to what the data is *supposed* to represent (e.g. a field named `plan_content` isn't automatically a real upfront plan — check its actual contents/structure for evidence of when and how it was written). And when data was already pulled via one channel (MCP/SQL), don't re-fetch the same thing through a second, weaker channel (browser without credentials) as theater — that wastes a step and produces no new information.

**Recurring pattern, confirmed again 2026-09-21 (발명학교/invent_school):** Asked "현재상태 확인해줘" for the 발명학교 HongHub project, the assistant read `hub_sites.plan_content` and relayed it verbatim as the current status. The user called it out: "최신상태를 깃허브에서 확인을 안하고 그냥 적힌데로 지껄이는구만 앵무새처럼" (you're just parroting what's written instead of actually checking GitHub for the latest state). On checking `github.com/mindaephow/invent_school/commits/main` directly, there was a whole extra round of commits (과목 선택 단계 + 부품 카탈로그 기능, `28d92d2`~`3e2e6f1`) committed *after* `plan_content`'s own `updated_at` timestamp — same calendar day, but later. A stored summary field (plan doc, memory, any prior write-up) can go stale within the same day; it is a snapshot, not a live query.

**How to apply (expanded again):** For any "what's the current status" question about a project with its own repo/live deployment, treat the stored plan/summary as a starting hypothesis, not the answer — cross-check against the actual source of truth (GitHub commit log, live site fetch, DB row counts) before answering, even if the doc's own "last updated" date is today. Don't rely on a same-day timestamp as proof of freshness.
