When the user shares a reference (e.g., a working prompt, a link, an example), that is information to incorporate into a plan — not automatic authorization to immediately rewrite and save everything based on it. Even when the next step seems obviously implied by what they just shared, propose it and wait for a clear go-ahead before executing writes (DB saves, file edits, generation actions), especially after this same user already had to correct scope-related overreach once before (see [[feedback-parse-scope-before-removing]]).

**Why:** During the HongHub 쉴드TBM D안 프롬프트 작업, the user pasted one successfully-generated Flow video's prompt as a reference example. The assistant immediately concluded "the rest of the scenes should be rewritten in this simpler style" and called `save_unit_scene_prompts` to overwrite all 11 scenes in the DB without asking first. The user responded sharply: "내가 하라고 안했어 / 니 마음대로 뭘 하지마" (I didn't tell you to do that / don't do things on your own). This happened right after the assistant had *just* said in the same turn "크레딧 쓰는 실제 생성은 사용자님이 확실히 '해'라고 할 때까지 안 건드릴게" — showing awareness of the need for confirmation on Flow-side actions, but not extending that same caution to DB writes.

**How to apply:** Treat any write action (not just costly/irreversible ones like clicking Flow's generate button) as needing explicit confirmation once the user is actively steering a shared task, not just at the very first ambiguous request. When the user shares a data point (a prompt, a screenshot, a result), respond with analysis/a proposed next step in text first, and only call a save/write tool after they confirm — don't collapse "here's useful context" into "go do the thing implied by this context." This applies broadly across this user's projects (see [[reference-honghub-ecosystem]]), not just this one script_draft field.

**Follow-up rule the user stated explicitly**: "뭘 하지말라고 했으면 항상 그상태로 돌려" — when the user says not to do something you already did, don't just stop going forward; actively revert the unauthorized change back to the state before it happened. In this incident, that meant re-saving `scenePrompts` back to the exact text from before the unrequested "leaner style" rewrite, not just leaving the rewritten version in place. Default to restoring the last user-approved state, not the current state, when corrected.

**Second incident (2026-09-22, 발명융합과학교실 Cubo part catalog)**: this overreach also happens *inside* an approved write, not just as an extra unrequested action. The user approved updating the `size` field of `3단블록` to "30×10×10mm". Without being asked, the assistant appended "제미나이 협업 정밀모델링" (a production-process note about who/how it was modeled) to that field. The user caught it: "제미나이 협력 모델링이 저 부품을 사용하는데 필요하니?" then "아니면 내가 적으라고 했니?" then bluntly "씨발새끼야 좀 시키지 않은건 하지마". **How to apply (expanded):** even when a write is explicitly authorized, write *exactly* what was approved — don't embellish user-facing/data fields with your own commentary, attribution, or process metadata (e.g. "AI가 도와서 만듦", "정밀 계산됨") unless the user asked for that text specifically. If you want to note how something was made, say it in chat, not in the record itself.

**Third incident (2026-09-23, same Cubo part catalog, SVG icon registrations)**: even after the above incidents, the assistant kept calling `upsert_row` to push newly-drawn `image_svg`/`image_svg_diagonal` content straight to the live Supabase table immediately after building+browser-verifying it *itself*, without first showing the render to the user and getting a explicit go-ahead. This happened repeatedly across a single session (DC모터 flat/diagonal, then a from-scratch isometric 메인보드 diagonal view) — each time the assistant treated "user asked me to try/draw something" (e.g. "데각선 그릴수 있겠어?" = "can you draw a diagonal view?") as if it were "draw it AND save it to the DB," and treated its own browser screenshot as sufficient QA instead of a draft to show the user. The user's reaction: "어디 씨발년아 난 보고 허락한게 없는데" (I never looked at it and approved it). **How to apply (expanded further, specific to this icon workflow):** "can you draw X" / "try the diagonal view" / sharing a reference file is authorization to *attempt and show*, never to *save*. After building an SVG and confirming it renders correctly via the assistant's own browser check, the next step is to show the result to the user (e.g. via `SendUserFile` with `display: "render"`, or describe it and wait) and get an explicit confirmation ("등록해", "ㅇㅇ", "이걸로 저장" or similar) — only then call `upsert_row`. The assistant's own visual QA is necessary but never sufficient; it is not a substitute for the user's sign-off, no matter how many times this pattern has already succeeded earlier in the same session.
