# 문서 지도 — 조립도 작업의 기준점 (2026-10-14)

이 파일이 "무엇이 어디에서 관리되는지"의 기준이다. 저장소 `CLAUDE.md` 가 맨 먼저 여기를 가리킨다.
새 내용을 적기 전에 아래 표에서 **원본**을 찾고, 거기에만 적는다. 다른 곳에는 복사하지 않고 "○○ 참고"로 가리킨다.

## 2. 사람·화면이 DB 에 남기는 것 (Claude 가 덮어쓰지 않는다)

| DB 표 | 내용 |

| `ivs_assembly_status` | 번호별 사용자 ✓(완료) 기록으로 추정 — 확인은 `userdone.py` 가 읽는 표 |

사용자가 지정한 ❄·📷·✓ 는 코드와 내 계산보다 우선한다.

## 3. 진행 기록은 어디에 적나 (2026-10-14)

**1) 도구가 계산하는 것은 문서에 적지 않는다** — 적어 두면 곧 틀린다. 필요할 때 그 도구로 본다.

| 알고 싶은 것 | 보는 곳 |
|---|---|
| 어느 번호까지 만들었나 | `<이름>_asm.json` 의 단계 수, `python number_start.py <이름> <번호>` |
| 사용자가 ✓ 한 번호 | `python number_start.py <이름> <번호>` 맨 위 "DB 읽기(사용자 ✓)" 줄 (DB `ivs_assembly_status`, 읽는 코드는 `userdone.py` 모듈) |
| 규칙을 지켰나(격자·카메라·증거·읽기 표) | `python rulecheck.py <이름>` |
| 푸시 안 한 변경 | `git status`, `git log` |
| 사용자가 저장한 ❄·📷 | DB `ivs_assembly_poses`·`ivs_assembly_cams`, `user_diffs/수정저장차이.md` |

**2) 사람이 판단한 것만 `process/진행기록_<이름>.md` 한 곳에 적는다.** 조립도마다 파일 하나. 안에 쓰는 것:
- 맨 위: 현재 상태 한 줄("몇 번까지 무엇이 끝났고 무엇을 기다린다") + 정확한 현황은 위 도구로 보라는 한 줄
- 이 조립도의 구조·고유 사실(대칭 여부, 기준 부품, 측정값)
- **내가 추정한 목록**(사용자 확인이 필요한 것)
- 다음 할 일, 막힌 곳
- 그 조립도에서만 알아 둘 함정
번호마다 절을 계속 덧붙이지 않는다 — 끝난 번호의 내용은 "현재 상태"와 "구조"에 녹이고, 번호별 상세는 `<이름>_read.json`·`_evidence.json` 에 이미 있다.

**3) 다른 종류는 각자의 원본에 적는다 (진행기록 문서에 복사하지 않는다)**
- 일반 규칙을 새로 배웠다 → 위 1번 표의 규칙 원본(`SKILL.md` 절 또는 `process/*.md`)
- 사용자가 말로 바로잡았다 → `user_diffs/요청차이.md`
- 새 PC·서버 같은 환경 → `CLAUDE.md`·`README.md`
진행기록 문서에서는 "○○ 참고"로 가리키기만 한다.

**4) Claude 메모리(이 PC 에만 있음)에는 조립도 진행 본문을 두지 않는다.** 메모리에는 사용자의 선호·피드백·참고 위치만 남기고, 조립도 진행 메모는 진행기록 문서로 옮긴 뒤 메모리에는 "진행기록_<이름>.md 참고" 한 줄(또는 삭제)만 둔다. 이유: 메모리는 다른 PC·새 세션·메모리 없는 Claude 에게 안 보인다.

**5) 새 조립도를 시작하면** `new_assembly.py` 로 번호를 등록할 때 진행기록 문서를 같이 만든다(아직 자동은 아니다 — 만든 사람이 한다).

## 4. 같은 내용이 둘 이상이면 어느 쪽이 이기나 (2026-10-14 겹침 측정 기준)

- **원칙:** 같은 글을 두 곳에 두지 않는다. 겹침을 찾으면 원본 한 곳만 남기고 나머지는 "원본은 ○○"로 가리키는 한 줄로 바꾼다(제목은 남겨서 `part=` 로 찾을 수 있게 한다).
- **규칙 문장:** 위 1번 표의 원본이 기준이다. 안내서(`app/lib/cubo-assembly-guide.js`)는 MCP(`get_assembly_guide`)가 돌려주는 별도 글로, 고유한 내용(조립 규칙 목록·단계별 절차·부품 크기 표 등)이 대부분이다 — 겹치는 절만 포인터로 바꿨다. 옛 사본은 원본과 어긋나기 쉽다(실제로 "검증 우회 옵션 삭제" 절이 SKILL.md 와 반대 규칙을 담고 있었다).
- **진행 상태:** 저장소의 `진행기록_<이름>.md` 가 기준이다. Claude 메모리(`~/.claude/projects/.../memory/`)에도 조립도별 진행 메모가 있는데, 메모리는 이 PC 에만 있고 git 에 없다. 이어받을 때 메모리가 없으면 진행기록 문서만으로 되어야 한다.
- **`.claude/`** 는 `.gitignore` 라 launch.json 이 새 PC 에 없을 수 있다(README "새 PC" 3번으로 만든다). SKILL.md 는 git 에는 추적돼 있다.

## 5. 알려진 정리 거리 (2026-10-14 기준, 아직 안 한 것)

- 저장소 조립도는 **17개**다(`design-assemblies.js` 의 `cubo-*` id). 조립 프로그램으로 만든 13개(`<이름>_asm.json` 있음)는 모두 `진행기록_<이름>.md` 가 있다. 도구 없이 `design-assemblies.js` 에 직접 넣은 초기 4개 중 풍차는 `진행기록_windmill.md` 를 만들었고, **토끼(`rabbit`)·양팔저울(`balance`)·로봇팽이(`spinner`)는 진행기록이 없다**(작업 도구·규칙 점검 대상이 아니다. `build.py` 의 `LEGACY_NO_GRID` 가 이들을 옛 조립도로 다룬다). 사마귀(mantis)는 부품이 0개인 틀뿐이라 그 사실만 적혀 있다.
- 메모리의 조립도 진행 파일 13개(풍차 포함)는 포인터 한 줄로 줄였다(원본은 `Downloads\invent_school_backup_20261014\` 아래 `memory_all`·`before_dedup2` 에 백업).
- `진행기록_dropchecker.md`·`진행기록_catapult.md` 는 2026-10-14 에 구조 중심으로 다시 썼다(날짜별 절 합침, 낡은 상태 문장 삭제).
- 옮긴 문서의 "미확인·추정" 목록은 메모리 기록 시점(2026-10-02~13) 것이라 이후 해결됐는지 확인하지 않았다. 사용자 ✓ 가 있는 번호는 확인된 것으로 본다.
- `05_조립.md` 는 약 50KB 로 크지만 이번에는 나누지 않기로 했다(사용자 2026-10-14 "추천대로"). 맨 위 "실행 순서"와 체크리스트가 입구다.
- 그 밖의 겹침은 100자 미만의 조각이다(측정: 30자 이상 같은 글 기준).

## 6. 문서를 고칠 때 규칙

1. 새 규칙·사실은 원본 한 곳에만 적는다. 다른 곳에는 "○○ 참고" 한 줄.
2. 포트·서버 이름·파일 경로처럼 바뀌는 값은 한 곳(이 표의 원본)에서만 정한다.
3. 규칙이 새로 생기면 문서만 고치지 않고 검사(`rulecheck.py`·`stepchecks.py`·`number_start.py`)에도 반영하고, 검사 파일을 바꾸면 보고에 적는다.
4. 문서를 지우거나 합치기 전에 어디서 이 문서를 가리키는지 먼저 검색한다.
5. **쓰지 않고 다른 것으로 대체한 기능(도구·스크립트·문서)은 같은 작업에서 지운다**(사용자 지시 2026-10-14). 지우기 전에 ① 대체한 것이 있는지 ② 다른 파일이 그 이름을 가리키는지 검색하고 ③ 백업한 뒤 ④ 가리키던 문장을 대체한 것으로 고친다. 대체했다는 증거가 없으면 지우지 않고 사용자에게 묻는다.
