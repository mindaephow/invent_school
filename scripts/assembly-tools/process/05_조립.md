**1. 번호 하나(N) 순서 — 각 단계가 끝나야 다음으로**
1. `python number_start.py <이름> N` — 앞 과정·앞 번호 점검, 읽기 표 칸 생성. 막히면 그 목록부터.
2. 책 그림 `refs/<이름>/NN.jpg` 를 `Read` 로 열어 부품·초록 링·화살표를 훑는다. 링은 색(HSV 색상 40~90·채도 50 이상)으로 검출해 중심 픽셀을 숫자로 얻는다. **결합 방향은 화살표 선의 방향을 재서 정한다** — 초록 선의 화면 기울기(수평에서 몇 °)를 재고 축선(X·Y·Z)이 화면에서 가리키는 각도와 비교한다(드롭체커 27번: 선이 세로가 아니라 +Z 축 43° 와 같아 결합 축이 Z 였다 — 세로로 짐작해 프레임을 블록 위에 얹었다가 사용자에게 지적받았다). **기준 부품 = 그 번호에서 결합을 받는 부품**(27번은 25프레임이 아니라 135도 프레임) — 격자·축은 기준 부품에 그린다.
3. 판 바깥 모서리 4곳 읽기: `python crop_ticks.py <이름> N corners x1 y1 x2 y2 x3 y3 x4 y4` 로 확대 눈금 그림을 만들어 `Read` 로 보고 원본 좌표를 읽는다(순서 = 칸1줄1, 칸N줄1, 칸N줄M, 칸1줄M). 한 번에 ≤100×100px 로 보면 ±2px.
4. **홀라인은 받는 부품·끼우는 부품 양쪽 모두(사용자 2026-10-19): 한쪽만 그리고 다른 쪽은 같은 구멍이라 가정하지 않는다 — 라벨을 달리해(P·U …) 둘 다 만들고 책 링이 각 부품의 몇 번 구멍인지 센다(체크리스트 13).** 홀라인: `python holefit.py <이름> N P <칸> <줄> 모서리8개 어두운판` (기본→어두운판→자동 DoG). 통과하면 `refs/<이름>/hf/NN_P.png` 를 **눈으로** 본다(점이 구멍 위, 번호 순서). 미달(판이 가려짐)이면 위 0-1 절 `infer_grid.py`. **기준 부품이 한 줄·L자 프레임**(135도·90도·15프레임…)이면 격자가 안 되므로 `python crop_ticks.py <이름> N x0 y0 x1 y1 4` 로 구멍을 확대해 중심 픽셀을 읽고 `python frame_fit.py <이름> N F "<부품이름>" "h1:x,y;h2:x,y;…" --빼기 <모서리·끝 구멍> --원점 <가운데 구멍> --다듬기` — 부품 모델 구멍 좌표로 PnP(정상 해만, 재투영 오차 보고, fits·axes·확인 그림 생성).
5. 축·그림: `python axes_fit.py <이름> N P <칸> <줄> +X +Z` (오차 ≤2px·phi ≤1.55) → `refs/<이름>/NN_axes.json` 에 `"no_rotate": true` 추가(없으면 그림이 펴져 축선이 어긋난다) → `python refs_rect.py <이름> N` → `NN_2.jpg` 를 눈으로 확인 → **바로 DB 에 올린다**(`viewer_snippets.md` 3). **이미지 작업이 곧 조립도를 만드는 과정이다(사용자 2026-10-13): 구멍·링을 읽느라 만든 확대 눈금 그림(`crop_ticks.py`), 홀라인 확인 그림(`hf/NN_*.png`), 프레임 검출·재투영 그림(`frame_fit.py`)도 그 번호의 `idx 3~` 로 설명과 함께 올린다**(틀린 배정이 그려진 실패 시도 그림만 올리지 않는다).
5-1. **새 창고(slot≥2)는 화면 가운데(원점)에 둔다 — 스크립트에 "X2=200·Z24=250·Z30=500" 같은 멀리 띄우는 오프셋 상수를 만들지 않는다**(배틀로봇 2권 7차시: 33번 z 800·12~21번 x 200·24~31번 z 250~500 에 놓아 사용자가 "작업장이 중심이 아니라 외곽, xyz 축도 안 보인다"고 지적, 2026-10-18 전부 원점 5mm 쪽으로 이동). 몸과 겹치면 5mm 어긋나게만 하고, 번호가 끝나면 `battlerobot2_asm.json` 으로 slot 2 번호의 부품 중심이 원점 ±100mm 안인지 훑는다. 어두운 판에서 holefit 가 미달하면 `holesearch.py`(모서리 자동 탐색, 5분)를 먼저 돌린다(34번: 4.4px→0.91px 통과) — 링 앵커 유추는 그 다음이다.

7. 읽기 표 `<이름>_read.json` 의 N: 면·링·부품·대조·방향·부품방향·판단과정(센 값). **`부품` 칸은 `713프레임 1, 리벳 2` 형식(괄호 설명 없이)** — 빌드가 모델 부품과 비교해 다르면 저장을 막는다.

**2. 코드 템플릿** (`dropchecker.py` 25·26번 참고)
```python
# ── N ── 교재 NN쪽 N (읽은 것 날짜 — 링·칸·돌기 근거를 주석으로)
sN = SKEL[N - 1]; sN.kw.pop("noPart", None)
sN.note = "[교재 N] …"
sN.kw["hideMade"] = {}                      # 앞 번호 부품을 숨길 때만 채운다(step.kw["hideMade"]={"만든 번호":"보관 이름"})
RV = [sN.attach("리벳", np.eye(3), {"돌기면 -y 1": (블록, "h3")}, rivet=True) for 블록 in (B10, B20)]   # 새 부품의 돌기 → 기존 구멍(꽂힌 채; 띄우려면 hover=40)
PL = sN.recv("713프레임", np.eye(3), {"홀면 -y 열6·줄2": (모터, "p3"), "홀면 -y 열1·줄1": (RV[0], "p2")}, hover=60)   # 새 부품의 구멍 ← 기존 돌기
A.steps[N - 1].cam = (theta, phi, False, None, None, None); A.steps[N - 1].camSrc = "eye"   # axes_fit 결과(오차·roll 을 주석에)
```
- `attach`: 움직이는 새 부품의 **돌기**가 받는 부품의 **구멍**에 들어간다. `rivet=True` 면 리벳(길이 9) 가운데가 구멍 입구 면에 온다(양 끝 4.5mm 씩 두 부품에).
- `recv`: 새 부품의 **구멍**이 기존 부품의 **돌기**를 받는다. 첫 연결로 위치를 계산하고 나머지는 어긋남을 검사한다(경고에 mm). 구멍 이름은 판 `홀면 ±y 열c·줄r`, 프레임·블록은 id(`h1_1` …). **위에서 내려오는 돌기는 `홀면 +y`, 아래에서 올라오는 돌기는 `홀면 -y`**(같은 구멍 id) — 틀리면 경고 "돌기가 들어오는 쪽 면이 아니다(앞뒤가 반대)".
- 새 부품의 회전 `R`: 구멍·돌기가 맞는 자세. 로컬 축·구멍은 `get_part_connectors`·`measure_part`·`get_part_faces` 로 읽는다. 프레임은 길이 로컬 x·구멍 축 로컬 y 가 기본(17프레임: 구멍 `h1_1~h7_1` 간격 10, 두께 5). 로컬 x→세계 z, 로컬 y→세계 x 로 세우려면 `R=[[0,1,0],[0,0,1],[1,0,0]]`.
- 변수는 앞 번호 코드에서 만든 부품 변수(`MO1`, `B10`, `B3[0]` …)를 그대로 쓴다. 이동(`move_made`)이 끝난 부품은 마지막 위치가 이미 반영돼 있다.

**3. 함정 (한 번씩 겪은 것)**
- 위치를 구멍 개수 점수·후보 탐색으로 정하면 틀린다(24번: 볼트·너트 축에 구멍 4개가 쌓인 자리가 이겨 리벳이 너트 구멍에 끼워졌다). 책 링 칸·대칭·돌기 높이 같은 사실로 정한다.
- 조립 스크립트를 분석할 때 `runpy.run_path("<이름>.py", run_name="probe")` 로 실행한다. `__main__` 으로 돌리면 `<이름>_asm.json` 을 덮어쓴다. 읽은 좌표는 마지막 번호까지 이동이 끝난 위치다(번호 시점 위치는 그 번호 앞에서 자른 사본으로).
- 읽기 표가 비었거나 `부품` 칸 형식이 다르면 빌드가 저장하지 않는다(끝줄 ❌). ✓ 한 번호 내용은 못 바꾼다(사용자가 ✓ 를 풀어야 열린다).
- 화면은 사용자가 📷 로 저장한 시점이 코드 시점보다 우선한다 — 책과 비교할 때 `viewer_snippets.md` 2 로 시점을 맞춘다.
- 판이 다른 부품에 가려 홀라인 40% 미달이면 멈추지 말고 0-1 절(`infer_grid.py` — 같은 판의 앞 번호·대칭 끼움·링). 책 그림이 기울어(roll) 그려진 번호도 있다 — 가설을 거르는 근거로 쓰지 않는다.
- `ivs_assembly_refs` 표에는 `created_at` 이 없다(`get_rows` 에 `order_by` 필수). 그림 DB 삭제는 사용자 확인 뒤에만.
- bash 명령 안(heredoc 포함)에 백틱이 많으면 도구가 깨질 수 있다 — 파이썬에서 `chr(96)` 으로 만들거나 파일로 쓴다.
- **책 그림에서 같은 조립이 둘 다른 방향으로 그려져 있으면 대칭(같은 조립을 반대쪽에서 본 것)이다**(드롭체커 27번 아치 둘 = 앞에서 본 것과 뒤에서 본 것 — 뒤에서 보면 판이 가장 앞이라 블록 돌기가 판 끝 구멍을 채워 어둡게 보인다). 모델은 하나로 만들고 하나를 Y축 180° 돌려 둔다.
- **서 있는 구조가 책대로 서면 바닥(y=0) 아래로 내려가는지 숫자로 본다**(드롭체커 27번: 꺾인 팔 3단블록이 −1.6mm). 내려가면 규칙대로 `A.meta["lift"]["N"]` 로 화면 전체를 올린다. 바닥 아래로 안 내려가면 방향을 잘못 읽었을 수 있다 — 책 그림의 서 있는 모습과 비교한다.
- 부품 모델 구멍 좌표는 꺾인 곳(L자 모서리·끝 구멍)이 책과 10mm 안팎 어긋나 보일 수 있다 — `frame_fit.py` 는 그 구멍을 `--빼기` 로 맞춤에서 빼고 어긋남을 보고한다.
- 한 장면의 카메라는 하나인데 부품마다 풀면 값이 다를 수 있다(27번 판 theta −0.43·phi 1.10 vs 프레임 −0.76·0.69) — 책이 부품을 임의 자세로 그렸거나 읽기 오차. **기준 부품의 값**을 쓰고 차이를 읽기 표 판단과정에 적는다.
- **같은 단계에서 "이미 붙은 덩어리"(프레임+꺾인 팔 블록)를 한 덩어리로 같이 띄우는 표현은 불가**(`public/design-verify.js` 방향 검사: 띄우는 방향 dir 의 반대로 돌기가 향해야 한다 — 꽂힌 블록은 프레임과 같은 쪽으로 못 띄운다). **"분리"(결합 전 모습)가 필요하면 덩어리를 쪼갠다**: 프레임은 제자리에 두고, 꽂힌 블록을 그 돌기가 향한 **반대쪽**으로 띄운다(`dir = -peg("p4").dir`) — 드롭체커 27번에서 이렇게 해 사용자 확인("완벽, 책과 같다"). 검사 코드는 안 고쳐도 된다.

- **화살표가 0개면 "제자리 거리 0.0"부터 의심한다**(드롭체커 27번). 뷰어는 완성(제자리) 자세에서 돌기가 구멍에 1mm 이상 들어간 쌍에만 화살표를 그린다(`design-assembly.js` mateGuides → `design-mates.js` check). 제자리를 떨어뜨려 두고 hover 를 더 얹으면 화살표가 안 나온다. **제자리(p)는 늘 돌기-구멍 거리 0.0, 떨어진 모습은 `dir`·`hover` 로만.** `python matecheck.py <이름> N` 이 안내점마다 어느 조건(방향·축 어긋남·깊이)에서 걸리는지 보여 준다. `build.py` 의 "안내점 맞물림 없는 부품" 검사가 같은 것을 잡는다(`<이름>_rules.json` 에 `\"mate_marks\": true` 인 조립도만 막고, 나머지는 ⚠ 참고).
- **3단블록은 돌기가 양쪽 면에 있다 — p3~p5(한 면)·p6~p8(반대 면), 위·아래 끝 p1·p2.** 책 화살표가 어느 돌기에서 나오는지 `get_part_connectors`·`matecheck.py` 로 전부 읽고 정한다. 27번에서 p7(판 반대 면)로 짐작해 틀렸고, 정답은 p3(프레임 쪽 면, 판 위로 나온 윗돌기 — 판은 y 15~35 라 y 40 의 p3 가 판 위로 나온다).
- **사용자가 "책과 같다"고 확인한 배치는 건드리지 않는다.** 화살표가 안 나오면 배치를 의심하지 말고 "맞물림 조건 중 무엇이 걸리는가"를 숫자로 본다(27번: 그룹 맞바꿈이 틀린 게 아니라 제자리가 30mm 떨어져 있었을 뿐이었다 — 이동하면 되는 값).
- **"분리해줘" = 그 부품을 결합 전 모습으로 띄워 화살표를 보이라는 뜻**이다. 부품마다 따로(프레임·판·블록·꺾인 팔 블록 모두), 서로 다른 hover 로.

### 예시: 화살표가 안 나올 때 (드롭체커 27번, 2026-10-13 — 다음에 같은 경우가 생기면 이 순서로)
1. 화면에서 번호를 연 뒤 `br.guides` 를 가로채 목록 길이를 본다(`viewer_snippets.md`) — 0이면 맞물린 쌍이 없다는 뜻(`guideMode: "mates"` 조립도는 안내점이 아니라 맞물림에서 그린다).
2. `python matecheck.py dropchecker 27` — 안내점마다 돌기 후보를 조건별로 채점한다. 27번 옛 상태 출력 요지: `블록 p7 ↔ 프레임 h5: 돌기 뿌리가 구멍 밖(30mm)` / `p3: 깊이 −15, 축 어긋남 0.0`. → 맞는 돌기는 p3 이고 15mm 모자란다는 것까지 한 번에 나온다.
3. 고침: 그룹을 +15 이동(제자리 거리 0.0)하고 hover 를 +15 해 보이는 자리는 그대로(`dropchecker.py` `_sd * 45.0`). 분리(결합 전)는 부품별 hover(프레임 0 · 판 30 · 블록 60 · 꺾인 팔 블록 30).
4. `python build.py <이름> --write`(검사 0건) → 화면에서 화살표 수를 세고(27번: 아치당 9, 합계 18) 책과 비교 → `record_check.py`.

- **책이 이미 꽂아 둔 리벳은 `extra["seated"] = True` 로 표시하되 `marks`(초록 링 자리)는 지우지 않는다**(29번: dir·marks 를 지웠더니 검증 "안내 화살표(marks)가 없는 부품 6개" 로 빌드가 막혔다 — seated 는 marks 가 링이다). seated 를 안 쓰면 리벳이 기본 hover 로 떠서 화살표가 책보다 많이 나온다(29번 12개 → 6개).
- **앞 번호에서 짝이 바뀌었으면 합치는 번호에서 짝대로 묶는다**(28번: 27번이 두 그룹을 맞바꿨으므로 한 아치 = 판+블록 묶음 k + 프레임·꺾인 블록 `ARCH27[1−k]`). 놓은 뒤 "위치 출력"(프레임·판·블록 z)으로 짝이 맞는지 확인한다.
- **한 번호에서 새로 알게 된 짝·배치·정정은 읽기 표 판단과정과 진행기록 문서에 적는다** — 다음 번호 시작 때 `number_start` 의 "이미 알고 있는 정보" 블록이 앞 두 번호의 읽기 표를 그대로 보여 준다.

- **사용자가 지정해 둔 것이 무조건 우선이다(사용자 2026-10-13 "무조건 사용자가 지정해놓은 걸 우선으로 해").** 화면의 ❄ 모습 기록(부품 위치 p·자세 r)과 📷 카메라는 코드 값을 덮는다 — **코드의 hover·dir 를 고쳐도 사용자 기록이 있는 부품은 화면이 안 바뀐다**(드롭체커 29번 "리벳 분리해줘": 사용자 ❄ 기록에 새 리벳이 제자리로 저장돼 있어 코드로 분리해도 사용자 화면은 그대로였다). 그래서 ① 번호를 시작할 때 `number_start` 의 "사용자 ❄ 기록 위치가 코드와 다른 부품"·"사용자 📷 카메라" 줄을 읽는다(위치까지 비교하도록 고쳤다) ② 사용자 기록과 내 값이 다르면 사용자 값을 따른다(카메라: 코드 `cam` 을 사용자 📷 값에 맞추고 비교 화면도 덮어쓰지 않는다 — 29번 사용자 phi 1.076 vs 내 풀이 0.86) ③ 사용자가 고치라고 한 부품이 ❄ 기록에 있으면 코드와 **기록 둘 다** 맞춘다: `python pose_edit.py <이름> N "<라벨>:x,y,z;…"`(백업 자동 `refs/<이름>/_pose_backup/`, `--보기`로 기록 위치 확인). 사용자가 안 시킨 기록은 건드리지 않는다.
- **"분리해줘"는 책이 꽂힌 모양으로 그렸어도 한다**(29번 리벳: 책은 BC 에 꽂힌 리벳이지만 사용자 지시로 결합 전으로 띄움). 지시가 책과 다르면 지시를 따르고 읽기 표 판단과정에 "사용자 지시로 책과 다름"을 적는다. 리벳 분리 = 리벳 hover 30, 판·막대 hover 60(리벳이 판·막대보다 BC 쪽에 남아 세 덩어리).
- **자동화 = 내가 판단하고 멈추지 않는다(사용자 2026-10-14 "니가 판단을 해야 자동화", "막힌 게 없는데 왜 멈춰 바로바로 진행").** 번호를 끝내면(빌드 0건·비교 증거·읽기 표·DB 그림) 사용자 ✓ 를 기다리지 않고 다음 번호로 간다. 대신 **번호마다 책 그림과 우리 화면(책과 같은 시점)을 사용자 폰으로 바로 보낸다**(`SendUserFile` 책 `refs/<이름>/NN.jpg` + 비교 증거 `refs/<이름>/cmp/NN.png`, 상태 proactive, "이상하면 말씀해 주세요, 답이 없으면 다음 번호로 계속" 한 줄). 답이 없다고 멈추지 않는다 — 사용자가 이상하다고 하면 그 번호만 고친다. 규칙 점검이 ❌ 로 막으면 사용자에게 묻지 말고 근거로 판단해 고친다(30번: 앵커만 유추 격자를 `rulecheck` 가 앵커 잔차·안정성으로 보게 사용자 지시로 고침). 정말 규칙 우회가 필요해 보일 때만 멈춰 보고한다.

## ✅ 번호를 시작할 때 맨 먼저 — 앞 번호까지 만든 모델에서 읽는다 (사용자 지시 2026-10-13, 드롭체커 28번: "뒤로 가도 항상 같은 기준으로 시작을 하니 점점 더 병신같아진다")
**책 그림 한 장의 격자부터 들어가지 않는다.** (`python number_start.py <이름> N` 맨 위의 "이미 알고 있는 정보" 블록이 아래 ①~⑤를 자동으로 보여 준다 — 쓴·남은 부품, 앞 두 번호 읽기 표(부품방향·정정), 창고·history, 사용자의 최근 교정, pegprobe 안내. 이 블록을 읽은 뒤에 이미지 작업을 시작한다.) 앞 번호에서 한 작업(읽기 표·진행기록 문서·창고 history)과 쓴 부품(03·LIST)이 이미 있다. 순서: ① 이번 번호의 사용 부품과, 앞 번호까지 쓴 부품·남은 부품(LIST 대비) ② 받는 부품(판 등)에서 **지금 비어 있는 구멍·돌기를 모델로 조회**(`python pegprobe.py <이름> 빈구멍 <칸> <줄>` · `위돌기` · `빈돌기 <부품>`) — 28번: 713프레임 위 판에서 리벳(칸1 줄1·줄7)·모터 돌기(6·8칸 줄2·6)가 쓰는 구멍을 빼면 후보가 좁아지고, 책 링 4개(리벳 옆 (2,1)·(2,7), 4칸 떨어진 (6,1)·(6,7))가 모두 빈 구멍이었다 ③ 그다음에야 책 그림으로 후보 중 어느 것인지 가린다(링·돌기 끝을 색으로 검출). ④ 이미지 격자는 **카메라를 풀고 화면과 비교하려는 용도**다 — 도구 기준(`holefit` 40%·2.0px)에 막히면 모델에서 칸이 확정된 점(리벳·링)을 앵커로 `infer_grid`(앵커만 유추, 6곳 이상)로 푼다. 한 장의 그림을 두고 모서리·옵션을 바꿔 가며 튜닝하지 않는다. **축선 원점은 늘 판 가운데 칸·가운데 줄**(앞 번호와 같게; 가려져 있어도 모델 좌표로 투영) — 도구가 고른 가장자리 앵커가 아니다.

### ✅ 0-1. 한 번호로 안 풀리면 "탈락"이 아니라 정보를 모아 유추한다 (사용자 지시 2026-10-13, 드롭체커 24·25번)
기준(구멍 ≥40% 등)에 모자랄 때 멈추거나 승인으로 넘기지 않는다. **그 번호·앞뒤 번호·대칭쪽·완성 사진의 정보를 전부 모아, 서로 맞는지(잔차 px)로 푼다.** 순서:
1. **`holefit.py`** — 기본/어두운판 → 실패하면 어두운 구멍(DoG)을 자동으로 이어서 시도한다(출력에 방식별 결과가 다 나온다).
2. 그래도 개수가 모자라면(다른 부품에 가려 구멍이 일부만 보임) **`infer_grid.py`** — 근거를 합쳐 푼다. 있는 근거를 옵션으로 전부 준다:
   `python infer_grid.py <이름> <번호> <라벨> <칸> <줄> 모서리8개 --판 16:P --거울 16 줄 --링 "x,y;x,y;…" [--anchor …] [--cam θ φ]`
   (`--판` 같은 판의 앞 번호 fits · `--거울` 반대편 유닛이 끼워진 번호 — 그 번호의 끼움 칸을 줄(또는 칸)로 뒤집어 앵커 칸으로 씀 · `--링` 책 초록 링 중심 픽셀(칸 번호 없이, 어느 링이 어느 칸인지는 도구가 모든 짝을 돌려 고름)). 근거 내용:
   ① **같은 판의 3차원 치수**(앞 번호에서 전체가 보인 판, 10mm 간격) ② 그림에서 선명하게 검출된 구멍 ③ **앵커** = 칸을 아는 책 초록 링(대칭 쪽에서 끼운 자리, 읽기 표, 뒷 번호로 칸이 정해진 것) ④ 줄·칸 배정 가설을 모두 돌려 잔차가 가장 작은 것.
   가설이 하나로 갈리지 않으면(2등이 1등의 1.3배 미만) 저장하지 않고 필요한 추가 근거를 말한다 — **뒷 번호 그림**(같은 몸체가 보이는 번호), **완성 사진(00)**, **대칭 유닛의 끼움**.

### ✅ 0-2. 판이 앞 번호에서는 보였는데 이번에는 가려졌다 → 앞 번호 책 그림과 판 무늬를 맞춘다 (사용자 지시 2026-10-13, 드롭체커 29번 — 새 판·프레임에 가려지고 앞에서 본 각도라 `holefit` 평균 4.7~8.5px, 앵커 5~7개 풀이 평균 2.9px 로 안 됐다)

- **`plate_match` 가 불안정하면(인라이어 20 미만·roll 큼·2등과 비 1.5 미만 — 30번: 인라이어 18·roll −14°) 쓰지 않는다.** 대신 **앞 번호에서 우리가 놓아 3D 가 확정된 점 + 판 먼 모서리 2곳을 앵커 8개 내외로 `infer_grid` 앵커만 유추**로 푼다(30번: 29번 리벳 6개 바깥 끝 + 판 먼 모서리 2곳, 평균 0.82·최대 1.34px, 하나씩 빼도 theta·phi·fov 가 안 변함 = 안정). **풀이가 안정한지는 앵커를 하나씩 빼 보아 확인한다**(29번 앵커 7개는 하나만 빼도 크게 변해 불안정했다). 앵커로 쓰기 좋은 점: 앞 번호에서 새로 단 부품의 눈에 띄는 끝(리벳 주황 링 중심·블록 윗돌기)과 판 먼 쪽 바깥 모서리.
- **판 칸 밖으로 환산되는 매칭은 버린다**(밀린 칸이 판 바깥 = 판 위에 없는 구멍 = 잘못 맞은 매칭, 도구가 처리).
- **규칙 점검은 이런 유추 격자를 ❌("구멍 0개 근거 부족")로 본다 — 사용자 ✓ 가 있으면 ⚠.** 처음부터 이 사실을 알고, 모델·읽기 표·증거까지 다 한 뒤 "격자만 사용자 ✓ 대기"라고 한 번에 보고한다(규칙 우회 금지, `rulecheck.py` 는 지시 없이 안 고친다).

### ✅ 0-3. 목표 구멍 둘레 모서리까지 새 부품(모터 등) 몸체가 덮어 0-1·0-2 로도 안 풀린다 → 다른 색·모양의 "이미 아는 점"을 그림에 직접 선으로 이어 비례로 읽는다 (사용자 지시 2026-10-19, 오토타깃 24번)
**언제:** `holefit`·`plate_match`·`infer_grid --anchor` 를 다 시도해도(각각 3회 이상) 잔차가 수십~100px 대로 안 내려간다 — 보통 앵커로 쓴 점(리벳 등)이 서로 비슷하게 생겨 **어느 점이 어느 구멍인지 픽셀 식별 자체가 애매해서**다(좌표 계산이 아니라 대응점 오인이 원인).
1. **눈에 띄게 다른 색·모양의 "이미 3D 가 확정된" 점 하나를 그림에서 고른다**(예: 다른 번호의 리벳, 지금 놓는 부품 자신의 독특한 생김새 — 모터의 노출된 윗돌기·빨간 십자 등). 후보가 여럿이면(비슷한 주황 리벳이 여러 개) 가장 멀리·가장 뚜렷이 떨어져 헷갈릴 리 없는 것 하나를 고른다.
2. **그 점과 목표(초록 원 등)를 실제로 그림 위에 선으로 그어 눈으로 본다** — 머릿속 좌표 계산이 아니라 `cv2.line`/`cv2.circle` 로 책 그림 원본(`refs/<이름>/NN.jpg`) 위에 점·선을 그려 `Read` 로 열어 확인한다(스크래치패드에 저장, 프로젝트에 커밋 금지). **한 번 그려서 눈으로 맞는지 보기 전에는 좌표를 확정하지 않는다** — 처음 읽은 픽셀이 실제 표시와 어긋나 있을 수 있다(오토타깃 24번: 리벳·목표점 픽셀을 다시 재서 두 번 고쳤다).
3. **선이 목표와 같은 줄(칸 또는 줄)을 지나면 그대로 쓴다.** 예: 기준점이 세계 x=−40 인데 목표가 그림에서 기준점과 거의 같은 세로줄이면, 목표도 x=−40 칸으로 본다(좌표 계산 없이 바로 정해진다 — 가장 믿을 수 있는 경우).
3-1. **그을 선 두 가지(사용자 지시 2026-10-19 — 홀라인 작업에 항상 추가한다):**
   - **리벳↔리벳 선:** 칸·줄이 이미 확정된 리벳(앞 번호에서 놓아 세계 좌표를 아는 것) 둘을 그림 위에서 찾아 직선으로 잇는다. 그 직선이 지나는 구멍들을 1칸씩 세면, 두 리벳 사이의 세계 칸 수(이미 안다)와 그림에서 센 구멍 수가 같아야 한다 — 다르면 리벳 픽셀을 잘못 짚었거나 직선이 다른 줄로 샌 것이니 다시 짚는다. 같으면 그 직선을 '칸1 간격' 자(scale bar)로 써서 목표가 몇 칸째인지 선 위에서 센다.
   - **모터(또는 새 부품) 돌기↔돌기 선:** 새로 놓는 부품 자신의 돌기 둘(지금 결합하려는 목표 둘)을 직선으로 잇는다. 부품 연결점 데이터(`get_part_connectors`)로 이미 아는 피치(예: 모터 옆 돌기 20mm = 2칸)가 그 직선의 세계 길이와 같아야 하므로, 리벳↔리벳 선으로 잰 '칸1 간격' 픽셀 길이와 비교해 돌기↔돌기 선의 픽셀 길이가 정확히 피치만큼(2칸분)인지 맞춰 본다 — 둘이 같은 자로 재서 맞으면(같은 기울기·같은 비율) 칸 배정이 맞다는 2차 증거다.
   - 두 선 모두 `cv2.line`으로 책 그림 원본 위에 실제로 그어 `Read` 로 본다(원인 한 줄 분석 없이 "맞겠지"로 넘기지 않는다). 리벳↔리벳 선의 칸 수 세기와 돌기↔돌기 선의 피치 비율이 **둘 다** 맞아야 그 칸 배정을 쓴다 — 하나만 맞으면 아직 추정(review)이다.
4. **두 목표(예: 새 부품의 돌기 두 개)가 같이 있으면 부품의 알려진 간격(피치)으로 교차 검증한다** — 두 목표 사이의 세계 거리는 부품 연결점 데이터(`get_part_connectors`)로 이미 안다(예: 모터 옆 돌기 피치 20mm = 2칸). 기준점→목표1, 기준점→목표2 를 각각 비례식(2점 선형 보간, 픽셀 Δ ↔ 세계 Δ)으로 풀어 두 결과의 칸 차이가 그 피치와 맞는지 확인한다 — 맞으면 식 자체가 맞다는 증거(자체 검산), 안 맞으면 기준점이나 목표 픽셀을 잘못 읽은 것이니 다시 그려 본다.
5. **한계:** 비례식은 국소적(가까운 두 벡터로 1차 근사)이라 기준점이 목표에서 멀수록(특히 화면 반대쪽) 오차가 커진다 — 정식 PnP(0-1·0-2 절)가 수렴하면 그게 우선이다. 이 절은 정식 방법이 막혔을 때의 마지막 수단이다. 결과는 소수점 단위까지 나오고(예: 칸 5.3) 가까운 정수로 반올림하되, 소수부가 0.3 이상이면 다음 번호 책에서 재확인 필요(⚠)로 남긴다.
6. 코드에는 `⚠` 주석으로 기준점·근거·반올림 전 소수값을 남기고, `step.kw["review"] = True` 로 표시한다(완료로 단정하지 않는다).

(**앞 과정(02 이미지·03 부품 체크·04 창고 정리)과 앞 번호 확인이 끝나지 않았으면 번호를 시작하지 않는다 — 확인은 내가 한다(책↔화면 비교 증거 `record_check.py`; 사용자 점검을 받으라는 뜻이 아니다, 사용자 2026-10-14).** 1번부터 끝 번호까지 차례로 하고, 번호 하나를 다 끝내기 전에는 다음 번호로 가지 않는다.)
번호를 시작할 때마다 SKILL.md 를 처음부터 다시 읽고, 이번 번호에서 특히 지킬 규칙 3개를 첫 보고 한 줄에 적는다.
**시작 명령:** `python number_start.py <이름> <번호>` — **먼저 앞 과정을 점검해 끝나지 않은 것(02 책 그림 없음 · 03 사용 부품 없음 · 04 창고·history 없음 · 앞 번호에 사용자 ✓ 도 비교 증거도 없음)이 있으면 그 목록만 보여 주고 멈춘다. 읽기 표·규칙 파일도 만들지 않는다 — 목록을 끝낸 뒤 다시 돌린다**(드롭체커 2026-10-12: 창고 정리를 건너뛰고 1번 격자부터 시작한 사례). 통과하면 읽기 표 칸 만들기(부품은 03 의 사용 부품으로 채움)·규칙 켜기를 대신 하고, 파일 상태(☑/☐)·창고·✓ 여부·방향 기준 부품 경고·**사용자가 이 번호에 남긴 ❄ 모습 기록과 📷 카메라(코드와 다른 부품 표시)**·다음에 할 일을 한 번에 보여 준다. 사용자 기록이 있는 값은 코드 값보다 사용자 값이 기준이다.

### 5-0. 축은 측정한다(투석기 24번, 2026-10-12)
판 구멍이 안 보이거나 일부만 보이면 **`holefit.py`(기본→어두운판→자동 DoG) 후 `infer_grid.py` 로 같은 판의 앞 번호·대칭 쪽 끼움·책 링·뒷 번호·완성 사진 정보를 모아 유추한다(위 0-1 절)** — 이웃 간격 각도·눈대중으로 `NN_axes.json` 의 X·Z 를 정하지 않는다. 축은 유추한 격자에서 `axes_fit.py` 로 계산한다. 축을 정한 뒤 부품마다 긴 방향·돌기 줄이 어느 축인지 읽기 표에 쓰고 놓는다. 자세한 사례는 `user_diffs/요청차이.md`.
- **+Z 의 부호는 칸·줄 번호 순서가 아니라 오른손 법칙(X×Y=Z)으로 정한다**(투석기 33~35번: 판 칸 번호가 오른쪽으로 늘어난다는 이유로 +Z 를 오른쪽 아래로 그려 틀렸다 — 몸 앞(+X)이 왼쪽 아래로 오는 시점에서는 +Z 가 왼쪽 위다). 시점마다 X 가 카메라 쪽/반대쪽, Y 위를 정하고 Z 방향을 계산해서 적는다.
- **카메라 theta·phi 는 측정한 X·Z 화면 방향으로 계산한다**: 화면(위가 +) 각도 αX·αZ 에서 cosφ=√(−tanαX·tanαZ), tanθ=−tanαX/cosφ (X 가 오른쪽이면 cosθ>0). 원근이 강해 값이 안 나오면 `axes_fit.py`(격자 PnP)를 쓴다. 눈대중 카메라(guess)로 두지 않는다.
- **전체를 올리는 `xform`(바퀴가 바닥 아래로 나올 때 등)은 부품·고무줄·줄 모두에 같이 적용된다**(뷰어가 처리). 새 번호에서 `xform` 을 쓰면 그 번호부터 줄이 제자리에 붙어 있는지 화면으로 본다.

## 5-1. 책 보기
1. 번호의 책 그림을 왼쪽→오른쪽, 위→아래로 훑어 부품 → 초록 원 → 안내선을 읽는다. 앞·뒤 번호 그림과 완성품 사진(00)을 같이 본다.
2. **카메라가 보는 면:** 어떤 부품의 어느 면이 카메라 쪽인지, 판이 서 있는지 눕는지, 가까운 쪽·화면 오른쪽·위가 부품의 ±X·±Y·±Z 중 어디인지 적는다.
3. **가위:** 부품만 남기고 글씨·테두리를 자른다(`<번호>_lv.json` 의 crop·erase).
4. **구멍 점 = 홀라인 맞추기(체크리스트 0번, 가장 중요) — `holefit.py` 를 쓴다**(모서리 4곳 → 구멍 검출 → 격자 호모그래피, 오차 기준 미달이면 저장 안 됨, `hf/` 확인 그림을 눈으로 본다). 아래 설명은 그 앞의 원칙이다. 격자는 아래(이미 놓인) 부품, 흰 판의 실제 구멍에 맞춘다(투석기 18번 — 사용자: "베이스가 화이트잖아"):** 위에 얹는 부품(빨간 프레임)·돌기 끝 링으로 격자를 만들면 가운데 축선이 판 가운데에서 어긋난다. 판 영역에서 `cv2.HoughCircles`(반지름 11~22px)로 구멍 중심을 모두 찾고, 이웃 간격(X 한 칸·Z 한 칸 벡터)으로 칸·줄 번호를 붙여 호모그래피로 격자(`fits/NN_P3.json`)를 만든다. 칸 번호는 스터드·가장자리로 정하고 추정이면 적는다. 옛 격자 파일은 지운다(함께 그려짐). **그림에서 가려 안 보이는 구멍(연장한 점)은 그리지 않는다 — `"hide_est": true`(20번: 칸13~15 점·번호가 브라켓 위에 그려져 있었다). 최종 그림은 번호 하나 끝낼 때 전체를 한 번 눈으로 보고 어색한 곳(점이 부품이 아닌 곳에 있는지, 번호가 겹치는지)을 찾아 고친다.** **기준(베이스)은 "결합을 받는 부품"이다 — 그 번호에서 새 부품이 결합하는 쪽(20번: 215프레임 긴 팔)에 격자를 그린다. 흰 판이 보인다고 흰 판을 기준으로 하지 않는다. 줄이 둘인 프레임은 줄 번호를 구멍 열(칸)과 한 칸씩 어긋나지 않게 맞추고, 모든 구멍(리벳 바로 위 구멍 포함)에 점이 있는지 확대해서 센다.** **격자 점은 구멍의 눈에 보이는 중심(구멍 안쪽 어두운 영역의 무게중심)에 둔다 — 눈대중 모서리·템플릿을 처음 격자 위치에서 자르면 처음 위치 쪽으로 쏠려 오차가 작게 나온다(투석기 20번: 점이 구멍 아래 테두리를 약 9px 지났다). 확대해서 점이 구멍 한가운데에 앉았는지 눈으로 확인하고 보고한다.** **격자는 구멍 줄(홀 라인) 위에만 그린다 — 줄이 둘뿐이거나 옆면을 비스듬히 본 프레임은 `"grid_rows_only": true` 로 칸 사이 세로선을 빼야 평행사변형처럼 안 보인다(20번 "격자를 왜 저렇게 그렸어"). **축선은 항상 구멍 줄(홀 라인)의 구멍 중심을 지나야 한다 — 줄이 둘뿐인 프레임(215프레임 등)은 가운데가 구멍 줄 사이라 `<번호>_axes.json` 에 `"center_row": 1` 처럼 줄 번호를 적어 그 줄의 구멍 중심을 지나게 한다(투석기 20번). 눈대중 모서리 4곳으로 격자를 만들지 말고 밝기 변화·Hough 로 실제 구멍을 찾아 맞춘다(20번: 모서리로 읽은 칸15가 실제 칸12였다).** **잔차는 실제 구멍과의 거리(평균·최대 px)로 말하고, 가운데 열·줄 선이 실제 구멍 중심에서 벗어난 거리(px, 구멍 반지름 대비)를 잰다.** 격자만으로 카메라를 맞추면 +Y 가 아래를 향하는 거울 해가 섞일 수 있으니 +Y 방향을 확인한다. 보이는 구멍 위에 칸·줄 점을 만든다(`holefit.py`, 원본 그림 좌표; 판이 가려지면 `infer_grid.py`). 한 직선 위에 놓인 구멍들은 여러 부품의 구멍이라도 한 줄(N칸×1줄)로 만든다(투석기 15번: 블록 둘의 큰 구멍 4개 = 4칸×1줄).
5. **방향 표시:** 그림의 +X·+Y·+Z 가 화면에서 가리키는 방향을 읽어 `refs/<이름>/<번호>_axes.json` 에 적는다(`global`, 필요한 곳에 `local`). 값은 4번의 구멍 점에서 `python axes_fit.py <이름> <번호> <라벨> <칸수> <줄수> <칸방향> <줄방향>` 으로 계산한다(앞 번호 값을 복사하지 않는다, `fit` 이 없으면 손으로 쓴 값). 오차 2px 초과나 phi 1.55 초과면 쓰지 않는다.
   - **방향을 파악할 때 기준이 되는 부품: 모터 종류, 메인보드, 기어 종류.** 이 부품들이 어느 쪽을 보는지(DC모터의 돌기 면·빨간 십자 면·옆돌기, 메인보드의 케이블·버튼 쪽, 기어의 종류와 핀·T축 구멍이 중심의 어느 쪽인지)를 먼저 읽고 그것으로 X·Y·Z 를 정한다. 방향이 정해진 부품이라 틀리면 뒤 번호가 다 어긋난다.
   - **가운데에 그린 X·Y·Z 축선을 기준으로** 각 부품이 어느 쪽에 있고 어느 쪽을 보는지(오른쪽·왼쪽·위·아래·앞·뒤)를 판단해 읽기 표 '방향'에 적는다. 이 판단은 그림을 보고 하지 않고 축선을 보고 한다.
6. **회전·격자 그림 — 사용자가 "이미지를 회전해서 맞추라"고 하면 `<번호>_axes.json` 에 `"level": true` 를 넣고 `refs_rect.py` 를 돌린다(투석기 18번): 판 구멍 줄이 수평이 되게 그림을 실제로 돌리고(1번 그림처럼) 축선·방향 표시도 같이 돌아간다. `level` 없이 돌리면 축선에 맞추는 0.0x° 미세 회전뿐이라 그림이 기울어진 채다. 확인은 돌린 각도(°)와 가운데 줄·열이 축선에서 벗어난 거리(px)로 말한다:** `<번호>_axes.json` 에 `rotate_to`(구멍 점 줄이 놓인 축, 예: "Z")를 적고 `python refs_rect.py <이름> <번호>` 를 돌린다. 축선이 지나는 **가운데 줄·가운데 열**(기준 판의 가운데 칸·가운데 줄 구멍)의 방향이 X·Z 축선과 같은 방향이 되게 작은 각도로 **회전만** 한다(늘이기·펴기·90° 눕히기·거울 금지). 줄들은 원근 때문에 부채꼴로 벌어져 줄마다 각도가 달라서(투석기 16번: 줄 45°~37°) 가장자리 줄이 4~5° 어긋나는 것은 정상이다. 순서는 방향 → 회전 → 격자이다. 기준은 원형 부품(기어·바퀴 — 거의 없다)이 아니라 판단이 잘 되는 줄(판 격자의 줄, 블록 구멍 줄)로 하고, 그 줄이 놓인 축(X 또는 Z)의 축선에 맞춘다. 가운데 축선(기준 판의 가운데 구멍에서 만난다)은 돌지 않는다. 격자 점은 눈으로 읽은 모서리에서 계산한 값이라 실제 구멍 중심과 평균 3~4px(간격의 약 7%) 차이가 날 수 있다. 회전 뒤 구멍이 축선에서 벗어난 거리(px)를 확인하고, NN_2 를 열어 점이 구멍·링 중심에 앉았는지 확인한다. 가려진 칸은 보이는 구멍에서 연장하고 "연장"이라 적는다. 만들자마자 DB 에 올린다.
7. **읽기 표**(`<이름>_read.json`): 면·링(센 칸·줄)·부품(이름 개수)·방향·부품방향·판단과정. 개수·종류는 확대해서 직접 센 값만 적고, 짐작은 "추정".

## 5-2. 부품 올려두기 (창고에 책과 같은 모습·자세로)
1. 창고(slot)를 먼저 확인한다(04).
2. 해당 번호의 부품을 가져와 책과 같은 모습·자세로 올려둔다. 자세는 읽기 표의 '부품방향' 그대로(첫 부품은 좌표로).
3. **폭이 다른 부품이 맞닿으면(215프레임 20mm 와 1열브라켓 10mm 등) 위/아래 어느 쪽에 붙는지를 책 확대로 두 부품의 위·아래 가장자리를 비교해 정한다(투석기 20번: 브라켓이 팔 위쪽 구멍 줄에 붙고 아래 줄이 드러남).** 확인 세 가지: **같은 부품인가**(이름·개수, LIST) / **동일한 자세인가**(방향·모습) / **결합되는 곳**(구멍·돌기·링 칸).
4. DC모터·메인보드처럼 방향이 정해진 부품과 창고에서 꺼내 합치는 그룹은 읽기 표에 방향 카드(면 사실 = `measure_part`·`get_part_connectors`, 책 증거 = 케이블·빨간 십자·접시 머리·돌기 수)를 먼저 쓰고 놓는다. 바퀴처럼 방향 있는 부품도 `measure_part` 로 면을 읽는다.
5. 책이 이미 꽂아 둔 부품은 꽂힌 채로, 결합 전으로 그린 부품은 띄워서 놓는다.

## 5-3. 결합
1. 조립할 부품을 선택해 결합한다(`attach`·`recv`, 그룹은 강체로 옮겨 합침). 좌표를 손으로 계산해 `place` 로만 놓지 않는다.
   - **✓ 한 앞 번호에서 만든 부품을 옮겨 붙일 때는 `move_group` 이 아니라 `move_made(A.group(이름, 부품들), R, pivot, shift, dir, hover, group=이름)` 을 쓴다**(투석기 17번). `move_group` 은 앞 번호 부품 데이터에 move 를 써서 ✓ 단계 지문이 바뀌어 빌드가 막힌다. `move_made` 는 이동을 이번 번호 데이터(`moveMade`)에만 적고, 화면·도구는 `design-assemblies.js` 끝의 합치기 코드로 읽는다. 부품마다 한 번만 옮길 수 있다.
   - **옮길 자세는 돌기 모양으로 정한다:** 옮길 묶음의 아래 돌기 위치를 회전시킨 뒤 받는 구멍 칸 위치와 모양(긴 변·짧은 변 개수, 거울 여부)을 맞춰 최대 어긋남(mm)을 출력한다(투석기 17번 L 둘: 0.30mm). 거울 모양이면 뒤집은 것이 아니라 서로 다른 묶음(A·B)이 맞는 것이다.
2. 확인 세 가지: **바른 부품인가** / **동일한 자세인가** / **결합되는 곳에 바르게 결합되는가**(책 링의 칸과 같은 해만 받는다).
3. **화면에서 화살표가 나오는지 확인한다(투석기 19번):** `build.py` 의 "안내 화살표 없는 부품 0" 은 화면 맞물림 검사와 다르다. 새 부품이 있는 번호는 화면을 열어 화살표가 그려졌는지 눈으로 본다. 안 나오면 브라우저에서 `IVS_MATES.check` 의 `mated` 수와 부품 DB 연결점의 구멍 `len`(깊이) 유무를 확인한다 — 215프레임 구멍에 `len` 이 없어 돌기가 안 들어간 것으로 판정돼 화살표가 빠졌다(DB 에 `len` 5 를 추가해 해결, 515·713프레임·DC모터·중간바퀴도 `len` 이 없으니 처음 쓰는 번호에서 같은 확인)., 겹침 없음, 바닥 아래 없음, 화살표 수 = 돌기 수. 돌기가 중심에서 치우친 부품은 오차를 한쪽에 몰지 않고 양쪽에 나눈다. 너트는 결합하는 쪽의 반대쪽에 둔다.

## 5-4. 모를 때: 유추
부품이 무엇인지, 어디에 결합되는지 모르겠으면 뒷부분의 결합 모습을 보고 유추한다. 앞·뒤 번호 그림과 완성품 사진을 같이 본다. 링이 안 맞으면 내 모델이 틀린 것으로 본다. 유추한 값은 "추정"이라 적는다.

번호 하나를 끝낼 때 `python rulecheck.py <이름> <번호>` 를 돌린다. ❌ 가 있으면 그 줄의 "해결" 명령대로 하고, 기준 미달이면 멈추지 말고 위 0-1 절의 순서(holefit 자동 DoG → infer_grid.py 로 앞·뒤 번호·대칭·완성 사진 정보를 모아 유추)로 푼다. 유추로도 가설이 하나로 안 갈릴 때만 멈추고 시도한 방법·수치·필요한 추가 근거를 보고한다(`holefit.py` 옵션 추가·손으로 만든 격자·추정 카메라로 지나가지 않는다 — 드롭체커 3~14번 사례). `<이름>_rules.json` 에 `"rulecheck": true` 인 조립도만 ❌ 로 막는다(새 조립도는 켠다).

## 5-6. 고무줄(규격 없는 줄) 사용 규칙 (사용자 지시 2026-10-12, 투석기 22번)
고무밴드·줄처럼 3D 모델이 없는 것은 부품이 아니라 **단계 데이터 `bands`**(노란 관)로 그린다. 부품 목록에는 "고무밴드 N (3D 모델 없음)" 만 적는다.
1. **책을 먼저 본다:** 고무줄이 어디(구멍·축·부시)에 어떻게 걸리는지, 걸리면서 **어떤 부품이 움직이는지**(22번: 긴 팔이 T축을 중심으로 지렛대처럼 섬)를 책 그림에서 찾는다. 움직임은 `move_made` 로 먼저 하고(길을 막는 부품은 각도 스윕으로 계산 — 2단블록에 걸려 약 75°), 고무줄은 그 최종 자세의 구멍 좌표(`part.hole(id)["pos"]`)에 건다.
2. **모양:** ① 가장 바깥에 보인다 — 부품 면(215프레임 바깥 면 z ±5)·판·블록(z ±10)에 파고들지 않는다. ② 구멍은 한쪽 바깥에서 들어가 반대쪽 바깥으로 나온다(앞뒤 점 z ±8). ③ 두 고리가 구멍에서 만나는 **8자**. ④ **팽팽하게** — 구멍과 걸이(부시) 사이는 접선 직선, 걸이 바깥쪽만 둥글게 감는다(늘어진 곡선 금지).
3. **계속 보인다:** `bands` 를 쓴 번호부터 뒤 번호에도 자동으로 이어 그려진다. 몸이 창고에 들어가 안 보이는 번호는 `kw["bandsHideAt"] = [번호…]`(걸이 부품의 `hideAt` 과 같게), 줄을 푸는 번호는 `kw["bandsEnd"] = True`. 걸린 팔·축을 뒤 번호에서 다시 움직이면 그 번호에 `bandsEnd` 를 쓰고 새 위치로 `bands` 를 다시 쓴다.
4. **확인:** 수치로 줄이 부품과 겹침 0 인지(팔·판·블록 상자와 비교) 보고, 화면에서 구멍 통과·팽팽함을 눈으로 본다. 책 그림과 나란히 비교해 증거를 남긴다. 위치·기울기 중 책에서 못 읽은 것은 [추정] 으로 적는다.
5. **전체를 올리는 `xform` 이 있으면 줄도 같이 움직인다**(뷰어 `bandsAt` 가 처리, 투석기 31번부터 27mm — 2026-10-12 "31번에 고무줄 위치가 이상해" 사례: 부품만 올라가고 줄이 제자리에 남았음). `xform` 을 쓰는 번호부터는 고무줄이 걸린 부시·구멍에 그대로 붙어 있는지 화면에서 본다.
(구현: `design.html` bridge `bands(list)`, `design-assembly.js` `bandsAt(step)`, 예: `catapult.py` 22번 블록.)
6. **돌기(걸이)에 거는 법 — 반드시 몸통(안쪽)에 건다(사용자 지시 2026-10-19, 오토타깃 14번):** 밴드는 돌기 **끝 바깥을 감싸지 않고**(돌기 위에 걸쳐 보인다) 돌기 **몸통을 한 바퀴 반 돌아** 건다 — 돌기 축에 수직인 원(반지름 = 돌기 반지름 + 1.5~2, 호 = 위 → 뒤쪽 → 아래, 양 끝 0.5rad 더). 이 호를 만드는 코드는 `autotarget.py` 14번 블록(`_ringL`·`_ringR`).
7. **가닥은 팽팽한 직선, 모서리만 둥글게:** 걸린 두 곳 사이는 곧게 당긴 선이다(처지거나 구불거리면 안 됨 — "고무줄은 철사가 아니고 구부릴 수 없다"). 단 판·블록·프레임 면 안으로 들어가면 안 되므로 가닥은 그 바깥(위판 위·아랫판 아래·프레임 위아래)으로 비껴 지나고, 조절점 다각형을 Chaikin 1~2회로 모서리만 둥글린다. 납작한 띠(폭)·가는 스플라인 평탄화는 쓰지 않는다(사용자가 둥근 관을 확정).
8. **수치로 확인:** `python _bandchk.py <번호>` — 밴드 점이 부품 상자(dims) 안에 들어가는 개수. 돌기를 감는 자리는 상자가 돌기까지 포함해 몇 점 걸리는 것이 정상, 판·프레임 몸체에서 걸리면 고친다. 걸린 곳은 책 확대(밴드 끝 픽셀)를 `_proj.py` 로 평면에 되투영해 가까운 돌기를 고른다.
9. **움직임이 사용자 그림으로 확정되면 그대로 따른다:** 사용자가 화면에 그려 보여 준 모양(걸린 곳·감는 방향)이 있으면 그것이 기준이다 — 내 추측으로 다시 만들지 않는다.

- **서 있는 부품의 카메라는 세계 3D 좌표로 푼다(2026-10-13 드롭체커 27번).** `frame_fit.py`·`axes_fit.py` 는 부품 평면이 바닥에 누운 것으로 가정해 theta·phi 를 낸다 — 서 있는 아치·벽·세운 프레임이면 값이 틀려(27번: −0.76·0.69 → 실제 −0.67·0.87) 화면이 책과 하나도 안 맞는다. 방법: 모델이 만든 부품의 구멍 세계 좌표(`q.world("hole", c)["pos"]`)와 책에서 읽은 구멍 픽셀을 `pnp.fit(obj3d, img, W, H, fov)` 에 넣는다(여러 부품 구멍을 한꺼번에 — 오차가 크면(27번 26px) 부품 상대 위치가 책과 다르다는 증거: 띄운 간격을 0~160mm 로 돌려 오차 최소를 찾는다 → 27번은 판 묶음 간격 30mm, 오차 4.2px). 구한 theta·phi 는 세계 기준이라 그대로 `A.steps[N].cam` 에 쓴다. 카메라가 맞는지는 책에서 "판 구멍 행 간격 ÷ 열 간격"(정면에 가까우면 ≈1)으로 먼저 의심해 본다.
- **함께 움직이는 부품은 화살표(marks)를 지운다.** `attach` 로 놓은 부품은 marks·dir 이 붙어 화면이 기본 띄움으로 떼어 그린다 — 책이 이미 꽂아 둔 모양(예: 프레임에 꽂힌 3단블록)이면 `part.extra.pop("marks")`·`pop("dir")` 해 꽂힌 채 둔다. 묶음이 같이 떠야 하면 한쪽(예: 판+블록)을 `dir`·`hover` 로 물리고 다른 쪽(프레임+블록)은 제자리에 두어 방향 검사(design-verify.js)를 피한다.


## 5-7. 방향·자세를 모르는 새 모습일 때 — 모델을 세우고 돌려 본다 (사용자 지시 2026-10-19, 오토타깃 15번)
책 그림이 앞 번호와 전혀 다르게 보이면(기어 축이 옆으로 눕고, 막대 방향·롤이 달라 풀리지 않을 때) **책이 본체를 세우거나 뒤집어 조립하는 번호**일 가능성이 크다. 점·링 후보를 억지로 맞추지 말고 이 순서로 한다.
1. **모델을 여러 쪽으로 돌려 본다:** 개발 서버 화면에서 `br.camera({target, radius, theta, phi})` 로 앞·뒤·좌·우·아래·위에서 번갈아 본다(phi > 1.57 이면 아래에서). 책 그림과 부품 위치·막대 방향이 비슷한 시점을 찾는다. 사용자 말: "새로운 모습은 모델을 세워 보거나 좌우 여러 모습으로 돌려서 봐야 한다".
2. **롤 제한 없는 PnP 로 후보 시점을 수치로 가린다:** 책 그림에서 3D 가 확정된 점 5~6개(리벳 끝·돌기 끝·축 끝·블록 끝)를 읽고 `python _freepnp.py <이름> <번호> <점.json>`(`CAMZ=-1` 이면 카메라가 −Z 쪽인 해만, `1` 이면 +Z 쪽). 해는 `anchors/NN_free.json` 에 저장되고 `_anchor_fit.py` 의 앵커에 `"free": true` 를 주면 그 해로 fits·axes 를 만든다. 오차 10px 대에서 끝나고 **롤이 크게(40°↑) 나오면 눕힌 좌표가 틀린 것**이다.
3. **본체를 세운 좌표로 다시 푼다:** 가설(예: x축 +90° 로 세워 뒷면 −Z 가 위)대로 점의 3D 를 변환(`y′ = −z, z′ = y` + 바닥에 놓이게 올림)해 같은 점을 다시 풀면 **롤이 거의 0°** 로 풀리고 theta·phi 가 앞 번호와 비슷해진다(15번: 롤 44° → −3°, theta −0.71 phi 0.85). 이것이 가설이 맞다는 증거다.
4. **코드로 반영:** 앞 번호·합친 자리의 부품은 그대로 두고 그 번호(와 이어지는 번호)만 `poseAt` 으로 세운 자세를 준다 — `extra["poseAt"][번호] = {"p": …, "r": …}` (`autotarget.py` 15번 블록 `_RST`·`_LST`). 새 부품은 눕힌 좌표로 만들어도 되지만 띄움 방향 `extra["dir"]` 은 세운 자세 기준(위 +y)으로 바꾼다. 고무줄(`bands`)도 같은 변환을 해서 그 번호에 다시 적는다. 검사(`design-verify.js`)는 poseAt 번호의 방향 검사를 건너뛴다.
5. **증명 그림:** `overlay_check.py` 는 poseAt 자세로 상자를 그린다(15번 NN_3 — 흰 프레임 상자가 책 흰 프레임 위에 거의 그대로 얹힘). 띄운 거리는 책 화살표 길이를 풀이 카메라로 투영해 정한다(15번 52mm).
6. 보고할 때 "책이 본체를 세워 조립한다 / 어느 쪽이 위인지 / 어떻게 알았는지(롤이 줄어든 수치)"를 읽기 표 판단과정에 적는다.
