# 큐보 부품결합규칙 (= 규칙 마스터) — 교재검사와 조립검사로 나눈 한 파일 (규칙 번호 A1~K)

**이 파일이 조립도 규칙 문장의 원본이다.** `SKILL.md`·`05_조립.md`·`CLAUDE.md`·`문서지도.md`·안내서는 이 파일을 가리키고, 새 규칙은 여기에만 적는다. 규칙을 바꿀 때는 이 파일의 해당 문장을 덮어쓰고 옛 문장은 지운다(바뀐 이유는 커밋 메시지에만 남긴다). 규칙 번호는 주제 글자+번호이고, 규칙 앞 표시는 `[도구]` = 도구가 막는다 · `[문장]` = 문장만 있다(도구로 올릴 후보).

## ★ 시작 전에 가장 먼저 읽는다 (사용자 지시 2026-11-04)

**큐보 규칙 정리·양팔저울(큐보 1권, `balance`) 점검을 이어받는 세션은 `큐보/인수인계.md`(큐보 작업 인수인계는 이 파일 하나뿐)를 맨 먼저 읽는다.** 어디까지 했고, 어디부터 이어가야 하는지가 거기에 있다(조립도 내용은 `큐보/조립도/1권/balance/진행기록.md`). 작업을 끝내거나 멈출 때는 `handoff.py` 로 그 블록을 덮어쓴다(메모리가 아니라 저장소에 남긴다 — 다른 PC·새 세션이 읽어야 한다).

## ★ 1번 규칙 — 절대 어길 수 없다 (사용자 지시 2026-11-04)

**가장 큰 문제점은 말을 안 듣고 규칙을 안 지키는 Claude 자신이다(사용자 지적 2026-11-05).** 사용자의 지시는 좁게 줄여 읽지 말고 가장 넓은 뜻으로 끝까지 적용한다(예: "규칙에 반할 만한 것은 다 삭제" = 안내점뿐 아니라 손 좌표·`p=` 까지 전부). 도구가 통과했다고 규칙을 지킨 것이 아니다 — 규칙을 항목별로 직접 대조한다. 못 고치고 남긴 것·규칙에 어긋나는 채로 둔 것은 보고에서 먼저, 숨기지 않고 말한다.

**큐보 로봇을 조립할 때는 이 파일의 K절(큐보 부품 결합규칙)에 따른다.** 한 가지 규칙으로 모든 차시·번호·조립도를 통일한다. 번호마다 다른 기준을 세우지 않고, 손 좌표(`p=`·`X.p=`)로 규칙을 덮지 않으며, 규칙에 어긋나면 번호를 고치지 말고 도구(`asmlib`·`cubo_joint_check.py`)를 고쳐 전체에 적용한다. 이 규칙이 아래 모든 규칙보다 앞선다. K0 "물리법칙이 가장 우선이다"가 모든 결합 판단의 바탕이다(결합 사실은 K절에만 적고 다른 곳에 되풀이하지 않는다).

## 검사 지도 — 교재검사 / 조립검사 (사용자 지시 2026-11-06: 한 파일 안에서 둘로 나눈다)

이 파일은 **공통편 → 제1부 교재검사 → 제2부 조립검사** 순서다. 검사를 돌리거나 위반을 보고할 때 어느 쪽 검사인지 먼저 밝히고, 한 보고에 둘을 섞지 않는다.

| 규칙 | 제1부: A(순서·게이트) · D(홀라인·격자) · E(방향·카메라) · F(대칭) · H(6방향·관찰·증거) · G7·G8읽기·G9·G10읽기·G18 | 제2부: G(부품별 규칙, G7·G8읽기·G9·G10읽기·G18 제외) · K(큐보 부품 결합규칙 K0~K4) |
| 도구 | `rulecheck.py`(격자 F·카메라 C·증거 E·읽기표 R·증명 P) · `verify_step.py` · `record_check.py` · `dbimgcheck.py` · `number_start.py` 의 게이트(부품 합계·창고·앞 번호 그림) · `stepchecks.py` 의 읽기 표·카메라 항목 | `cubo_joint_check.py`(K1 규칙 1~10·13~16, 11·12 는 규칙 10 이 방향 카드로) · `joincheck.py`(리벳 틈·볼트 묻힘·돌기 충돌) · `matecheck.py`(화살표 진단) · `tiltjoin.py`(기울어진 결합) · 빌드의 몸통 겹침·바닥 검사 |

- `verify_step.py` 의 '돌기↔구멍' 줄은 조립 쪽 내용이지만 교재 대조 흐름 안에서 같이 돈다. 결합 위반 판정은 조립검사 도구가 기준이다.
- 번호를 끝낼 때는 두 검사를 각각 돌려 각각 보고한다(H8·J4 형식, 한 것/⚠/못 한 것).
- **"조립점검"이라고 하면 조립검사만 한다 — 사전점검(교재검사) 도구와 책 비교는 하지 않는다(0번 체크리스트 나).**

# 공통편 — 작업 순서·질문·도구·DB·화면 (교재검사·조립검사 모두에 적용)

## 00. 조립도를 시작할 때 (조립도당 한 번 — 번호 조립 전에 03·04 를 모두 끝낸다)

- **새 차시의 기본 환경은 `new_assembly.py` 가 처음부터 갖춘다(사용자 지시 2026-11-09):** `Asm(..., guideMode="mates")`(G26) · `_rules.json` 의 `parts_sum`·`mate_marks`·`strict`·`orient_check`·`placecheck`·`img_db`·`rulecheck` 전부 켬 · 카메라 보는 중심은 뷰어가 번호를 열 때마다 자동으로 보이는 부품 전체의 가운데로 맞춘다(`fitCenter`, E11 ①, 📷 저장 시점이 있으면 그것이 우선). 검사·환경은 내가 번호마다 손으로 챙기는 것이 아니라 기본으로 켜져 자동으로 도는 것이어야 하고, 빠진 항목이 보이면 번호가 아니라 `new_assembly.py`·도구를 고친다(C8).
조립도를 시작하면 **03 부품 정리와 04 창고 정리를 모든 번호에 대해 먼저 다 하고, 그다음에 1번부터 조립한다**(A1~A3). 순서는 01 번호 등록 → 02 이미지 자르기 → **03 부품 정리 → 04 창고 정리 → 05 번호별 조립**이며 앞 과정이 끝나기 전에는 05 로 넘어가지 않는다. **03·04 는 "1차"다 — 책을 번호 순서대로 대략 훑어 모든 번호의 사용 부품과 작업 창고를 먼저 적는 것이고 완벽할 필요가 없다. 모든 번호가 적혀 합계 = LIST 가 되면 1차 완료(번호판 위 배지, A2a·A3a)이고, 상세·정정은 05 번호 조립 중에 한다(B5).**

- **03 부품 정리(1차 — 모든 번호 한 번에, 대략 훑어서):** 책 1번부터 끝 번호까지 순서대로 읽어 번호마다 새로 쓰는 부품·개수를 표(`USED`)에 적고(2개 만들기 번호는 2배), 부품별 합계를 교재 LIST 와 맞춘다. 안 맞으면 숫자를 고치지 말고 책을 다시 뒤져 어느 번호를 잘못 읽었는지 찾는다. **합계가 다 맞을 때까지 04 로 넘어가지 않는다.** 조립 중 부품이 틀린 것을 발견하면 이 표를 고치고 이어간다.
- **04 창고 정리(1차 — 모든 번호 한 번에, 대략 훑어서):** 같은 순서로 책을 읽으며 번호마다 창고(slot)와 `history`(창고가 바뀌는 번호), 숨길 앞 번호(`hideMade`)를 정한다. 연달아 이어지면 같은 창고, 새 세트가 시작되면 새 창고(원점), "N + M" 합치기는 작은 번호 창고로.
- 둘 다 끝나면 읽기 표 칸이 생긴 번호부터 아래 "0. 번호 하나 체크리스트"로 1번부터 조립한다. 조립 도중 부품·창고가 어긋난 것을 발견하면 조립을 멈추지 않고(B5) 03·04 표를 고친 뒤 이어간다.

## 0. 번호 하나 체크리스트 (1쪽 — 번호마다 이것을 먼저 읽는다. 상세는 괄호의 규칙 번호)

**"조립 시작" = 가. 사전점검작업 → 나. 조립점검작업 → 다. 조립도 그리고 저장, 이 순서로 번호마다 한다(사용자 지시 2026-11-06). 세 가지는 겹치지 않고 각각 따로 말하고 따로 보고한다.**
- **"사전점검"·"교재점검" = 가만.** 책을 읽고 관찰·분석한 것이 맞는지 본다.
- **"조립점검"·"조립검사" = 나만.** 부품을 놓으면서 놓는 즉시 조립 규칙(K·G절)을 어기는지 규칙·도구로 점검한다. 책을 읽거나 책과 비교하지 않는다. 이미 그려진 조립도를 점검만 할 때는 나의 검사 도구를 번호 범위 전체에 돌린다.
- **"조립도 그리기"·"그리고 저장" = 다만.** 점검을 마친 조립을 저장(`--write`)하고 책과 맞춰 마무리한다.
- 말이 애매하면 한 줄로 어느 쪽인지 묻는다.

**순서는 가 → 나 → 다 이지만, 가와 다(책 비교)는 나(놓기)와 중간중간 오간다: 나에서 놓은 모델을 가-4 로 책과 비교하고, 다르면 나로 돌아가 다시 놓는다. 각 칸 끝의 [→ …]가 그때 볼 곳이다.** 각 단계가 끝나야 다음으로 가고, 단계를 건너뛰지 않으며, 막혀도 멈추지 않고 그 단계 안에서 B5(관찰 → 자기에게 묻기 → 다시 관찰, 맞으면 진행)로 푼다. 단계마다 만든 그림은 만들자마자 DB 에 올리고 화면 🖼 에서 확인한다(I1·B8).

### 가. 사전점검작업 — 교재검사 (책을 읽고 관찰·분석이 맞는가)
**★ 사전작업의 목적은 사전작업을 멋지게 하는 것이 아니라 조립 위치를 바르게 찾는 것이다(사용자 지시 2026-11-07). 격자·카메라·증거는 위치를 정하는 데 필요한 만큼만 하고, 위치가 책에서 바로 읽히면 계산을 더 늘리지 않는다. 격자 오차를 줄이거나 검사 항목을 통과시키는 것이 목표가 되면 멈추고, 지금 정하려는 위치가 무엇인지부터 다시 적는다.**

## B. 질문·자동화 (멈추지 않는다)

- **B1 [문장] 질문에는 답만 한다 — 화면·값·코드를 바꾸지 않고, 사용자가 좋다고 한 단계·카메라는 건드리지 않는다.** 단 "~했어?"처럼 한 일을 확인하는 물음은 사실대로(안 한 것은 안 했다고) 말하고 곧바로 그것을 한다 — 변명·재질문으로 멈추지 않는다. 작업 중인 번호만 본다: 뒤 번호 그림은 읽기 보조로만 보고 그 번호를 만들거나 요청 밖의 것을 손대지 않는다. 한 줄 지시는 그 한 가지만 바꾸고, 말이 두 가지로 읽히면(번호 작업 중이 아닐 때만) 구체적인 선택지로 한 번만 되묻는다 — 번호 작업 중에는 묻지 않고 더 넓은 쪽으로 읽어 진행하며 읽은 방식을 보고에 적는다(B4).
- **B2 [문장] 사용자가 틀렸다고 하거나 고치라고 하면 설득·변명 전에 그 결합 부분을 책에서 다시 관찰하고 숫자로 확인한 뒤 고친다. 한 줄로 받아 그대로 하고 범위를 넓히지 않는다.**
- **B3 [문장] 사용자가 지정한 것(말씀·❄ 모습 기록·📷 카메라·✓)이 코드와 내 계산보다 무조건 우선한다.** 수정 지시가 ✓ 잠금에 막히면 코드 수정은 되돌리지 말고 그 번호의 ✓ 를 스스로 풀고 마지막 보고에 적는다(C2, 사용자 2026-11-07).
- **B4 [문장] 번호 도중에는 묻지 않는다. 읽을 수 있는 것을 먼저 다 읽고(이번·앞·뒤 번호·완성 사진·모델 6방향·숫자, 자기에게 6질문) 그래도 구멍·방향·개수를 정할 정보가 없으면 책에 보이는 그대로 놓고 읽기 표 판단과정에 "⚠ 근거가 약함"으로 적은 뒤 계속한다. 모아 둔 ⚠ 는 끝 번호(없으면 완성)를 끝낸 마지막 보고에서 한꺼번에 묻는다.**
- **B5 [문장] 문제가 생기면 멈추지 않는다. 먼저 규칙을 순서대로 지켰는지 확인한다 — 증거는 이 번호의 이미지 작업이 DB 에 다 올라가 화면(🖼 배지·그림 목록)에 보이는 것이다.** 그림 목록(교재 원본 · 방향선 · 격자 · 모서리 확대 눈금 · `hf` 홀라인 확인 · 링 읽기 · 관찰 · 증명)에 빠진 그림이 있으면 그 그림을 만드는 단계를 건너뛴 것이니 그 단계부터 한다(대부분의 문제는 순서를 건너뛴 데서 나왔다). 그다음에도 풀리지 않으면 무엇이 문제인지 자기에게 묻고 해답을 찾을 때까지 책을 뒤진다. 횟수 제한은 없다. 문제 = 도구·검사가 막힘 · 책과 모델이 안 맞음 · 오차가 큼 · 방향·개수를 모름. 자기에게 묻는 순서: ① 지금 어떤 부품이 어디에 결합하나 ② 그 결합 부분을 책 어느 번호(이번·앞·뒤·완성 사진)에서 보았나 ③ 모델의 같은 부분을 같은 시점·확대로 나란히 보았나 ④ 다르면 정확히 어디가 다른가(개수·칸·방향·높이를 숫자로) ⑤ 원인은(구멍 축 방향·카메라·칸 한 칸 차이·앞 번호 위치·뒤집힘) ⑥ 고친 뒤 같은 곳을 6방향으로 다시 보았나. 책은 4~6배로 확대해 바꿔 가며 뒤지고, 모델은 앞·뒤·좌·우·위·아래로 돌려 본다.
- **B6 [문장] 막히면 B9(확인 → 원인 → 테스트 → 규칙 수정 → 테스트 적용)가 먼저다(사용자 2026-11-07). B9 를 거치고 책을 다 뒤져도 정할 수 없는 사실이 남을 때에만: 가설을 만들지 않고 책에 보이는 그대로 놓고(F4) 읽기 표 판단과정에 "⚠ 근거가 약함: 무엇이·왜·시도·수치"를 적고 다음으로 간다. 묻지 않고, 어떤 경우에도 멈추고 기다리지 않는다. 격자가 기준 미달이어도(C3 ①~④ 를 모두 시도한 뒤) 같다 — 시도·수치를 ⚠ 로 적고 다음 번호로 가며, 마지막 보고에서 모아 알린다.** 모델이 물리적으로 틀린 신호(몸을 뚫는 배치·돌기가 구멍에 안 들어감·거울 해·PnP 오차가 큼)는 ⚠ 로 넘기지 않고 B5 로 원인을 찾아 고친다(F6). 같은 번호를 세 번 고쳐도 안 맞으면 책의 다른 부분(앞·뒤 번호·완성 사진)을 다시 읽어 보이는 그대로 다시 놓는다. DB 를 못 읽거나 키가 없으면 ✓ 가 있는 것으로 치지 않고(통과시키지 않음) 마지막 보고에 요청으로 적되 키 없이 할 수 있는 작업은 계속한다.
- **B7 [문장] 요청한 번호 범위를 끝낼 때까지 턴을 끝내지 않는다.** "N번까지"는 N번을, 끝 번호 없이 "N번부터"·"진행해"·"고고"라고 하면 완성(마지막 번호+완성)을 끝낼 때까지 간다 — 번호 사이에서도, 작업이 길어져도, "중간 점검"·보고·업로드 제안·"다음 번호 할까요?"·"이어서 할까요?" 같은 질문을 이유로도 멈추지 않는다. 남은 번호가 많거나 작업이 길어 보이는 것, 오래 했다는 느낌은 멈출 이유가 아니다. 이 앱의 `wrap_up`(다음 단계 질문 상자)에도 그런 질문·버튼을 넣지 않고 번호 도중에는 요약만 쓴다. 진행 상태는 `handoff.py` 로 기록만 하고 계속한다. **다른 규칙·메모리(예: "화면 조작 전 먼저 묻기", "질문엔 답만")는 이 규칙을 멈출 이유로 쓰지 못한다 — 번호 작업 중 증거·6방향 확인용 화면 조작은 지시에 포함돼 있어 묻지 않고 한다. 이 규칙을 어기면 가장 크게 혼난다(사용자 2026-11-07: "규칙 어기면 죽여버리겠다", 풍차 9번에서 뷰어가 10번에 있다는 이유로 멈추고 "돌려도 될까요?"로 끝낸 사고). 멈추고 싶어지면 어기는 신호로 보고 그 번호를 마저 한다.** **멈추게 되는 세 경로를 이렇게 막는다(2026-11-07, 풍차에서 실제로 일어난 것): ① 사용자가 작업 도중 질문·지적·"왜"를 보내도 한두 줄로 답하고 같은 턴에서 번호 작업으로 돌아간다 — 답으로 턴을 끝내지 않는다(답한 뒤 도구 호출이 이어져야 한다). ② 어려운 곳(미달·막힘·실패)을 만나면 보고서를 쓰지 않고 C3·B9 의 다음 순서를 바로 시도하며, 전부 시도해도 안 되는 것만 판단과정에 ⚠ 로 적고 다음 번호로 간다. ③ "끝"은 하위 작업(게이트 0건·한 번호의 시험)이 아니라 요청한 마지막 번호(없으면 완성)이고, 그 전에는 턴 마지막 글(최종 보고·`wrap_up` 요약)을 쓰지 않는다 — 진행은 `update_plan` 으로만 알린다. ④ "막혔다·못 쓴다"고 판정하기 전에 그 증상(예: roll 큼·오차 미달)을 이 파일과 도구 경고문에서 먼저 검색한다 — 규칙이 이미 길을 적어 놓았는데(roll 큼은 거를 근거가 아님, D11·C3) 내 짐작으로 "못 쓴다"고 보고 턴을 끝낸 것이 풍차 24번(2026-11-07) 사고다. 사용자가 "왜 멈췄냐"고 물으면 이유를 한두 줄로 답하고 바로 도구 호출로 번호 작업에 돌아간다.** **⑤ 도구가 없거나 오차가 기준에 못 미쳐도(2026-11-09 3륜바이크 3번: 카메라 4.5px>2px, silfit 도구 없음) 멈추는 이유가 못 된다 — 값·한계를 읽기 표 판단과정에 ⚠ 로 적고 다음 번호로 간다. 장치: 완성 지시를 받으면 첫 줄에 `python finish_guard.py on <이름>` 을 켠다 — Stop 훅(`finish_guard.py`)이 rulecheck ❌ 번호가 남은 동안 턴 종료를 막고(종료 코드 2), ❌ 가 0개면 스스로 끈다. 질문에 답만 할 때는 `finish_guard.py off`, 4번 연속 ❌ 개수가 안 줄면 막지 않고 막힌 이유를 보고한다.**
  - **멈춰도 되는 것은 ① 요청한 마지막 번호(끝 번호가 없으면 완성)를 끝냈을 때 ② 사용 한도가 모자랄 때뿐이다.** ② 는 "N번까지"를 못 채워도 번호 마무리(증거·DB 업로드·`handoff.py`)까지 끝낸 마지막 번호에서 멈춘다(30번까지 요청했어도 28번까지 했으면 28번에서 마무리). 만들다 만 번호(코드만 있고 증거·DB 가 없는 번호)를 남기지 않는다.
  - **10번호마다 다시 시작:** 번호 10개를 끝낼 때마다(번호 마무리까지) 같은 대화 안에서 처음 시작하듯 리셋한다 — 규칙 파일을 처음부터 다시 읽고, `number_start.py` 를 다시 돌리고, 파일(읽기 표·증거·`fits`·진행기록)에 쌓인 앞 번호 결과를 가져와(H16) 다음 번호를 계속한다. 멈춤이 아니고 사용자에게 묻지도 않는다. 그 번호에서 알게 된 것은 리셋 전에 읽기 표·진행기록에 적어 둔다.
  - **번호를 끝내면** 사용자 ✓ 를 기다리지 않고 다음 번호로 가며, 번호마다 책 그림(`refs/<이름>/NN.jpg`)과 비교 화면(`refs/<이름>/cmp/NN.png`)을 `SendUserFile`(status proactive)로 보내 "이상하면 말씀해 주세요, 답 없으면 계속"이라고 알린다. 이상하다고 하면 그 번호만 고친다. 규칙 점검 ❌ 는 묻지 말고 근거로 판단해 고친다.
- **B8 [도구:number_start `img_set_from`] 번호 도중에는 사용자에게 질문하며 턴을 끝내지 않는다 — 막히면 B5(책을 4~6배 확대해 다시 읽기, 빠진 그림의 단계부터)로 풀고, 그래도 정할 수 없는 사실은 B6대로 ⚠ 로 적고 계속 만든다. 질문은 마지막 보고에서 모아서 한다.** 번호마다 이미지 작업이 순서대로 됐다는 증거는 그림 목록이다: 0 교재 원본 · 1 방향선 · 2 축선 · 3 격자 · 4 확대 눈금(`crop_ticks`) · 5 홀라인 확인(`hf`) · 11~ 관찰 3장 이상. `<이름>_rules.json` 의 `img_set_from: N` 을 켠 조립도는 N 번부터, 앞 번호의 이 목록이 다 있어야 `number_start` 가 다음 번호를 시작하게 하고 빠진 그림을 알려 준다(DB 에 올렸는지는 `img_db`).
- **B9 [문장] 문제가 생기면 한 번에 하나씩 이 순서로 푼다(사용자 지시 2026-11-06): ① 확인(눈·도구·DB 로 실제 상태를 읽는다, 추정으로 말하지 않는다) → ② 원인 파악(왜 그렇게 나오는가, 어느 규칙이 비었거나 어겨졌는가) → ③ 테스트(같은 입력으로 다시 돌려 재현하고, 규칙이 비었거나 어겨졌음을 확인한다) → ④ 규칙 수정(비어 있으면 원본 한 곳에 규칙을 쓴다, 사실은 손으로 따로 적지 않고 원본 자리(DB·도구)에 둔다) → ⑤ 테스트 적용(고친 규칙으로 다시 돌려 통과를 확인하고 해결한다).** **문제가 없으면 이 과정 없이 그냥 진행하고, 사전작업(가→나→다)을 번호마다 하면서 문제가 생길 때마다 이 과정을 반복해 규칙을 다듬어 나간다(사용자 2026-11-07, 가-8).** 원인 확인 전에 땜질(목록에 이름 더하기·사본 만들기)을 하지 않고, 여러 문제를 한꺼번에 건드리지 않는다. 규칙 쪽 수정은 묻지 않고 하고, DB·푸시처럼 밖에 나가는 일만 허락을 받는다.

## C. 검증 우회 금지·도구 규칙

- **C1 [도구:build] `build.py` 옵션은 `--write` 하나뿐이다. 검사가 경고하면 끄지 말고 보고한다. 확인의 근거는 사용자의 ✓(DB `ivs_assembly_status`) 또는 책↔화면 비교 증거(`record_check`)뿐이며, 목록에 번호를 적어 막힘을 풀지 않는다. ✓(완료) 버튼은 절대 누르지 않는다.**
- **C2 [도구:build] ✓ 완료 한 번호의 내용(부품 위치·자세·설명)은 바꿀 수 없다(빌드가 막는다). 조립도 전체가 ✓ 완료면 제목 오른쪽에 "✔ 완료"가 뜬다(조립 보기가 DB 로 켠다). 고쳐야 하는데 이 잠금에 막히면 ✓ 를 스스로 풀지 말고 사용자에게 "완료 표시를 풀고 수정해도 되나요?"라고 먼저 묻는다 — 사용자가 풀어도 된다고 하면 풀고 고친다(사용자 지시 2026-11-08, 앞의 "막힌 건 스스로 풀어도 됨"은 이 문장으로 바꾼다). 풀었으면 어느 번호를 왜 풀었는지 마지막 보고에 적고, 고친 뒤 다시 ✓ 를 거는 것은 사용자에게 묻는다. **규칙 위반(화면의 빨간 표시)이 한 건이라도 있는 번호는 ✓ 완료로 잠그지 않는다 — 뷰어가 ✓ 를 막고, 조립도 전체를 잠그기 전에 번호별 위반이 0인지 먼저 본다(2026-11-08 양팔저울·토끼를 위반 34건·3건을 두고 잠갔다가 푼 사고).** 새 ✓ 를 누르는 것(C1)과 `gate_watch --accept` 는 사용자가 시킬 때만 한다.**
- **C3 [도구:rulecheck+number_start, 순서는 문장] 격자 기준(구멍 ≥40%·평균 ≤2px·최대 ≤4.5px) 미달이면 기준을 낮추는 옵션·손으로 만든 격자·추정 카메라로 지나가지 않는다.** **푸는 순서의 유일한 원본(멈추지 않고 전부 시도, 눈으로 "안 되겠다"고 건너뛰지 않는다):** ① `crop_ticks` 모서리 → `holefit`(기본→어두운판→DoG) ② 미달이면 `holesearch`(모서리 자동 탐색 — 어두운 판이면 ①보다 먼저) ③ 앞 번호에 같은 판 격자가 있으면 먼저 이어 쓰고(H16) `plate_match` ④ `infer_grid`(링·판·거울 앵커) ⑤ 프레임·L자는 `frame_fit`, 한 줄 부품은 `line_fit`, 판이 없는 번호는 `mkfit3d` ⑥ 몸체에 가려 ①~⑤ 가 다 안 풀리면 `05_조립.md` 0-3(선 긋기)→0-4(주황 리벳 별자리). 각 단계의 기준·검증은 D12, 명령 사용법은 `05_조립.md` 0-1~0-4. ①~⑥ 을 모두 시도해도 기준 미달이면 멈추지 않고 시도·수치를 읽기 표 판단과정에 ⚠ 로 적고 다음 번호로 간다(마지막 보고에서 모아 알린다). 유추 격자는 `rulecheck` 가 ⚠(사용자 확인 권장, 진행은 막지 않음)로 보고한다. **사다리는 번호마다 한 번만 끝까지 돌린다 — 조립이 책과 맞는 것이 6방향·감시 칩으로 확인됐으면 격자 ⚠ 를 지우려고 더 시도하지 않는다(사용자 지시 2026-11-10, 축구로봇 19번).** 예외는 사용자 말씀을 그대로 적은 `<이름>_approvals.json` 뿐이고 Claude 는 이 파일을 쓰지 않는다.
- **C0 [도구:ladder-gate 훅] invent_school 안의 모든 수정(Edit·Write·Bash 쓰기)을 하기 전에 같은 문제를 푼 조립도·도구를 먼저 찾아 `ladder.py` 로 기록한다(사용자 지시 2026-11-08).** 책 그림이 기울어 보이는 것 같은 문제는 새 뷰어 기능이 아니라 `xform`·자세 변환 등 이미 쓰는 방식(9개 조립도)을 먼저 따른다. 기록 없이 고치려 하면 훅이 막는다. 책 그림에서 부품 줄이 비스듬히 누워 있으면(풍차 20번) 카메라를 돌리지 않고 `to_side` 의 옆자리 회전 Rs 로 묶음을 돌려 놓는다 — Rs 는 놓은 자세→화면 변환 D 로 `D.T @ R_세계 @ D` 를 쓴다(windmill.py `_Rs20` 참고, 검산은 화면 serialize 의 축 방향).
- **C4 [문장] 도구가 파일을 덮어쓴다: `frame_fit`·`axes_fit`·`mkfit3d` 는 `<번호>_axes.json`·`fits/` 를 말없이 새로 쓴다.** 부품이 달라 푼 카메라가 판 카메라(오차 ≤2px)와 크게 다르면(롤 40° 이상) 그 값으로 덮지 말고 판 기준 값으로 되돌린다(`axes_fit` + `rotate_to`). 쓰기 전에 기존 값 백업.
- **C5 [도구:build] 빌드 뒤 끝줄의 ❌·"막힌 항목"·"기존 항목을 바꿨다"를 읽는다. 읽기 표가 비거나 `부품` 칸이 "이름 개수" 형식(괄호 설명 없음)이 아니면 조용히 저장되지 않는다.** 스크립트 끝(`A.save_links()` 앞)에 `import stepchecks; stepchecks.apply(A, "<이름>")` 가 있어야 `--write` 가 된다. `<이름>_rules.json` 의 플래그가 점검을 켠다: `strict`(화면 확대·칸 수 대조·카메라 대조·카메라 출처 guess 아님도 `--write` 를 막는다 — 안 했다고 보고하지 않고 실제로 해서 채운다) · `orient_check`(읽기 표 `부품방향` 이 20자 미만이면 막음) · `placecheck`(그룹으로 옮겨 붙이는 부품의 상대 자세가 옮기기 전후 1mm 이상 다르면 막음 — 관절처럼 돌아가는 부품만 `nonRigid`) · `parts_sum`(A2) · `img_db`(I1) · `rulecheck`(켜면 번호 점검 ❌ 가 막음, 새 조립도는 켠다) · `mate_marks`(안내점 맞물림 없는 부품을 막음, 끄면 ⚠ 참고). 읽기 표(`<이름>_read.json`)에는 부품이 있는 번호마다 `면`(카메라가 보는 면)·`링`(센 칸·줄, 격자 점이 구멍 위인지 확인한 근거)·`부품`·`부품방향` 을 적는다.
- **C6 [문장] 코드 쓰는 법: 결합은 `attach`/`recv` 를 `p=` 없이(자동 계산), `p=` 는 자동 계산이 안 될 때만 이유 주석과 함께. 앞 번호 부품을 옮길 때는 `move_made`(`move_group` 금지), `hover` 는 0 이 아니라 0.01(뒤집기 등).** 틈·겹침 판정은 회전한 상자(`obb.py`). 조립도 데이터는 `<이름>_asm.json → build --write → public/design-assemblies.js` 로만 만들고 손으로 고치지 않는다. **축 양 끝에 부시·바퀴를 끼울 때도 `p=` 손값을 쓰지 않는다(사용자 지시 2026-11-09, 3륜바이크 23번 부시를 ±17.75·±29.95 손값으로 넣어 "자기 구멍 축 위에 없음" 위반이 났다): `recv("부시", R, {"h1": (축, "p1")}, dir=<끼우는 쪽 방향>)` 처럼 구멍 id 를 주고 `dir` 로 끝을 고르면 `asmlib.recv` 가 그 끝(tip/뿌리)에 자동으로 놓는다 — 안내점(marks)과 같은 규칙이다. 자동 계산이 안 되는 것 같으면 손값을 넣지 말고 먼저 도구(`recv`)가 그 경우를 지원하는지 읽고, 없으면 도구를 고친 뒤 그 문장을 여기에 덧붙인다(새 위반 유형을 알게 되면 규칙·도구를 같이 고쳐 적용한다).**
- **C7 [문장] 규칙을 바꾸는 법: 흩어 적지 않고 원본 한 곳을 덮어쓴다(옛 설명은 지운다). 보완할 때는 문장 끝에 덧붙이지 않고, 그 규칙의 문장 전체를 다시 써서 한 덩어리로 만든다(덧붙인 문장·사건 날짜가 쌓여 규칙이 길어지는 것을 막는다). 같은 실수가 두 번 나오면 문장이 아니라 `stepchecks.py` 검사로 올린다. 규칙이 새로 생기면 문서와 검사(`rulecheck`·`stepchecks`·`number_start`)를 같이 고치고 보고한다. 검사·규칙을 바꾸면 이미 만든 조립도 전부에 돌려 결과를 확인한다. 쓰지 않는 도구·문서는 같은 작업에서 지운다.** `build`·`stepchecks`·`userdone` 검사를 풀거나 고치는 일은 사용자가 지시했을 때만 한다. 규칙·기능이 바뀌면 항목마다 판단한다: 새로 추가된 기능은 남기고, 방식이 바뀐 것은 옛 문장을 지우고 새 문장으로 덮어쓴다(정리 과정·충돌 목록·출처·"옛 문장 보관" 파일·날짜 덧붙임을 문서에 쌓지 않고, 바뀐 이유는 커밋 메시지에만 남긴다). 고치기 전에 `05_조립.md`·`SKILL.md`·`CLAUDE.md` 에 같은 말이 있는지 찾아 한꺼번에 덮어쓰고, 마스터에 없는 내용(플래그·형식·도구 사용법)은 지우기 전에 마스터로 옮긴다. 안내서 절 제목은 `get_assembly_guide` 코드(CATS·`isCore`: `★`·`작업 흐름`·`제1편`·`단계 N`)가 쓰니 바꾸면 깨지는지 본다. 규칙은 기억 파일이 아니라 저장소(이 파일)에만 둔다 — 어떤 Claude 가 와도 같은 규칙으로 일해야 한다.
- **C8 [문장] 어기게 되는 규칙은 도구가 대신 하거나 어기면 막히게 한다. 둘 다 안 되는 규칙은 지운다("지키기 쉬워야 규칙이다").**

## I. DB 올리기·푸시·업로드

- **I1 [문장] 그림(책 이미지·격자·방향선·확대 눈금·hf·관찰·증명)은 만들자마자 DB(`ivs_assembly_refs`)에 올린다 — 번호를 끝내고 올리지 않는다. DB 에 올리지 않은 채 멈추거나 보고하거나 다음 일로 넘어가는 일은 없다: 그림을 만들었으면 그 자리에서 올리고, 올리지 못한 그림이 남은 채로 턴을 끝내지 않는다. "이미지 작업이 규칙 순서대로 끝났다"는 증거는 DB·화면의 그림 목록(🖼 배지)이다.** 올린 뒤 화면을 새로 불러와 🖼 배지 장수가 올린 장수와 같은지 확인한다. 틀린 배정이 그려진 실패 시도 그림은 올리지 않는다(유추한 번호의 근거 그림은 idx 3~ 로 설명과 함께). `ivs_assembly_refs` 에는 `created_at` 이 없고(`get_rows` 에 `order_by` 필수), 그림 DB 삭제는 사용자 확인 뒤에만 한다. MCP 만 쓰는 Claude 는 `get_step_refs(assemblyId, 번호)` 로 그 번호에 올라간 그림을 연다(번호 0 = 교재 맨 앞 완성품 사진, 99 = 마지막 "완성" 그림). 이미 올라간 그림이 있으면 다시 만들지 않는다. **[도구] `<이름>_rules.json` 에 `"img_db": true` 를 켠 조립도(새 조립도는 반드시 켠다)는 `number_start` 가 번호별 체크리스트에 "그림 DB 업로드(🖼)" 를 보여 주고 앞 번호에 안 올린 그림이 있으면 막으며, `rulecheck` 가 번호별 "그림DB" 항목으로 안 올린 그림이 있으면 ❌ 로 막는다(점검 도구가 실패해도 ⚠ 로 표시한다 — 조용히 넘기지 않는다, 2026-11-07).**
- **I2 [문장] 푸시는 사용자가 "업로드"라고 말할 때만, 모아서 한 번 한다(요청하지 않은 업로드·푸시를 미리 하지 않는다 — 푸시마다 Vercel 빌드).** 절차: ⓪ **"업로드"라는 말을 들으면 커밋 전에 먼저 `python handoff.py <작업 이름> --아이디 <계정> --어디까지 "…" --다음 "…"` 로 `큐보/인수인계.md` 를 지금 최종 상태로 덮어쓴다(사용자 지시 2026-11-06 — 업로드 때마다 인수인계가 최신이어야 한다. 작업 이름·어디까지를 정할 수 없으면 직전 진행기록을 보고 쓰고, 애매하면 한 줄만 묻는다)** ① `git add` 로 이번 작업 파일과 `큐보/인수인계.md` 를 하나씩 지정(다른 작업의 미추적 파일·`.bak`·`_spec*` 제외) ② `git commit`(메시지 끝에 Co-Authored-By 줄) ③ `node --check app/lib/cubo-assembly-tools.js` ④ **`git push newrepo main`**(원격 이름은 origin 이 아니라 newrepo).
- **I3 [문장] 사용자가 새로 바로잡으면 이 파일(이 파일)의 해당 규칙을 덮어쓴다 — 기억 파일에만 적지 않는다. 새 PC·새 세션은 `session_start.py` → `git pull newrepo main` → `setup_new_pc.py` → 이 파일 처음부터 읽기.**
- **I4 [문장] 여러 PC·여러 계정에서 이어서 작업한다 — 저장소에 올린 것만 모든 PC 에 전달되고, 기억 파일·`.env.local`·`.claude/` 밖의 로컬 파일은 전달되지 않는다.** 그래서 ① 세션을 시작할 때 `session_start.py --아이디 <내 계정>` 으로 최신을 받고 "마지막 작업은 어느 PC·어느 아이디가 어디까지, 지금 이 PC·이 아이디가 이어받아 시작"을 사용자에게 정리해 보고한 뒤 `handoff.py <작업 이름> --아이디 <내 계정> --시작` 으로 이어받음을 기록하고(작업트리가 더러우면 받지 않으니 그 사실을 보고) ② 이어받을 상태는 `python handoff.py <작업 이름> --아이디 <작업한 계정> --어디까지 "…" --다음 "…"` 로 `큐보/인수인계.md` 의 마지막 작업 블록(파일 하나뿐)에 적는다 — 날짜·PC 이름·아이디·커밋이 같이 기록되고, 다음 번에는 이 블록을 덮어쓴다(쌓지 않는다, 이력은 git). **사용자가 "업로드"라고 하면 푸시 전에 반드시 한 번 더 덮어써 같은 커밋에 넣는다(I2 ⓪).** `session_start.py` 가 이 블록을 조립도별로 보여 준다(A12). 임시 파일(`_spec*.json`·`*.bak*`·`*_tmp.py`)은 올리지 않는다. DB 에 올린 그림·✓·❄·📷 는 PC 와 상관없이 같이 보인다.
- **I6 [문장] 표시되는 값(구멍 번호 등)을 고치라는 지시는 그 값이 보이는 모든 층(라이브 렌더·DB 에 저장된 사본)을 함께 고친다.** DB·공유 함수를 추천하거나 바꾼 뒤에는 익명 키로 막히는지 직접 시험한다. 부품을 DB 에 등록·수정한 뒤에는 묻지 않고 새로 불러와 부품 3D 창을 열어 보여 준다.
- **I5 [도구:`app/api/local-refs`·design.html `refStore`] 작업 중인 차시의 그림은 라이브 DB 에서 받지 않는다 — 개발 서버(localhost)는 `scripts/assembly-tools/refs/<이름>/`(index.json)의 파일을 바로 읽고(DB 요청 0), 저장소에 그림이 없는 차시만 DB 에서 받는다. DB 에서 받을 때는 접속한 차시의 그림만 뒤에서 이 컴퓨터(IndexedDB)에 저장해 두고, 그림마다 버전(ctid·xmin·updated_at)을 비교해 바뀐 것만 다시 받는다(사용자 2026-11-03).**

## J. 화면 조작·보고·말투

- **J1 [문장] 사용자가 보는 화면은 평소 기본 모습으로 둔다: 왼쪽 패널 펼침·1~N번·완성 번호판·카메라·관절 버튼을 요청 없이 바꾸지 않고, 패널을 접거나 관절을 토글하지 않는다.** 단 번호를 끝내기 전 카메라를 돌려 직접 보는 것(H6)은 상시 허락이며, 확인하느라 바꾼 카메라·패널·팝업은 끝나면 반드시 기본 모습(저장된 카메라)으로 되돌린다.
- **J2 코드·데이터·문서·DB 그림·카메라 값 중 무엇이든 하나라도 고쳤으면(화면이 안 바뀔 것 같아도, `build --write` 가 막혀 반영이 안 될 것 같아도), 고친 턴 안에서 반드시 페이지 전체를 새로 불러와(`navigate`) 화면을 보여 주고(스크린샷) 무엇이 어떻게 보이는지 설명한다 — 반영이 안 됐으면 "안 바뀌었다, 이유는 …"를 보여 주는 것까지가 이 규칙이다. 옛 메모리의 "전체 새로고침 금지·먼저 묻기"는 이 규칙에 진다(2026-11-07 풍차 9번: 그 메모리와 "막혀서 소용없다"는 제 판단을 이유로 건너뛰어 혼남). 사용자가 시키지 않아도 한다(사용자 지시 2026-11-02, 어긴 사례: 규칙 문서만 고치고 화면 확인을 빼먹음).** 저장·빌드한 데이터를 화면에 반영해 보려면 페이지 전체를 새로 불러온다(`navigate` 로 설계 화면을 다시 열고 3권·3차시·번호 선택). 메모리 `no_full_page_reload` 의 "차시 select 토글로 데이터를 다시 읽는다"는 이번에 확인한 결과(토글은 새로 저장한 데이터를 못 읽음)와 다르다 → 그 메모리를 이 규칙으로 고친다. 사용자가 "다시 불러와 화면에 보여 주라"고 지시했고(2026-11-02) 수정할 때마다 6방향(H2)으로 보는 일에 필요하다. 사용자가 보는 화면을 요청 없이 새로고침하는 것과는 다르다.
- **J3 [문장] 보고는 존댓말·짧게. 말이 거칠어도 규칙대로 하나씩 정직하게(확인한 것/추정 구분) 보고한다.**

# 제1부 교재검사 — 사전작업: 교재 읽기·관찰·분석이 맞는가

## A. 순서·게이트

- **A1 [도구:number_start] 큰 순서는 01 번호 등록 → 02 이미지 자르기 → 03 부품 정리 → 04 창고 정리 → 05 번호별 조립이다. 앞 과정·앞 번호가 안 끝났으면 다음으로 가지 않고, 안 한 것은 보고하지 말고 그것부터 한다.**
- **A2 [도구:number_start, `parts_sum` 켠 조립도] 03 부품 정리(1차, A2a): 모든 번호의 사용 부품을 책 그림에서 읽어 번호별 표(`USED`)로 적고 교재 LIST와 합계를 맞춘다.** "N~M번 2개 만들기"는 2배로 센다. 합이 안 맞으면 숫자를 고치지 말고 그림을 다시 보고 어느 번호를 잘못 읽었는지 찾는다. 안 맞는 부품이 남아 있으면 번호 작업을 시작하지 않는다. 번호 설명(note)의 아래 줄에 "▣ 사용 부품: 부품 개수, …"를 줄을 바꿔 한 줄로 따로 적는다(합치는 단계는 "▣ 사용 부품: 없음(합치는 단계)", 두 벌 만드는 번호는 끝에 "(2벌)", 스크립트에는 번호 → 부품 표 `USED` 를 두고 반복문으로 붙이며 이미 있는 줄은 잘라 내고 다시 붙여 중복을 막는다). 추정한 개수는 코드 주석과 보고에만 적고 note 에는 쓰지 않는다. 조립도 쪽 개수가 교재 LIST 와 다르지만 사용자가 맞다고 확인한 부품은 `Asm(..., qtyOverride={"15프레임": 6})` 로 적는다 — 화면의 "필요 부품"이 그 개수를 기준으로 보이고 책 개수는 "⚠ (책 N개)"로 알린다. 리벳은 그림 옆 "(n)" 표시 숫자 그대로 쓰고 다른 부품은 그림에서 센 값(근거가 약하면 "추정")을 쓴다. 부품 이름은 `<이름>_list.json` 의 이름과 똑같이 쓴다(LIST 이름과 DB 이름이 다르면 LIST 이름으로 적는다). 3D 모델이 없는 부품(부품 DB 에서 모델 없음으로 나오는 것)은 조립도 제외 대상이라 번호 설명에만 적고 모델 부품 수에 넣지 않으며, 그런 부품만 나오는 번호는 빈 단계로 두고 `USED` 에 "고무밴드 2 (3D 모델 없음)" 처럼 적는다(줄은 `bands`, G10). 03 을 끝내면 번호별 부품 표 / LIST 와 맞는 부품 / 안 맞는 부품과 의심 번호로 보고한다.
- **A2a [도구:build, 화면 배지] 03 부품정리는 "1차"다 — 책을 번호 순서대로 대략 훑어 모든 번호의 사용 부품을 적는 것이고, 완벽할 필요가 없다. 상세·정정은 번호 조립 중에 한다(B5).** 번호판 위 배지는 기본 "미완"이고, **모든 번호에 `▣ 사용 부품` 이 적혀 있고 부품별 합계가 교재 LIST 와 같을 때** `build.py` 가 "1차 완료"로 적는다(`prepDone.parts`). 조립하다 부품이 틀린 것을 발견하면 03 표를 고치고 이어간다.
- **A3 [문장+도구일부:build] 04 창고 정리(1차, A3a): 책을 번호 순서로 보며 번호마다 slot·history를 정한다.** ① 연달아 이어지는 번호(세트, "N~M 2개 만들기")는 같은 창고 ② 새 세트가 나오고 기존 세트가 안 보이면 새 창고 ③ "N + M" 합치기는 앞(작은 번호) 창고로 가져가 조립. 창고가 바뀌면 `history` 글, 안 보여야 할 앞 번호는 `hideMade`, "2개 만들기" 둘째 벌은 `copy_to_slot`. 창고 0 = 메인, 1~5 = 따로 만드는 자리이고 **1번은 창고 1에서 시작한다.**
  - **그룹 이름:** "그룹 1, 그룹 2…"(원점에 가까운 쪽이 먼저, 그다음 왼쪽부터)로 쓰고 다른 이름으로 바꾸지 않는다.
  - **history 쓰기:** 창고·불러오기는 번호·설명 본문에 쓰지 않고 `history` 에만 쓴다(예: "창고 1에서 불러와서 조립 → 그룹 1").
  - **둘째 벌 복사:** "N~M번 2개 만들기"의 둘째 벌은 새로 만들지 않고 `copy_to_slot` 으로 복사해 다른 창고에 보관한다(같은 창고 옆에 두면 겹침 문제, 사용자 2026-10-15) — 복사본은 `until` 전까지 보관 중이고 원본과 기본 z +300 떨어져 있으며 읽기 표 부품 수에서는 빠진다(`copyOf`).
  - **사용자 ✓:** 앞 번호에 사용자 ✓ 가 있으면 그 번호의 부품 데이터는 고치지 않고 새 번호에서 `hideMade` 로 숨기며, 새 창고 원점이 숨은 세트와 맞닿으면 그 부품에 `noGuide` 를 쓴다.
- **A3a [도구:build, 화면 배지] 04 창고정리도 "1차"다 — 책을 훑어 모든 번호의 작업 창고를 먼저 기록하는 것이고, 상세·정정은 번호 조립 중에 한다.** 배지는 기본 "미완"이고, 모든 번호에 slot 이 있고 창고가 바뀌는 번호마다 `history` 가 있으면 "1차 완료"(`prepDone.slots`)로 적는다. **배지는 기록이 있다는 뜻일 뿐 정리가 맞다는 증거가 아니다:** 번호마다 작업장(화면)을 책과 비교해 책에 없는 앞 번호 부품이 같이 보이거나 놓인 자리·창고가 책과 다르면, 배지가 완료여도 증거를 남기기 전에 그 자리에서 `hideMade`·slot·`history` 를 고치고(A5) 다시 불러와 확인한 뒤 넘어간다. **`hideMade` 는 번호마다 그 번호 책 그림에 나오는 부품만 남기게 정한다 [도구:hidecheck.py]** — 도구는 부품마다 지금 있는 창고(만든 번호의 창고, 합쳐지는 번호 `side.until` 이후엔 그 번호의 창고, 옮겼으면 옮긴 번호의 창고)를 계산해 이 번호 창고가 아닌 곳의 부품이 화면에 보이면 보고한다(풍차 18번 날개 4개 사고, 2026-11-08). 합쳐지기를 기다리는 부품은 `hideMade` 의 "만든번호:부품순서" 키로 숨기되 값은 `side.until` 에서 계산해 만든다. 앞 번호 줄을 복사해 붙이지 않고, 새 창고(slot 이 바뀌는 번호)는 그 창고에 속하지 않는 앞 번호(이미 다른 창고로 합쳐 간 번호 포함)를 모두 숨기며, 책 그림을 열어 어느 부품이 그려졌는지 본 뒤 정한다. 풍차 16·17·20번에서 허브·날개가 같이 보인 원인은 13~22번의 `hideMade` 가 모두 "1~12번" 복사본이었고 점검(배지·build)은 slot·history 가 적혀 있는지만 봐서 아무도 못 잡은 것이다(2026-11-07 사용자 지적). `python hidecheck.py <이름>` 이 "새 창고 번호인데 다른 창고 앞 번호가 숨겨지지 않은 곳"을 찾지만 합쳐 간 같은 slot 번호는 못 잡으므로 최종 판단은 책 그림이다. 화면 반영이 `build --write` 에 막히면 막은 항목을 B9 순서로 풀어 반영하고, 반영 전에는 그 번호를 "책과 같다"고 증거로 적지 않는다. **막는 항목별 푸는 법(2026-11-07 풍차에서 확인):** ① 새 창고의 첫 부품(원점에 `place`)과 옆자리 묶음이 앞 몸체 자리와 겹쳐도 `noGuide` 를 붙이지 않는다 — 점검기(`design-verify.js`·`check_local.js`)가 같은 창고(slot)의 부품끼리만 결합으로 세므로 겹쳐도 가짜 결합이 안 된다(G1b, 풍차 5번 `noGuide` 를 빼도 점검 0건) ② 옆자리 묶음이 바닥(y=0) 아래로 내려가면 `side_row(..., floor=True)` ③ 합치는 부품의 안내점이 없으면 `to_side(..., hosts=(받는 부품…))` ④ 긴 축은 돌기 가운데가 구멍에서 멀어 `marks='auto'` 가 못 내므로(`join_marks` 3.5mm 한계) 받는 구멍 입구를 `hole()` 에서 계산해 `moveMade` 의 `marks` 에 넣는다 ⑤ 위를 다 풀어도 아직 시작하지 않은 번호에 격자가 없으면 `build --write` 가 막는다 — 그 번호까지 순서대로 만들고(C3 순서) 한꺼번에 반영한다.

### P4. 04 창고 정리 (1차 — 기준은 A3·A3a)

**번호마다 창고(slot) 정하기**
창고 0 = 메인, 1~5 = 따로 만드는 자리. 책을 번호 순서대로 보며 정한다. **1번은 창고 1에서 시작한다.**

**스크립트에 적기**
- 번호마다 `kw["slot"] = 번호`. 앞 번호와 slot 이 바뀌면 `history` 글이 반드시 있어야 한다(`build.py` 검사). 창고·불러오기는 번호·설명 본문에 쓰지 않고 `history` 에만 쓴다. 예: "창고 1에서 불러와서 조립 → 그룹 1", "그룹 1 + 그룹 2 합침".
- 그룹 이름·`history` 에만 쓰는 것 → 규칙 A3.
- 다른 창고에서 작업하는 동안 안 보이게 둘 세트: 그 부품들에 `hideAt`(숨길 번호들), `store`({번호: "N번까지 만든 본체"}), `storeThumb`(사진). 사진은 사용자가 📷 썸네일 저장으로 만든다.

## D. 홀라인·격자

- **D1 [도구:holefit·rulecheck, 순서는 문장] 홀라인(구멍 격자) 맞추기가 번호 이미지 작업의 첫 단추다. 순서: ① 책 그림을 훑어 부품·초록 링·화살표 읽기(링은 색으로 검출해 중심 픽셀을 숫자로) ② 기준 부품 정하기 ③ 판 바깥 모서리 4곳을 `crop_ticks.py`(≤100×100px 확대 눈금)로 읽기 ④ `holefit.py` ⑤ `hf/NN_<라벨>.png` 를 눈으로 보고 점이 모든 구멍 한가운데에 있는지 확인 ⑥ `axes_fit` → ⑦ `refs_rect` → ⑧ 만들자마자 DB 에 올림.** 눈대중 모서리·간격 어림으로 격자나 축선을 긋지 않는다.
- **D2 [도구:verify_step '양쪽 홀라인'(18번부터)] 홀라인은 결합하는 부품과 결합되는 부품 양쪽 모두 만든다(라벨 P·U 등).** 책 링이 받는 쪽·끼우는 쪽 각각 몇 번째 구멍인지 세고 두 부품의 구멍 간격(피치)이 같은지 대조한다. 같은 구멍이라고 가정하지 않고 `recv`/`attach` 에 구멍 id 를 명시한다. 기준(베이스) = 그 번호에서 결합을 받는 부품이며, 흰 판이 잘 보인다고 흰 판을 기준으로 하지 않는다. 결합 쪽이 판이 아니라 돌기·프레임일 때 잘 보이는 판의 격자는 **카메라를 풀기 위한 격자**로만 쓰고, 결합 홀라인(끼우는 쪽 구멍·받는 쪽 돌기 칸)은 따로 센다. **끼우는 부품이 한 줄 막대(19프레임 등 1×N)여도 링을 "양 끝 구멍"이라고 짐작하지 않는다 — 막대의 구멍 N개를 `crop_ticks.py` 확대 그림(3배 이상)에서 왼쪽 끝부터 하나씩 세어 링이 몇 번 구멍인지 적고(읽기 표 링 칸), 링 사이 구멍 수 × 10mm 가 받는 쪽 돌기 간격과 같은지 대조한 뒤 `recv` 구멍 id 를 쓴다(사용자 지적 2026-11-08 로봇팽이 10번: 링이 h2·h4·h9 인데 h1·h3·h8 로 읽었다 — 링이 구멍 중심에서 10~15px 어긋나 그려지는 것도 확대해서만 보인다).**
- **D3 [문장] 격자 점은 구멍 한가운데에 둔다. 확대해서 모든 구멍(리벳 위 구멍 포함)에 점이 있는지 센다. 가려진 구멍(격자로 채운 연장 점)은 화면에 그리지 않고 "연장"이라 적는다(`hide_est`). 구멍 점을 손으로 같은 간격으로 채우지 않는다.**

- **D7 [문장] 축선은 항상 구멍 줄(홀 라인)의 구멍 중심을 지난다. 가운데 줄·가운데 열이 축선에서 벗어난 거리(px)는 격자가 채운 점이 아니라 실제로 검출된 구멍 중심으로 잰다.** 줄이 둘뿐인 프레임은 `center_row`·`grid_rows_only`. 축선 원점은 늘 판 가운데 칸·가운데 줄(앞 번호와 같게, 가려져 있어도 모델 좌표로 투영)이고, 도구가 고른 가장자리 앵커가 아니다.
- **D8 [문장] 새 부품의 칸은 링 픽셀 환산만으로 정하지 않는다: ① 이미 놓은 부품(축·프레임 가운데·블록 등)을 지나는 X·Z 축선을 그림에 긋고 ② 그 선이 격자 어느 칸·줄을 지나는지, 새 부품이 그 선 위인지 옆인지를 보고 ③ 환산 값과 함께 맞춰 읽는다.** 둘이 다르면 선 정렬이 먼저다. 읽기 표 `링` 에 "○○ 선(칸N) 위/옆 한 칸"으로 적는다.
- **D9 [문장] 판의 한 변이 책 그림 밖으로 잘렸으면(713프레임 16번: 윗변이 그림 위쪽 밖) 안쪽으로 눌러 읽은 가짜 모서리를 쓰지 않는다 — 보이는 실제 모서리 3곳과 판 치수(칸 수)로 잘린 모서리를 이미지 밖 좌표(음수 가능)로 외삽해 `holesearch`·`holefit` 에 준다.** 모서리가 이미지 안에 있다고 가정해 눌러 읽으면 평균 3~5px 로 미달한다(16번 외삽 후 DoG 평균 1.65px·최대 3.64px 통과).
- **D10 [도구] 격자 도구 선택은 C3(푸는 순서), 단계별 기준·검증은 D12 를 따른다.** 도구 설명(`holefit`·`holesearch`·`infer_grid`·`plate_match`·`frame_fit`·`line_fit`·`mkfit3d`)은 부록 "도구 지도"에 한 곳으로 모은다.
- **D11 [문장] 격자 주의 다섯(⑤ 추가 2026-11-07): ⑤ 격자가 미달이면 ⚠ 로 적고 멈추기 전에 미달 원인이 도구 한계인지 먼저 본다 — `holefit` 의 "이상한 구멍 버리고 다시 맞추기"는 남는 점 수가 칸 수의 절반(최소 5, 최대 10·DoG 20)을 넘게 요구하지 않는다(예전엔 10점 고정이라 칸이 10개뿐인 25프레임 2×5 판은 초록 선·링에 가려 치우친 구멍을 하나도 못 버려 평균 7px 로 미달했다). 격자는 보이는 구멍으로 항상 만든다(`build --write` 가 격자 그림 1·2번 없는 번호를 막는다). 그리고 앞 번호 읽기 표 판단과정에 이미 적힌 시도를 먼저 읽고 같은 시도를 되풀이하지 않는다. 격자 주의 넷: ① 한 직선 위에 놓인 구멍들은 여러 부품의 구멍이라도 한 줄(N칸×1줄)로 만든다(투석기 15번: 블록 둘의 큰 구멍 4개 = 4칸×1줄). ② 격자만으로 카메라를 맞추면 +Y 가 아래를 향하는 거울 해가 섞일 수 있으니 +Y 방향을 확인한다. ③ 격자 점은 구멍의 눈에 보이는 중심(안쪽 어두운 영역의 무게중심)에 둔다 — 눈대중 모서리·템플릿을 처음 격자 위치에서 자르면 처음 위치 쪽으로 쏠려 오차가 작게 나온다(투석기 20번: 점이 구멍 아래 테두리를 약 9px 지났다). 잔차는 실제 구멍과의 거리(평균·최대 px)로 말한다. ④ `holefit`·`holesearch` 통과(평균 ≤2px)는 모서리가 판 윗면 위에 있다는 증거가 아니다 — `holesearch` 는 평균 오차만 줄이므로 가까운 쪽 끝 모서리를 윗면 밖(끝면·옆면)으로 끌고 가도 통과한다(풍차 8번: 가까운 끝 모서리가 끝면의 초록 링 쪽으로 이동해 holefit 1.85px 통과, `axes_fit` 카메라 3.61px 미달). 그래서 격자를 저장한 뒤 반드시 `axes_fit` 을 돌려 카메라 오차 ≤2px 를 확인하고, 미달이면 점별 잔차가 큰 열(보통 판 끝)을 찾아 그 모서리를 ≥5배 확대 눈금 그림(`crop_ticks`)에서 윗면 가장자리로 다시 읽어 `holefit` 부터 다시 한다(점을 빼서 맞추지 않는다 — 그 모서리로 풍차 8번은 평균 0.92px·카메라 1.08px). `axes_fit` 은 미달이어도 `<번호>_axes.json` 을 덮어쓰므로(C4) 거울 방향까지 돌려 본 뒤에는 통과한 값으로 다시 한 번 돌려 파일을 맞춘다.**
- **D12 [문장+도구] 격자 풀이 기준·검증 (사용자 2026-10-13~10-31; 명령 사용법은 `05_조립.md` 0-1~0-4):**
  - **근거를 전부 모은다:** 기준에 모자랄 때 멈추거나 승인으로 넘기지 않고, 그 번호·앞뒤 번호·대칭쪽·완성 사진의 정보를 모두 모아 서로 맞는지 잔차(px)로 푼다. 대칭 쪽은 반대편 끼움 그대로 따른다(거울, F2·F10).
  - **`infer_grid`:** 근거 = 같은 판의 3D 치수(앞 번호에서 전체가 보인 판, 10mm 간격) · 선명하게 검출된 구멍 · 앵커(칸을 아는 책 초록 링) · 줄·칸 배정 가설 전부 돌려 잔차 최소. 가설이 하나로 안 갈리면(2등이 1등의 1.3배 미만) 저장하지 않고 필요한 추가 근거(뒤 번호 그림·완성 사진·대칭 유닛의 끼움)를 말한다.
  - **검증은 개수가 아니라 거리로:** 링·앵커 오차 px, 풀이 카메라와 사용자 📷·뒤 번호 카메라 비교, 모델 화살표 끝점이 책 링과 몇 px 인지. 풀이 카메라 roll 이 크면 책 그림이 기울어 그려진 것이니 그림을 그만큼 돌려 비교하고 가설을 거르는 근거로 쓰지 않는다.
  - **근거 그림:** 유추한 번호에만 붙인다(기본은 ①원본 ③방향 ④격자 3장). 앞 번호(같은 판·대칭)·완성 사진(00)·뒤 번호 그림과 확대 눈금·hf·`frame_fit` 확인 그림은 만든 즉시 DB 에 `idx 3~` 으로 올리고 설명에 무엇으로 무엇을 유추했는지 적는다. 실패한 홀라인 시도 그림은 틀린 배정이 그려져 있으니 올리지 않는다(찾은 구멍 수·오차는 격자 그림 설명에).
  - **`rulecheck` 보고:** 유추 격자는 ⚠ "사용자 확인 필요"(근거 부족이면 ❌). 근거(앵커·잔차·유일성)는 `fits/NN_<라벨>.json` 의 `evidence` 에 남는다. 사용자 ✓ 를 기다리느라 멈추지 않는다(마지막 보고에 한 줄).
  - **`line_fit`(한 줄 부품 — 115·15·17·19프레임 등) 통과 기준:** 읽은 구멍 ≥6 · 평균 ≤2.5 · 최대 ≤4.5px · 기준 격자 ≤2.5px. 미달이면 점을 빼지 말고 큰 오차 구멍을 더 작은 창(≤100×100px)에서 다시 읽는다. **`mkfit3d`(판이 없는 번호):** 3D 확정 점 ≥6 · 평균 ≤2.5 · 최대 ≤4.5px(눕힌 좌표 조립도는 `--눕힌좌표`, `05_조립.md` 0-1 8). 공중에 뜬 부품의 점은 뜬 높이를 모르는 값으로 두고 시야각(fov 8~25)과 함께 훑어 가장 작은 오차를 고른다(풍차 7번: 뜬 높이 약 50mm에서 5·6번과 같은 카메라가 나옴 — 같은 카메라면 앞 번호 카메라를 쓴다, H16). 평균이 2.5px 를 넘으면 격자를 저장하지 않고 판단과정에 ⚠ 로 적는다(B9 를 거친 뒤). 통과하면 `rulecheck` 가 ⚠ "사용자 확인 권장"(진행은 막지 않음).
  - **`plate_match`:** 칸 밀림은 `--검증` 점(앞 번호에서 우리가 놓아 3D 가 확정된 점 5개 이상)을 순방향으로 투영한 오차가 가장 작은 밀림으로 고르고 2등과 비 1.5 이상이어야 유일하다(역투영은 선택 기준이 아니다). 판 칸 밖으로 환산되는 매칭은 버린다. 인라이어 20 미만 · roll 큼 · 2등과 비 1.5 미만이면 쓰지 않고, 앞 번호 3D 확정 점 + 판 먼 모서리 2곳(앵커 8개 안팎)으로 `infer_grid` 앵커만 유추한다 — 앵커를 하나씩 빼 theta·phi·fov 가 안 변하면 안정이다.
  - **0-3(몸체가 목표 구멍 둘레까지 덮어 대응점 식별이 애매할 때):** `holefit`·`plate_match`·`infer_grid` 를 각각 3회 이상 시도해도 잔차가 수십~100px 대일 때만 쓴다. 눈에 띄는 3D 확정 점 하나와 목표를 책 그림 위에 실제로 선으로 그어 눈으로 보기 전에는 좌표를 확정하지 않고, 리벳↔리벳 선(칸 수 일치)과 새 부품 돌기↔돌기 선(부품 피치 일치)이 **둘 다** 맞아야 그 칸 배정을 쓴다(하나만 맞으면 추정 — `step.kw["review"]=True`). 정식 PnP 가 수렴하면 그게 우선이고, 소수부 0.3 이상은 다음 번호 책에서 재확인(⚠).
  - **0-4(주황 리벳 별자리 — 판이 가려져 격자를 못 만들 때):** 가장 뚜렷한 리벳 4개로 임시 카메라를 풀고 나머지 리벳 3D 를 투영해 ≤12px 면 같은 리벳으로 붙인다. 거울 해(phi>2)면 `fov` 를 고정하고 8px 넘게 벗어난 점은 빼며(근거를 name 에) 하나씩 빼 theta·phi 가 안 변하는지 본다. 링은 앵커로 쓰지 않고 독립 확인으로 남긴다(투영한 칸이 링에서 몇 px 인지).

## E. 방향·카메라·축·이미지 회전

- **E1 [도구:axes_fit·rulecheck(오차 ≤2px·점 4개 이상)·pnp.fit] 카메라·축 값은 번호마다 그 번호의 격자에서 `axes_fit.py` 로 계산한다 — 앞 번호 값 복사·"같겠지" 금지.** 오차 2px 초과·phi 1.55 초과(거울 해)면 쓰지 않는다. PnP 해는 모든 점이 카메라 앞에 있는 것만 쓴다(`pnp.fit` 이 걸러 낸다 — 오차가 같아도 점이 카메라 뒤인 거울 해는 화면에서 프레임·블록이 위아래로 뒤집혀 보인다). 점이 평면에 가까워 해가 여럿이면 모델 자세를 24가지 직교 자세로 돌려 보며 카메라가 땅 위(phi<π/2)·롤이 작은 자세를 고른다(해머배틀 17번). `_axes.json` 에 `fit` 이 없으면 손으로 쓴 값이다. 카메라는 짐작(guess)으로 두지 않고 책에서 읽은 방향(가까운 쪽·화면 오른쪽·위)으로 정해 `camSrc="eye"`. 눈맞춤만으로 "맞췄다" 하지 않고 책에서 방향 3개(화살표·판 긴 변·짧은 변)의 화면 각도를 재서 모델 방향을 투영한 각도와 차이를 숫자로 본다.
- **E2 [문장] +Z 의 부호는 칸·줄 번호 순서가 아니라 오른손 법칙(X×Y=Z)으로 정한다.** theta·phi 는 측정한 X·Z 화면 각도로 계산한다(`cosφ=√(−tanαX·tanαZ)`, `tanθ=−tanαX/cosφ`).
- **E3 이미지 회전: 구멍 줄이 놓인 축(예: "X")을 `<번호>_axes.json` 의 `rotate_to` 에 적고 `refs_rect.py` 를 돌린다 — 가운데 줄·가운데 열의 방향이 그 축선과 같아지게 작은 각도로 회전만 한다(늘이기·펴기·90° 눕히기·거울 금지).** 가운데 축선은 돌지 않고 읽은 원래 화면 방향 그대로. 가장자리 줄이 4~5° 벌어지는 것은 원근이라 정상. `level: true` 는 사용자가 "회전해서 맞추라"고 했을 때 구멍 줄을 수평으로 돌린다. `no_rotate: true` 는 구멍 줄이 없는 번호(링 점만 찍는 그림)에만 쓴다.
- **E4 [문장] 번호마다 책 그림의 +X·+Y·+Z 가 화면에서 가리키는 방향을 `_axes.json` 의 `global` 에 적고(`axes_fit` 계산값), 읽기 표 '방향' 판단은 그림이 아니라 가운데 축선을 보고 한다.** 방향이 정해진 부품(DC모터·메인보드·기어)과 창고에서 꺼내 합치는 그룹은 읽기 표에 방향 카드(면 사실 = `measure_part`·`get_part_connectors`, 책 증거 = 케이블·빨간 십자·접시 머리·돌기 수)를 먼저 쓰고 놓는다. 형식: `{"global": {"X": [dx,dy], "Y": [dx,dy], "Z": [dx,dy]}, "local": [{"at": [x,y], "label": "DC모터", "X": [...], "Z": [...], "size": 45}]}` (원본 그림 화면 좌표, 오른쪽 +x·아래 +y, 안 쓰는 축은 빼도 된다). `refs_rect.py` 가 이 파일로 X(빨강)·Z(파랑)·Y(초록) 축선을 그리고 `local` 자리에도 같은 모양을 또 그린다(색은 조립 보기 화면과 같다).
- **E5 [문장] 카메라가 보는 면을 먼저 적는다: 어떤 부품의 어느 면이 카메라 쪽인지, 판이 서 있는지 눕는지, 가까운 쪽·화면 오른쪽·위가 ±X·±Y·±Z 어디인지.** 책 그림이 "판이 서 있는" 모양이면 눕힌 모델에 카메라만 맞추지 않고 모델 자세를 책과 같게 놓는다. 카메라를 땅 밑(phi>π/2)으로 보내지 않는다. 카메라 `theta` 규약: 0 = +Z 에서 봄(화면 오른쪽 +X), π/2 = +X 에서 봄(오른쪽 −Z), π = −Z 에서 봄(오른쪽 −X), −π/2 = −X 에서 봄(오른쪽 +Z). 격자·축 방향을 만든 뒤 그 그림에서 가까운 쪽·화면 오른쪽·위가 ±X·±Z·±Y 중 어디인지 읽기 표 `방향` 칸에 적고, 그 방향이 되게 `step.cam` 을 정한다.
- **E6 [문장] 서 있는 부품(아치·벽·세운 프레임)의 카메라는 세계 3D 좌표로 푼다** — `frame_fit`·`axes_fit` 는 부품이 바닥에 누운 것으로 가정해 theta·phi 가 틀린다. 한 장면의 카메라는 하나인데 부품마다 풀면 값이 다를 수 있으니 기준 부품의 값을 쓰고 차이를 판단과정에 적는다. 다리를 눕혀 만드는 번호(꼬마기사 13번)는 눕히는 변환(x 축 90°)을 코드에 적고, 서 있는 다리는 앞(+Z)에서 본다.
- **E7 [문장] 방향이 앞 번호와 전혀 달라 보이면(롤 40° 이상·거울 해) 읽은 방향이 틀렸다는 신호다 — 책에 보이는 그대로 모델을 여러 쪽으로 돌려 책 시점과 비교하고, 책 점을 모델 3D 점으로 다시 풀어 롤이 0 에 가까워지는 쪽을 고른다.**
- **E8 [문장] 번호를 시작할 때 사용자가 저장한 ❄·📷 값을 먼저 읽는다(B3).** 사용자가 고치라고 한 부품은 코드와 ❄ 기록을 둘 다 `python pose_edit.py <이름> N "라벨:x,y,z"`(백업 자동)로 맞추고 시키지 않은 기록은 건드리지 않는다. 비교 화면에서 `br.camera` 로 사용자 📷 를 덮지 않고 코드 `cam` 도 맞춘다. 수정저장차이를 분석할 때 📷 차이는 마감 취향이라 오류로 세지 않고 ❄ 자세와 요청차이만 오류로 센다(사용자 지적).
- **E9 [문장] 교재 그림은 거의 다 대각선 시점이다 — 구멍 수·열 번호를 세기 전에 판·팔 축이 가로가 되게 돌리고(보통 12~25°) 확대해서 읽는다.** 격자가 안 맞을 때만이 아니라 처음부터 한다.
- **E10 [문장] 방향 기준 부품은 모터 종류·메인보드·기어 종류다 — 이 부품들이 어느 쪽을 보는지(DC모터의 돌기 면·빨간 십자 면·옆돌기, 메인보드의 케이블·버튼 쪽, 기어의 종류와 핀·T축 구멍이 중심의 어느 쪽인지)를 먼저 읽고 X·Y·Z 를 정한다(틀리면 뒤 번호가 다 어긋난다). 각 부품이 어느 쪽에 있고 어느 쪽을 보는지는 그림이 아니라 가운데에 그린 X·Y·Z 축선을 보고 판단해 읽기 표 '방향'에 적는다.**
- **E11 [문장·도구: 칸 표 출력은 아직 없음, 윤곽 맞춤은 bookcam.py·camiou.py] 카메라는 열십자 4칸 비교로 맞추고 확인한다 (사용자 지시 2026-11-08, "대충 하지 말 것").** 책 그림과 뷰어 화면 양쪽에 가로선·세로선을 하나씩 그어 4칸(1 왼쪽 위·2 오른쪽 위·3 왼쪽 아래·4 오른쪽 아래)으로 나누고, 칸마다 보이는 부품을 이름으로 적어 나란히 비교한다. ① **먼저 카메라 핀(보는 중심)을 지금까지 조립한 부품 전체의 가운데로 맞춘다** — 뷰어는 기본으로 이번에 끼운 부품만 가운데에 잡아서 나머지가 치우치고 잘리기 때문이다(카메라 방향 theta·phi 는 그대로 두고 중심과 거리만 바꾼다. 예: 풍차 24번은 중심 [-20, 163.75, 0]·거리 640 으로 날개·탑·상자가 한 화면에 다 들어왔다). 그런 다음 선의 교점을 책 그림 정중앙과 뷰어 화면 정중앙에 긋는다. 그래도 크기·중심이 안 맞으면 카메라를 더 옮기지 말고 양쪽 그림에서 같은 부품의 같은 점(예: 풍차 중심 기어)에 긋는다. ② 이 점은 눈짐작으로 찍지 않고, 책 쪽은 fits 의 3D↔그림 점으로, 뷰어 쪽은 같은 3D 점을 화면에 투영해서 찍는다. ③ 칸 사이에 걸친 부품은 어느 선을 넘는지까지 적는다. ④ 칸이 화면 밖으로 잘려 안 보이면 "비교 못 함"으로 적고 "비슷하다"로 넘기지 않는다. ⑤ 이것은 방향을 보는 보조 확인이며, E1 의 오차(≤2px) 계산을 대신하지 않는다. ⑥ 뷰어에 얹은 선은 확인이 끝나면 지우고, 시험하느라 바꾼 카메라는 원래 값으로 되돌린다. ⑦ **맞추는 순서(앞으로 모든 번호): 카메라 핀을 전체 가운데로(①) → 열십자 → 칸별 부품 비교 → 어긋난 칸이 가리키는 쪽으로 theta·phi 를 조금씩 돌려 칸이 같아질 때까지 반복 → 같아지면 그 값을 카메라 값으로 저장하고, 칸 비교 표(책·뷰어 칸별 부품 이름, 같음/다름/비교 못 함)를 판단과정에 남긴다.** 윤곽 겹침(IoU)으로 자동 탐색하는 bookcam.py·camiou.py 가 이미 있으니, 먼저 그 값을 시작점으로 쓰고 이 칸 비교로 확인·보정한다(그 도구의 각도는 모델 좌표 기준이라 xform 이 있는 조립도는 세계 좌표로 바꿔서 쓴다 — E6).

## F. 대칭·같은 조립 둘·방향

- **F1 [문장+observe 그룹비교] 같은 조립이 둘 이상이면 "같은 방향"인지 "대칭"인지 가정하지 않는다.** 책을 확대(원본 PDF 300dpi)해서 두 벌의 같은 부분(블록의 보이는 면·리벳이 보이는 쪽·판 앞뒤·끝 돌기 쪽)을 나란히 비교한다. 같은 면이 보이면 같은 방향, 다른 면이면 대칭 — 읽기 표 '부품방향'에 어느 부분이 달랐는지 적는다. 책에서 같은 조립이 서로 다른 방향 둘로 그려졌으면 대칭(같은 조립을 반대쪽에서 본 것)이고 모델은 하나.
- **F2 [문장] 대칭(거울) 쪽은 반대편이 끼워진 그대로(거울 위치) 따르고 점수·후보 탐색으로 정하지 않는다. 한쪽을 고치면 반대쪽에도 같게 적용한다.** 대칭형이면 먼저 F9·F10 을 본다(모범 = 드롭체커).
- **F3 [문장] 합치는 번호는 놓기 전에 뒤 번호(없으면 완성 사진)를 확대해 층 순서·판 위치·블록이 어느 쪽인지·돌기가 어디로 나왔는지 적는다. 뒤 번호 구조와 안 맞으면 방향을 의심한다.**
- **F4 [문장] 방향을 확정할 수 없으면 멈추거나 묻지 않는다 — 가설을 만들지 않는다. 책 그림에 보이는 그대로(부품의 보이는 면·돌기 방향·링 위치) 모델을 놓고, 책 확대와 같은 시점에서 나란히 보며 다른 곳을 숫자로 찾아 고친다(B5 관찰 → 자기 질문 → 다시 관찰).** 점수 탐색·PnP 는 관찰로 맞춘 뒤 확인용이다.
- **F5 [문장] 판 구멍 격자 일치(holefit·mkfit3d)는 방향 증거가 아니다 — 판·블록은 뒤집혀도 격자가 맞는다. 방향은 비대칭 특징(3단블록 돌기 면·끝 돌기 쪽·리벳 머리가 보이는 쪽·DC모터 십자)의 위치로 확정한다.**
- **F6 [문장] 이상 신호(돌기가 z 로 안 들어감·블록 겹침·판 간격 부족·"책과 일부만 같다")는 ⚠ 로 적고 넘기지 않고 방향·대칭을 다시 정한다. 계산(PnP·점수 탐색)이 관찰을 대신하지 않는다.**
- **F7 [문장] 결합 해가 여러 개(구멍 무늬 반복으로 한 칸씩 밀려도 오차 0)면 책 링의 칸으로 고정하고, 위치를 구멍 개수 점수·후보 탐색으로 정하지 않는다.**
- **F8 [문장] 번호 시작 때 책 그림 속 글자(긴 쪽·말풍선·뒤집기 화살표 등)를 먼저 읽어 반영한다.** 단 "리벳 홈 방향 주의"(파란 가로선)는 사용자가 쓸데없다고 했으니(2026-11-04) 맞추려 애쓰지 않고 ⚠·못 한 것 목록에도 올리지 않는다(기존 리벳 자세를 따른다).
- **F9 [문장] 거울 변환: 대칭면이 z = c 이면 위치는 `p' = (x, y, 2c − z)`(x 거울이면 x 를 뒤집는다), 자세는 같은 부품을 돌려 놓는다 — `R' = M·R·M`(`M = diag(1,1,−1)` z 거울, `diag(−1,1,1)` x 거울).** 부품 자체를 거울로 뒤집는 것이 아니라 같은 부품을 거울 위치·거울 자세로 놓는 것이다. 부품이 스스로 거울 대칭이 아니면(135도 프레임·DC모터·메인보드 …) 거울 자세만으로는 안 되고 길이 축으로 180° 더 뒤집는다(드롭체커 `R_F135X = diag(1,−1,−1)`: 17번 둘째 팔은 7번 첫째 팔과 거울쌍이라 프레임을 뒤집어 짧은 팔이 반대쪽으로 꺾인다). 모터 면·돌기 면은 `measure_part` 로 읽고, 거울쌍으로 놓은 부품의 `R_*` 도 부품 DB 면으로 확인한다 — 모터·메인보드·기어 방향이 틀리면 뒤 번호가 다 어긋난다.
- **F10 [도구:symcheck] 대칭 쪽 검증·유추: `python symcheck.py <이름> [--축 z --중심 5] [--빠진것]` 이 거울 위치 거리가 0.00mm 인지 본다(`--빠진것` 은 반대쪽에 아직 없는 부품 = 그 부품의 거울 위치가 반대편에서 놓일 자리). 한 번호 그림만으로 안 풀리면 대칭 쪽 번호의 끼움 칸을 앵커로 쓴다: `infer_grid.py … --판 <앞번호>:<라벨> --거울 <대칭번호> 줄 --링 "x,y;…"`(링↔칸 짝은 도구가 모든 짝을 돌려 고른다).** 한쪽을 먼저 완성하고 반대쪽은 거울 위치에 같은 결합으로 만든다 — 처음부터 다시 탐색하지 않는다. 위치를 구멍 개수 점수·후보 탐색으로 정하지 않는다(드롭체커 24번: 구멍 4개 쌓인 볼트·너트 축 자리가 이겨 리벳이 너트 구멍에 끼워졌다).

## H. 6방향·관찰·증거·비교

- **H1 [도구:observe.py] 관찰의 대상은 부품 이름·개수가 아니라 결합되는 부분이다 — 링 한 개씩·화살표가 시작하는 돌기·판 구멍 칸.** 번호마다 결합 2곳 + 6방향 1곳(필요하면 그룹비교·뒤번호)을 `observe.py add` 로 책 크롭·화면 크롭(같은 시점·가까이)을 나란히 보고 기록하며, 판정이 '다르다'면 고쳐서 다시 기록한다. 관찰 그림(6방향 합성·크롭)은 번호마다 새로 만들고 `add` 하기 전에 그 파일을 열어 이번 번호 그림인지 확인한다(합성이 실패한 채 앞 번호의 낡은 그림이 증거로 들어가는 것을 막는다). **한 번호의 관찰 그림은 지점마다 서로 다른 그림이어야 하며, 같은 그림을 복사해 결합·6방향 증거로 채우면 증거가 아니다(3륜바이크 11~23번에서 한 장이 복사돼 통과한 것을 2026-11-09 발견 — `observe.py check` 가 같은 파일을 막는다).** 도구 ✅·"비슷하다"·"같은 것 같다"는 관찰이 아니다 — 센 값과 어느 번호 그림의 어디인지를 말한다. 한 번호를 읽을 때 눈에 띄는 곳부터 보지 말고 그림을 왼쪽에서 오른쪽, 위에서 아래로 훑으며 부품 → 초록 원 → 안내선을 하나씩 적고, 그다음 ① 이 번호 부품이 교재 LIST 에 있는지 ② 부품마다 돌기 수 = 꽂히는 홀 수인지(3단블록 돌기 3 → 홀 3) ③ 홀 간격(피치 10mm)과 블록 사이 간격 ④ 판에서 비어 있어야 할 열이 비어 있는지를 차례로 잰다. `get_part_faces` 로 조립 데이터를 이름으로 뽑아 책과 대조한다.
- **H2 [문장 → 도구로 올릴 후보] 6방향(위·아래·앞·뒤·왼·오른쪽)은 크게(화면의 절반 이상) 띄워 보고 방향별 한 줄로 적는다. 작은 썸네일·한 시점만 보고 끝내지 않는다. 수정할 때마다(번호를 끝낼 때만이 아니라) 다시 한다. 찍은 화면에 책 그림 팝업 등이 덮이지 않고 모델이 보이는지 확인한다.**
- **H3 [도구:record_check] 책↔화면 비교 증거: 같은 시점 스크린샷 + 센 개수가 든 비교 한 줄(30자 이상), 스크린샷은 45분 이내(긴 경로 파일은 PowerShell 로 짧은 경로에 복사).** 번호의 조립 모양이 바뀌면 증거가 무효가 되므로 다시 비교한다. 증거는 모양을 남기는 것이지 위치를 남기는 것이 아니다 — 조립 전체가 같이 옮겨진 것(1번 원점 이동 등)은 모양 지문(`stepfp.shape_fp`, 1번 첫 부품 기준 상대 좌표)이 같아 무효가 아니다(사용자 2026-11-05).
- **H4 [문장] 검토는 "통과 확인"이 아니라 "틀린 곳 찾기"다: 뒤 번호(없으면 완성 사진)를 확대해 센 특징 표(층·부품 순서·보이는 면·머리·옆 돌기 그룹·판·블록 개수와 방향)를 먼저 쓰고 모델에서 같은 항목을 같은 방법으로 센다. "다르다"가 하나라도 있으면 끝내지 않고 고친다.** 센 특징 표와 결과는 읽기 표 판단과정과 `<이름>_via.json` 에 센 값으로 적는다. `<이름>_via.json` 형식: `{"번호": [{"step": 다음번호, "image": "NN.jpg", "book_only": true, "what": "…"}]}`. 책 격자로 환산하면 수치(열·줄)로 말할 수 있다(오토타깃 19번: 21번 책 검은 판 격자로 샌드위치 열 5·13·줄 0·1). 안 맞을 때만 규칙·도구(홀라인·카메라·돌기↔구멍)를 되짚어 원인을 찾는다.

규칙 문장은 이 파일이 원본이다. 규칙을 바꾸면 이 파일만 덮어쓰고(옛 문장은 지운다), 도구에 올릴 수 있는 것은 `cubo_joint_check.py` 로 올린다. `[확정]` 은 사용자가 직접 말한 것, `[집계]` 는 조립도 20개에서 센 값(확인 전), `[가정]` 은 내 추정이다.
### K0. 물리법칙이 가장 우선이다 (결합 규칙 전체의 바탕)

- [확정, 사용자 2026-11-05] **모든 결합의 가장 큰 우선순위는 물리법칙이다 — 숨쉬듯이 바탕에 깔려 있는 규칙이다.** 조립도·3D 부품·결합원리 화면 모두 이 원리로 판단하고, 아래 모든 규칙은 이 위에서 읽는다. 위치를 정한 뒤에는 반드시 "어디에서 물리적으로 멈추는가, 무엇과 겹치는가"를 따져 보고, 모델이 이 원리와 어긋나면 번호가 아니라 도구·부품 모델을 고친다(예: 8볼트·12볼트 머리가 홀 테두리에 안 들어가는 크기였다).
- [확정, 사용자 2026-11-05] **면과 면은 자석처럼 붙는다 — 물리법칙을 무시하고 겹치거나 침범하면 안 된다(틈도 없다).** 홀처럼 뚫린 곳을 통과하거나 돌기가 구멍에 들어가는 것은 겹침이 아니다(T축이 기어·프레임 구멍을 지나는 것 등) — 이 규칙은 구멍이 아닌 몸통·면끼리의 겹침이다. 도구: `asmlib.py place_rest`(몸통 크기 기준으로 끝면에 닿게 놓음), `attach`/`recv`(돌기 끝이 구멍 면에 닿게 놓음).
- **부품끼리는 겹칠 수 없다.** 프레임끼리도 겹칠 수 없다(규칙 3·17). 겹침은 구멍 길이가 아니라 **실제 모양**으로 판단한다 — 부품 몸통 크기(`dims.json`·STL)와 홀 테두리(판 면 위로 솟은 고리)까지 포함한다(2026-11-05: 구멍 길이로 기어를 놓아 몸통이 홀 테두리를 파고듦).
- **구멍보다 큰 것은 지나갈 수 없다.** 대가리(볼트·너트·T축·서보고정볼트의 머리)는 프레임 홀(홀 테두리)에 맞춰서 끼워지고 통과할 수 없다 — 구멍의 좁은 곳보다 커서 지나가지 못하고 멈춘다(사용자 2026-11-04). 프레임에서는 머리가 홀 테두리에 맞춰 쏙 들어가 프레임 면과 같아진다.
- **T축은 끝까지 끼운다.** 홀 테두리가 없는 작은기어에서는 T축 머리가 기어 구멍을 지나가지 못하고 기어 윗면에 닿아 멈추며 머리가 기어 밖으로 남는다 — 남는 두께는 머리 두께(둥근 접시, 두께는 T축 STL 실측값 — 부품 상세내역에 아직 없음)이고 "2mm" 는 옛 예시였다(사용자 2026-11-04 정정). 세로·가로 모두, 띄운 모습은 그대로 두고 제자리만. 도구: `asmlib.py attach` 가 기어에 끼우는 T축을 머리 두께(`T_HEAD_OUT`)만큼 올려 놓는다. 프레임에 끼우는 T축은 도구가 아직 검증하지 못한다(눈으로 확인).
- **[확정, 사용자 2026-11-04] 축(T축)의 끝이 구멍 안에 그냥 들어가 있는 것은 결합이 아니다.** 돌기가 구멍에 들어가 있어도 꽂아 고정하는 결합(안내 화살표·안내점이 필요한 결합)은 책이 초록 링과 화살표로 보여 주는 것만이다. 길이가 긴 T축이 프레임·부시를 지나 끝이 아래 프레임 구멍에 들어가 있는 정도는 결합으로 세지 않고, 합치는 번호에서도 T축에는 합치기 안내점을 요구하지 않는다(안내는 구멍을 받는 부품이 맡는다). 도구: `check_local.js` 의 settle 검사가 T축을 건너뛴다.
- **돌기 하나는 프레임 한 장의 구멍에만 들어간다.** 돌기 길이가 판 한 장 두께쯤이라 프레임 두 장을 통과할 수 없다(규칙 5·7). 리벳은 양 끝 돌기가 각각 한 장씩 맡아 두 장을 묶는다.

### K3. 부품 연결점(돌기·구멍) — 어디에 있고 어떻게 확인하나
- **연결점 보조 규칙:** 순서는 `joinOrder`(작을수록 먼저)·`settleOrder`·`settleHover`, 단계 이름표는 `Asm.step(..., label="창고"/"불러오기")`. 옛 조립도(오토건·토끼 등)는 사용자가 말하기 전에는 mates 방식으로 옮기지 않는다.

**원본은 DB 의 부품 상세내역(`data.detail`) 하나뿐이다 — 크기·돌기·구멍 번호·위치·방향·지름·길이·관통이 있고, 이것이 기준이다(사용자 지시 2026-11-04). 연결점 `data.connectors`(`pegs` 돌기·`holes` 구멍: `id`·`pos`·`dir`·`r` 반지름·`len`·`through`, 부품 `size`, `confidence`)는 **상세내역에서 DB 트리거가 저장 순간에 자동으로 만든다**(`supabase/part_catalog_sync_connectors.sql`) — 상세내역을 고치면 연결점이 같이 바뀌어 둘이 어긋날 수 없고, 연결점을 따로 써도 상세내역이 있는 부품은 덮인다(`set_part_connectors` 는 그런 부품을 거절한다). 안내점(`marks`·`dir`)은 이 연결점에서 `asmlib.py` 가 계산한다(조립도에 따로 적지 않는다). 연결점이 어긋나면 안내점도 어긋난다.

| 무엇 | 어디 |
|---|---|
| 원본(고치기) | DB 부품 행의 `data.detail`(돌기·구멍 목록·`크기_mm`). 고치면 `data.connectors` 가 자동으로 따라온다. 읽기는 MCP `get_part_connectors`(연결점 형태)·`run_sql`(`data->'detail'`), 화면은 설계 화면 0차시 "큐보 부품 전체 리스트" → 부품마다 🟢 연결점 버튼 |
| 부품 상세 내역(원본) | DB 부품 행의 `data.detail`: 크기, 돌기·구멍 개수와 번호·위치·방향·지름·길이·관통, 규칙 수치, 대가리·몸통 방향, 등록값이 규칙과 다른 점, 알아 둘 것(사용자 확정·STL 실측 포함). 연결점은 여기서 자동으로 만들어진다 — 돌기·구멍 목록을 고치면 같은 저장에서 연결점도 바뀐다. 돌기·구멍 목록이 없는 부품만 `connectors` 를 직접 쓴다. 크기·구멍 번호는 연결점 좌표(y 위, bbox 가운데 원점)와 같은 기준이다. |
| 조립 프로그램용 사본 | `scripts/assembly-tools/conn.json`(+`dims.json`) — `partlib.py` 가 DB 상세내역을 읽어 만든다(값을 `partlib.py` 에 따로 적지 않는다). 상세내역을 고친 뒤에는 `python partlib.py` 로 사본을 다시 만든다. N프레임도 상세내역에 있다. |
| 부품 크기 | 부품 상세내역 `data.detail` 의 `크기_mm` — 별도 크기 표는 없다 |

**확인하는 순서**
1. `check_chapter_parts(권, 차시)` — 부품마다 연결점의 `confidence`(`checked` 확인함 / `auto` 자동탐지·확인 필요 / 없음)와 면 이름 확정 여부를 본다. `auto`·없음은 번호 조립 전에 확인한다(P3 A).
2. `get_part_connectors(부품)` — DB 에 등록된 현재 값. `conn.json` 사본과 **구멍·돌기 번호(id)까지** 같은지 본다(번호가 바뀌어 있으면 스크립트가 다른 구멍을 가리킨다 — 2026-11-04 2열브라켓 h2·h3 가 DB 와 conn.json 에서 서로 바뀌어 있었다).
3. `measure_part(부품)` — 3D 모델(STL)을 재서 등록값과 ✓ 일치 / △ 차이 / ✗ 못 찾음 / ➕ 등록 안 됨으로 대조한다. **한계: 둥근 벽만 찾는다.** 십자·소켓·네모 구멍과 블록 돌기·리벳·T축·기어처럼 둥글지 않거나 홈이 있는 모양은 "못 찾음"이 나오는데, 이것은 틀렸다는 뜻이 아니다. 도형으로 만든 프레임(N프레임)은 대상이 아니다. 구멍은 홀 테두리와 안쪽 관통 구멍이 따로 잡혀 등록값(관통 한 개)과 숫자가 달라 보일 수 있다.
4. 3D 뷰어 🟢 연결점 버튼 — 돌기·구멍 개수와 위치를 눈으로 세어 본다(자동탐지 부품은 반드시).
5. 숫자 기준은 부품 상세내역(`data.detail`)이다 — 크기·구멍 지름·돌기 지름·길이는 상세내역을 읽는다. 상세내역과 다른 등록값은 부품마다 따로 보정하지 않고 한꺼번에 맞춘다.

**고칠 때 순서**: DB 부품 상세내역(`data.detail` — 연결점은 자동으로 따라온다) → `python partlib.py`(conn.json·dims.json 다시 만듦) → 그 부품이 쓰인 조립도를 `python build.py <이름>` 으로 다시 만들어 `python cubo_joint_check.py <이름>` 이 0건인지 본다. 연결점을 바꾸면 그 부품을 쓰는 모든 조립도의 결합 점검이 달라질 수 있어 범위를 먼저 센다.

### K4. 양쪽 면이 다른 부품 — A면·B면으로 따로 표시

양쪽 면의 모양이 다른 부품은 면을 구분해서 적는다. 지금은 면 이름이 모델 축(홀면 +y / −y)뿐이라 양쪽이 같은 구멍·같은 번호로 보여 어느 쪽인지 알 수 없다(부시 `h1` 이 두 면에서 같음).

- [확정, 사용자 2026-11-04] **부시·너트·T축·볼트·스프라켓은 대가리가 있는 부품으로 다룬다.** 면은 대가리 쪽과 몸통 쪽으로 나뉜다.
- [확정, 사용자 2026-11-04] **스프라켓은 넓은 톱니 부분이 대가리다.**
- [확정, 사용자 2026-11-04] **부시와 너트도 넓은 지름 부분을 대가리라고 부른다**(볼트·T축의 머리와 같은 말).
- [확정, 사용자 2026-11-04] **부시와 너트는 대가리 부분이 바깥쪽이다.**
- **대가리가 모델 어느 쪽인가**(부품 모델 축은 부품마다 다르다 — 쓸 때는 이 표로 대가리 쪽을 찾는다):

| 부품 | 대가리 | 몸통 | 근거 |
|---|---|---|---|
| 부시 | −y (넓은 지름 쪽, 바깥) | +y (좁은 지름 쪽, 판 쪽) | 이 파일 G5 |
| 너트 | −y (넓은 지름 쪽, 머리·턱) | +y (좁은 지름 쪽, 몸통 돌기) | G3, 연결점 `p1` 방향 +y |
| T축 | −y (둥근 접시) | +y (십자 끝, 꽂는 쪽) | 부품 DB 상세내역 `대가리_몸통`(사용자 확정 2026-11-04), 연결점 `p1` 방향 +y |
| 8볼트·12볼트·서보고정볼트 | +y (머리) | −y (나사 돌기) | 연결점 `p1` 방향 −y(등록값, 눈으로 확인 전) |
| 스프라켓 | −y (넓은 톱니 부분) | +y (허브 관) | 이 파일 G6 "돌기(+y 허브 관)"(등록값 `h1` 방향 −y, 눈으로 확인 전) |

- [가정 — 사용자 확인 전] 이름: **A면 = 몸통 쪽(판 구멍에 먼저 들어가는 면) / B면 = 대가리 쪽(바깥에 보이는 면).** 모델 축 부호는 위 표대로 부품마다 반대일 수 있다(볼트는 대가리가 +y). 연결점 구멍 번호에 A·B 를 붙이는 일은 아직 안 했다.
- **[규칙] 면 이름이 확정됐는지는 부품 DB 상세내역(`data.detail`)에서 읽는다 — 코드에 확정 부품 이름 목록을 따로 두지 않는다.** 확정한 내용(대가리·몸통 방향, A·B면 구분 여부)은 DB 상세내역에 적고 이 K4 에는 규칙만 쓴다. (2026-11-06: `check_chapter_parts` 는 부품 DB 상세내역(`data.detail`)의 `면이름_확정`(근거 한 줄) 항목이 있으면 '면 이름 확정'으로 본다. 옛 확정 부품은 `design-faces.js` 의 `CONFIRMED` 목록도 함께 본다. 새로 확정한 부품은 상세내역에 `면이름_확정` 한 줄만 적는다 — 양팔저울의 리벳·부시·축·눈블록 기록 완료, T축 등 다른 미확정 부품은 쓸 때 같은 방식으로 적는다.)
- [확정, 사용자 2026-11-04] **눈블록과 바퀴(작은바퀴·데코바퀴·중간바퀴)는 돌기가 분명해서 방향이 돌기로 정해진다 — 대가리 구분(A면·B면)을 따로 하지 않는다.**
- 이 밖에 양쪽이 다른 부품(서보혼 등)은 사용자가 정하면 여기에 추가한다 — 아직 정하지 않았다.

5. ✅(일부) `dbimgcheck.py <이름> [번호…]`: `index.json` 그림과 DB(`ivs_assembly_refs`)를 비교해 안 올린 그림을 알려 주고 종료 코드 1(I1·B5). `number_start` 가 앞 번호 그림을 이 도구로 점검한다(2026-11-07: 조립도 id 를 `Asm("…")` 큰따옴표만 찾아 풍차(`Asm('…')` 작은따옴표)에서는 점검이 조용히 실패해 그림이 DB 에 없어도 한 번도 안 걸렸다 — 따옴표 둘 다 읽게 고쳤다). `rulecheck` 에는 아직 안 묶었고, 번호마다 필요한 그림 목록 점검도 없음. **도구가 "없음"·실패를 조용히 넘기면 안 된다 — 점검 도구가 오류로 끝나면 `number_start` 도 그 사실을 표시해야 한다(아직 안 함).**
