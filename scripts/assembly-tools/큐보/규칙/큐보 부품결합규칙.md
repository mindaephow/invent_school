# 큐보 부품결합규칙 (= 규칙 마스터) — 교재검사와 조립검사로 나눈 한 파일 (규칙 번호 A1~K)

**이 파일이 조립도 규칙 문장의 원본이다.** `SKILL.md`·`05_조립.md`·`CLAUDE.md`·`문서지도.md`·안내서는 이 파일을 가리키고, 새 규칙은 여기에만 적는다. 규칙을 바꿀 때는 이 파일의 해당 문장을 덮어쓰고 옛 문장은 지운다(바뀐 이유는 커밋 메시지에만 남긴다). 규칙 번호는 주제 글자+번호이고, 규칙 앞 표시는 `[도구]` = 도구가 막는다 · `[문장]` = 문장만 있다(도구로 올릴 후보).

## ★ 시작 전에 가장 먼저 읽는다 (사용자 지시 2026-11-04)

**큐보 규칙 정리·양팔저울(큐보 1권, `balance`) 점검을 이어받는 세션은 `큐보/인수인계.md`(큐보 작업 인수인계는 이 파일 하나뿐)를 맨 먼저 읽는다.** 어디까지 했고, 어디부터 이어가야 하는지가 거기에 있다(조립도 내용은 `큐보/조립도/1권/balance/진행기록.md`). 작업을 끝내거나 멈출 때는 `handoff.py` 로 그 블록을 덮어쓴다(메모리가 아니라 저장소에 남긴다 — 다른 PC·새 세션이 읽어야 한다).

## ★ 1번 규칙 — 절대 어길 수 없다 (사용자 지시 2026-11-04)

**가장 큰 문제점은 말을 안 듣고 규칙을 안 지키는 Claude 자신이다(사용자 지적 2026-11-05).** 사용자의 지시는 좁게 줄여 읽지 말고 가장 넓은 뜻으로 끝까지 적용한다(예: "규칙에 반할 만한 것은 다 삭제" = 안내점뿐 아니라 손 좌표·`p=` 까지 전부). 도구가 통과했다고 규칙을 지킨 것이 아니다 — 규칙을 항목별로 직접 대조한다. 못 고치고 남긴 것·규칙에 어긋나는 채로 둔 것은 보고에서 먼저, 숨기지 않고 말한다.

**큐보 로봇을 조립할 때는 이 파일의 K절(큐보 부품 결합규칙)에 따른다.** 한 가지 규칙으로 모든 차시·번호·조립도를 통일한다. 번호마다 다른 기준을 세우지 않고, 손 좌표(`p=`·`X.p=`)로 규칙을 덮지 않으며, 규칙에 어긋나면 번호를 고치지 말고 도구(`asmlib`·`cubo_joint_check.py`)를 고쳐 전체에 적용한다. 이 규칙이 아래 모든 규칙보다 앞선다. K0 "물리법칙이 가장 우선이다"가 모든 결합 판단의 바탕이다(결합 사실은 K절에만 적고 다른 곳에 되풀이하지 않는다).

# 공통편 — 작업 순서·질문·도구·DB·화면 (교재검사·조립검사 모두에 적용)

## 00. 조립도를 시작할 때 (조립도당 한 번 — 번호 조립 전에 03·04 를 모두 끝낸다)

조립도를 시작하면 **03 부품 정리와 04 창고 정리를 모든 번호에 대해 먼저 다 하고, 그다음에 1번부터 조립한다**(A1~A3). 순서는 01 번호 등록 → 02 이미지 자르기 → **03 부품 정리 → 04 창고 정리 → 05 번호별 조립**이며 앞 과정이 끝나기 전에는 05 로 넘어가지 않는다. **03·04 는 "1차"다 — 책을 번호 순서대로 대략 훑어 모든 번호의 사용 부품과 작업 창고를 먼저 적는 것이고 완벽할 필요가 없다. 모든 번호가 적혀 합계 = LIST 가 되면 1차 완료(번호판 위 배지, A2a·A3a)이고, 상세·정정은 05 번호 조립 중에 한다(B5).**

- **03 부품 정리(1차 — 모든 번호 한 번에, 대략 훑어서):** 책 1번부터 끝 번호까지 순서대로 읽어 번호마다 새로 쓰는 부품·개수를 표(`USED`)에 적고(2개 만들기 번호는 2배), 부품별 합계를 교재 LIST 와 맞춘다. 안 맞으면 숫자를 고치지 말고 책을 다시 뒤져 어느 번호를 잘못 읽었는지 찾는다. **합계가 다 맞을 때까지 04 로 넘어가지 않는다.** 조립 중 부품이 틀린 것을 발견하면 이 표를 고치고 이어간다.
- **04 창고 정리(1차 — 모든 번호 한 번에, 대략 훑어서):** 같은 순서로 책을 읽으며 번호마다 창고(slot)와 `history`(창고가 바뀌는 번호), 숨길 앞 번호(`hideMade`)를 정한다. 연달아 이어지면 같은 창고, 새 세트가 시작되면 새 창고(원점), "N + M" 합치기는 작은 번호 창고로.
- 둘 다 끝나면 읽기 표 칸이 생긴 번호부터 아래 "0. 번호 하나 체크리스트"로 1번부터 조립한다. 조립 도중 부품·창고가 어긋난 것을 발견하면 조립을 멈추지 않고(B5) 03·04 표를 고친 뒤 이어간다.

## 0. 번호 하나 체크리스트 (1쪽 — 번호마다 이것을 먼저 읽는다. 상세는 괄호의 규칙 번호)

**"조립 시작" = 가. 사전점검작업 → 나. 조립점검작업 → 다. 조립도 그리고 저장, 이 순서로 번호마다 한다(사용자 지시 2026-11-06). 세 가지는 겹치지 않고 각각 따로 말하고 따로 보고한다.**
- **"사전점검"·"교재점검" = 가만.** 책을 읽고 관찰·분석한 것이 맞는지 본다.
- **"조립점검"·"조립검사" = 나만.** 부품을 놓으면서 놓는 즉시 조립 규칙(K·G절)을 어기는지 규칙·도구로 점검한다. 책을 읽거나 책과 비교하지 않는다. 이미 그려진 조립도를 점검만 할 때는 나의 검사 도구를 번호 범위 전체에 돌린다.
- **"조립도 그리기"·"그리고 저장" = 다만.** 점검을 마친 조립을 저장(`--write`)하고 책과 맞춰 마무리한다.
- 말이 애매하면 한 줄로 어느 쪽인지 묻는다.

**순서는 가 → 나 → 다 이지만, 가와 다(책 비교)는 나(놓기)와 중간중간 오간다: 나에서 놓은 모델을 가-4 로 책과 비교하고, 다르면 나로 돌아가 다시 놓는다. 각 칸 끝의 [→ …]가 그때 볼 곳이다.** 각 단계가 끝나야 다음으로 가고, 단계를 건너뛰지 않으며, 막혀도 멈추지 않고 그 단계 안에서 B5(관찰 → 자기에게 묻기 → 다시 관찰, 맞으면 진행)로 푼다. 단계마다 만든 그림은 만들자마자 DB 에 올리고 화면 🖼 에서 확인한다(I1·B8).

### 가. 사전점검작업 — 교재검사 (책을 읽고 관찰·분석이 맞는가)
1. **시작 — 가장 먼저 작업장 치우기와 준비물 가져다 두기(이 칸을 끝내기 전에는 책 그림·격자에 손대지 않는다):** ① 작업장 = 이번 번호의 창고(slot)·`history`·`hideMade` 를 먼저 정하고 코드에 넣어 화면을 새로 불러와 책에 없는 앞 부품·다른 창고 부품이 안 보이는지 확인한다(A3·A5) ② 준비물 = 이번 번호에서 새로 쓰는 부품(`USED` 표)과 앞 번호에서 가져올 묶음(창고 어디에서)을 적고 남은 부품(LIST 대비)을 센다(A2) ③ 그다음 서버·로그인·`.env.local`(J5) → `number_start.py <이름> N`(A1) → 규칙을 읽고 "이번 번호에서 지킬 규칙 3개"를 첫 보고에 적는다(A6).
2. **책 원본 읽기(그림 목록 맨 위):** 이번 번호 + 앞·뒤 번호 + 완성 사진(00)을 4~6배 확대해 부품·초록 링·**화살표가 시작하는 돌기**를 하나씩 센다(H1·G7). 그림 속 글자(뒤집기 화살표 등)를 읽는다(F8). 개수는 센 값만, 짐작은 "추정"(G13). 앞 번호까지 만든 모델·읽기 표·창고·남은 부품도 먼저 본다(`pegprobe`, A6).
3. **xyz 방향 + 홀라인(결합하는 양쪽):** 기준 부품(결합을 받는 쪽)을 정하고 → 모서리 4곳 `crop_ticks`(판이 그림 밖으로 잘렸으면 D9) → `holefit`(통과 못 하면 C3 순서) → `hf` 그림을 눈으로(D1) → 결합하는 쪽도 같은 방법으로(D2·D6) → `axes_fit`(오차 ≤2px, E1) → `rotate_to`(E3) → `refs_rect` → 축선과 실제 구멍의 거리(D7). 방향은 격자만으로 정해지지 않는다(F5).
4. **방향대로 위치해 비교:** 앞 번호까지 만든 조립(과 이번 부품)을 3번의 카메라로 책 번호 그림과 **같은 방향·같은 시점**에 놓고(방향이 불확실하면 가설을 세우지 않고 책에 보이는 그대로 놓은 모델을 돌려 책과 비교, F4·E7), 책과 나란히 보며 **어디가 다른지**(개수·칸·방향·높이·거리를 숫자로) 찾는다. 다르면 고쳐서 다시 비교하고, 맞을 때까지 다음으로 가지 않는다(B5 자기 질문 6개, H4·H5 겹침 그림). [→ 비교할 모델은 나-1 로 놓아 만든다. 다르면 나로 돌아가 고치고, 고친 뒤 다시 여기서 비교한다.]
5. **어디와 어디가 결합하는지:** 책 링·화살표로 부품 쌍을 정한다(끼우는 부품 ↔ 받는 부품). 같은 조립이 둘이면 방향 가정 금지(F1), 합치는 번호는 뒤 번호부터(F3). [→ 이 쌍이 나-1 에서 놓을 계획이다.]
6. **어떤 구멍·돌기인지:** 쌍마다 양쪽 구멍·돌기 id 와 칸을 정한다 — 책 링 칸·피치 10mm 로 두 부품이 같은지 대조(D2·D8·G7), 모델에서 `pegprobe`·`matecheck` 로 숫자 확인. [→ 나-2 의 `pegprobe`·`matecheck` 로 확인한다.]
7. **읽기 표:** 면·링(센 칸·줄)·부품·대조·방향·부품방향·판단과정(H7·E4·E5). 센 값만 쓰고 짐작은 "추정"이라 적는다. [→ 나·다에서 고친 값이 있으면 읽기 표도 같이 고친다.]

### 나. 조립점검작업 — 조립검사 (부품을 놓으면서 규칙을 어기는지 그때그때 본다, 책을 읽지 않는다)
가에서 정한 결합 계획대로 부품을 한 쌍씩 놓고, **놓을 때마다 바로 아래 검사를 돌려** 규칙 위반이 나오면 그 자리에서 고친 뒤 다음 부품을 놓는다. 결과는 항목별로 한 줄씩(한 것/⚠/못 한 것) 보고한다.
1. **놓기:** `attach`/`recv` 를 `p=` 없이(C6), 새 창고는 원점(A4). 리벳·T축·부시·볼트·너트는 결합 전(띄운) 모양(G1·G3~G5), 볼트·너트 묻힘(G2), 스프라켓(G6), 방향 있는 부품(DC모터·메인보드·서보·기어)은 면·방향 카드(`<이름>_orient.json`, K1 규칙 10~12, G8)에 맞게. [→ 어디를 놓을지는 가-5·6, 방향 카드는 가-3·4 의 결과를 쓴다.]
2. **놓으면서 보는 검사(물리법칙 K0 부터):** `python pegprobe.py <이름> 빈구멍|위돌기|빈돌기 …`(놓을 자리, A6) · `python build.py <이름>`(쓰기 없이: 몸통 겹침·띄우는 길·안내점 맞물림·단계 계약·바닥 G15) · `python cubo_joint_check.py <이름> N`(G13) · `python joincheck.py <이름> N`(G1·G2) · `python matecheck.py <이름> N`(화살표 수 = 돌기 수, 깊이·축 어긋남, G12) · 기울어진 결합은 `python tiltjoin.py <이름> N`(G14) · 대칭 조립은 `python symcheck.py <이름>`(F9·F10). [→ 책과 모양이 다르면 가-4 로, 읽기 표 값이 틀렸으면 가-7 로 간다.]
3. **화면에서 보며 놓기:** 부품이 구멍 위에 떠 있지 않은지·화살표가 끝점에 닿는지 카메라를 돌려 본다(H6의 '볼 것', 끝나면 카메라 기본으로 J1). [→ 책과 같은 시점 비교와 6방향은 가-4·다-2 에서 한다.]
위반이 보이면 번호가 아니라 도구·부품을 고쳐 전체에 적용한다(1번 규칙·C7). 모두 0건이 되어야 다로 간다.

### 다. 조립도 그리고 저장 — 점검이 끝난 조립을 저장하고 책과 맞춰 마무리한다
1. **저장:** `python build.py <이름> --write`, 끝줄 ❌(C5)를 읽고 풀어서 다시 저장한다. [→ ❌ 가 규칙 위반이면 나로, 책과 안 맞으면 가로 돌아간다.]
2. **그린 뒤 교재검사 마무리(가의 몫):** 전체를 새로 불러와(J2) 책과 같은 시점 비교는 가-4 결과를 쓰고 저장 뒤 달라졌을 때만 다시 한다 → 6방향을 크게(H2) → 관찰 기록(H1) → 다음 번호(없으면 완성 사진)에서 이 조립이 적용된 모양을 센 값으로 비교(A8·H4) → `record_check`(H3) → `rulecheck`(A7). 이 번호와 뒤 번호에 책에 없는 부품이 같이 보이면 `hideMade`·slot 을 고친다(A5). [→ 안 맞으면 가-4(원인 찾기) → 나(다시 놓기) → 다-1(다시 저장) 순으로 돌아간다.]


### 마무리
- **보고:** 가·나·다를 따로, 각각 한 것/⚠/못 한 것(H8·J4). 번호가 끝났으면 다음 번호로 간다(사용자 답을 기다리지 않음, B5·B7).
- **푸시:** 사용자가 "업로드"라고 할 때만(I2).

문제가 생기면 멈추지 않는다: **먼저 이 체크리스트를 순서대로 지켰는지 확인** → 책을 뒤진다(B5~B6). 도구·검사가 막을 때: C1~C3. 사용자가 틀렸다고 할 때: B2.

## B. 질문·자동화 (멈추지 않는다)

- **B1 [문장] 질문에는 답만 한다 — 화면·값·코드를 바꾸지 않고, 사용자가 좋다고 한 단계·카메라는 건드리지 않는다.** 단 "~했어?"처럼 한 일을 확인하는 물음은 사실대로(안 한 것은 안 했다고) 말하고 곧바로 그것을 한다 — 변명·재질문으로 멈추지 않는다. 작업 중인 번호만 본다: 뒤 번호 그림은 읽기 보조로만 보고 그 번호를 만들거나 요청 밖의 것을 손대지 않는다. 한 줄 지시는 그 한 가지만 바꾸고, 말이 두 가지로 읽히면 구체적인 선택지로 한 번만 되묻는다.
- **B2 [문장] 사용자가 틀렸다고 하거나 고치라고 하면 설득·변명 전에 그 결합 부분을 책에서 다시 관찰하고 숫자로 확인한 뒤 고친다. 한 줄로 받아 그대로 하고 범위를 넓히지 않는다.**
- **B3 [문장] 사용자가 지정한 것(말씀·❄ 모습 기록·📷 카메라·✓)이 코드와 내 계산보다 무조건 우선한다.** 수정 지시가 ✓ 잠금에 막히면 코드 수정은 되돌리지 말고 ✓ 해제를 요청한다.
- **B4 [문장] 언제 묻나: 읽을 수 있는 것을 먼저 다 읽고(이번·앞·뒤 번호·완성 사진·모델 6방향·숫자, 자기에게 6질문) 그래도 구멍·방향·개수를 정할 정보가 없을 때만 그 사실 하나를 한 줄로 묻는다. 묻는 동안 확실한 부분은 계속 만든다.**
- **B5 [문장] 문제가 생기면 멈추지 않는다. 먼저 규칙을 순서대로 지켰는지 확인한다 — 증거는 이 번호의 이미지 작업이 DB 에 다 올라가 화면(🖼 배지·그림 목록)에 보이는 것이다.** 그림 목록(교재 원본 · 방향선 · 격자 · 모서리 확대 눈금 · `hf` 홀라인 확인 · 링 읽기 · 관찰 · 증명)에 빠진 그림이 있으면 그 그림을 만드는 단계를 건너뛴 것이니 그 단계부터 한다(대부분의 문제는 순서를 건너뛴 데서 나왔다). 그다음에도 풀리지 않으면 무엇이 문제인지 자기에게 묻고 해답을 찾을 때까지 책을 뒤진다. 횟수 제한은 없다. 문제 = 도구·검사가 막힘 · 책과 모델이 안 맞음 · 오차가 큼 · 방향·개수를 모름. 자기에게 묻는 순서: ① 지금 어떤 부품이 어디에 결합하나 ② 그 결합 부분을 책 어느 번호(이번·앞·뒤·완성 사진)에서 보았나 ③ 모델의 같은 부분을 같은 시점·확대로 나란히 보았나 ④ 다르면 정확히 어디가 다른가(개수·칸·방향·높이를 숫자로) ⑤ 원인은(구멍 축 방향·카메라·칸 한 칸 차이·앞 번호 위치·뒤집힘) ⑥ 고친 뒤 같은 곳을 6방향으로 다시 보았나. 책은 4~6배로 확대해 바꿔 가며 뒤지고, 모델은 앞·뒤·좌·우·위·아래로 돌려 본다.
- **B6 [문장] 책을 다 뒤져도 정할 수 없는 사실이 남으면: ① 그 사실 하나만 한 줄로 묻고(B4) 묻는 동안 확실한 부분은 계속 만든다 ② 정할 수 없는 부분은 가설을 만들지 않고 책에 보이는 그대로 놓고(F4) 읽기 표 판단과정에 "⚠ 근거가 약함: 무엇이·왜·시도·수치"를 적고 다음으로 간다. 어떤 경우에도 멈추고 기다리지 않는다.** 모델이 물리적으로 틀린 신호(몸을 뚫는 배치·돌기가 구멍에 안 들어감·거울 해·PnP 오차가 큼)는 ⚠ 로 넘기지 않고 B5 로 원인을 찾아 고친다(F6). 같은 번호를 세 번 고쳐도 안 맞으면 책의 다른 부분(앞·뒤 번호·완성 사진)을 다시 읽어 보이는 그대로 다시 놓는다. DB 를 못 읽거나 키가 없으면 ✓ 가 있는 것으로 치지 않고(통과시키지 않음) 사용자에게 한 줄로 요청하되 키 없이 할 수 있는 작업은 계속한다.
- **B7 [문장] 사용자가 "N번까지"라고 하면 N번을 끝낼 때까지 턴을 끝내지 않는다 — 번호 사이에서도, 작업이 길어져도, "중간 점검"·보고·업로드 제안을 이유로도 멈추지 않는다(2026-11-02 18번에서 임의로 멈춰 지적받음). 진행 상태는 `handoff.py` 로 기록만 하고 계속한다. 턴을 끝내도 되는 것은 ① 요청한 마지막 번호를 끝냈을 때 ② 책으로도 정할 수 없는 사실 하나를 한 줄로 물어야 할 때(그 부분만, 확실한 부분은 이어 만든 뒤) ③ 사용 한도가 모자랄 때 — 이때는 "N번까지"를 못 채워도 **번호 마무리(증거·DB 업로드·`handoff.py`)까지 끝낸 마지막 번호**에서 멈춘다(사용자 지시 2026-11-02: 30번까지 요청했어도 28번까지 했으면 28번에서 마무리). 만들다 만 번호를 남기지 않는다(코드만 넣고 증거·DB가 없는 번호 금지).** 번호를 끝내면 사용자 ✓ 를 기다리지 않고 다음 번호로 가며, 번호마다 책 그림(`refs/<이름>/NN.jpg`)과 비교 화면(`refs/<이름>/cmp/NN.png`)을 `SendUserFile`(status proactive)로 보내 "이상하면 말씀해 주세요, 답 없으면 계속"이라고 알린다.** 사용자가 이상하다고 하면 그 번호만 고친다. 규칙 점검 ❌ 는 묻지 말고 근거로 판단해 고친다.
- **B8 [도구:number_start `img_set_from`] 번호 도중에는 사용자에게 질문하며 턴을 끝내지 않는다 — 막히면 B5(책을 4~6배 확대해 다시 읽기, 빠진 그림의 단계부터)로 풀고, 정할 수 없는 사실 하나만 B6대로 한 줄 묻되 확실한 부분은 계속 만든다.** 번호마다 이미지 작업이 순서대로 됐다는 증거는 그림 목록이다: 0 교재 원본 · 1 방향선 · 2 축선 · 3 격자 · 4 확대 눈금(`crop_ticks`) · 5 홀라인 확인(`hf`) · 11~ 관찰 3장 이상. `<이름>_rules.json` 의 `img_set_from: N` 을 켠 조립도는 N 번부터, 앞 번호의 이 목록이 다 있어야 `number_start` 가 다음 번호를 시작하게 하고 빠진 그림을 알려 준다(DB 에 올렸는지는 `img_db`).
- **B9 [문장] 문제가 생기면 한 번에 하나씩 이 순서로 푼다(사용자 지시 2026-11-06): ① 확인(눈·도구·DB 로 실제 상태를 읽는다, 추정으로 말하지 않는다) → ② 원인 파악(왜 그렇게 나오는가, 어느 규칙이 비었거나 어겨졌는가) → ③ 규칙에 넣기(비어 있으면 원본 한 곳에 규칙을 쓴다, 사실은 손으로 따로 적지 않고 원본 자리(DB·도구)에 둔다) → ④ 그 규칙대로 해결한다.** 원인 확인 전에 땜질(목록에 이름 더하기·사본 만들기)을 하지 않고, 여러 문제를 한꺼번에 건드리지 않는다. 규칙 쪽 수정은 묻지 않고 하고, DB·푸시처럼 밖에 나가는 일만 허락을 받는다.

## C. 검증 우회 금지·도구 규칙

- **C1 [도구:build] `build.py` 옵션은 `--write` 하나뿐이다. 검사가 경고하면 끄지 말고 보고한다. 확인의 근거는 사용자의 ✓(DB `ivs_assembly_status`) 또는 책↔화면 비교 증거(`record_check`)뿐이며, 목록에 번호를 적어 막힘을 풀지 않는다. ✓(완료) 버튼은 절대 누르지 않는다.**
- **C2 [도구:build] ✓ 한 번호의 내용(부품 위치·자세·설명)은 바꿀 수 없다(빌드가 막는다). 고쳐야 하면 사용자가 ✓ 를 풀어 줄 때만 연다.**
- **C3 [도구:rulecheck+number_start, 순서는 문장] 격자 기준(구멍 ≥40%·평균 ≤2px·최대 ≤4.5px) 미달이면 기준을 낮추는 옵션·손으로 만든 격자·추정 카메라로 지나가지 않는다.** 푸는 순서(멈추지 않고 전부 시도): ① `holefit`(기본→어두운판→DoG) ② `holesearch`(모서리 재읽기) ③ `infer_grid`·`plate_match`(앞 번호 판 무늬·대칭 끼움·링 앵커·뒤 번호) ④ 프레임·L자는 `frame_fit`, 한 줄 부품은 `line_fit`, 판이 없는 번호는 `mkfit3d`. 유추 격자는 `rulecheck` 가 ⚠(사용자 확인 필요)로 보고한다. 예외는 사용자 말씀을 그대로 적은 `<이름>_approvals.json` 뿐이고 Claude 는 이 파일을 쓰지 않는다.
- **C4 [문장] 도구가 파일을 덮어쓴다: `frame_fit`·`axes_fit`·`mkfit3d` 는 `<번호>_axes.json`·`fits/` 를 말없이 새로 쓴다.** 부품이 달라 푼 카메라가 판 카메라(오차 ≤2px)와 크게 다르면(롤 40° 이상) 그 값으로 덮지 말고 판 기준 값으로 되돌린다(`axes_fit` + `rotate_to`). 쓰기 전에 기존 값 백업.
- **C5 [도구:build] 빌드 뒤 끝줄의 ❌·"막힌 항목"·"기존 항목을 바꿨다"를 읽는다. 읽기 표가 비거나 `부품` 칸이 "이름 개수" 형식(괄호 설명 없음)이 아니면 조용히 저장되지 않는다.** 스크립트 끝(`A.save_links()` 앞)에 `import stepchecks; stepchecks.apply(A, "<이름>")` 가 있어야 `--write` 가 된다. `<이름>_rules.json` 의 플래그가 점검을 켠다: `strict`(화면 확대·칸 수 대조·카메라 대조·카메라 출처 guess 아님도 `--write` 를 막는다 — 안 했다고 보고하지 않고 실제로 해서 채운다) · `orient_check`(읽기 표 `부품방향` 이 20자 미만이면 막음) · `placecheck`(그룹으로 옮겨 붙이는 부품의 상대 자세가 옮기기 전후 1mm 이상 다르면 막음 — 관절처럼 돌아가는 부품만 `nonRigid`) · `parts_sum`(A2) · `img_db`(I1) · `rulecheck`(켜면 번호 점검 ❌ 가 막음, 새 조립도는 켠다) · `mate_marks`(안내점 맞물림 없는 부품을 막음, 끄면 ⚠ 참고). 읽기 표(`<이름>_read.json`)에는 부품이 있는 번호마다 `면`(카메라가 보는 면)·`링`(센 칸·줄, 격자 점이 구멍 위인지 확인한 근거)·`부품`·`부품방향` 을 적는다.
- **C6 [문장] 코드 쓰는 법: 결합은 `attach`/`recv` 를 `p=` 없이(자동 계산), `p=` 는 자동 계산이 안 될 때만 이유 주석과 함께. 앞 번호 부품을 옮길 때는 `move_made`(`move_group` 금지), `hover` 는 0 이 아니라 0.01(뒤집기 등).** 틈·겹침 판정은 회전한 상자(`obb.py`). 조립도 데이터는 `<이름>_asm.json → build --write → public/design-assemblies.js` 로만 만들고 손으로 고치지 않는다.
- **C7 [문장] 규칙을 바꾸는 법: 흩어 적지 않고 원본 한 곳을 덮어쓴다(옛 설명은 지운다). 같은 실수가 두 번 나오면 문장이 아니라 `stepchecks.py` 검사로 올린다. 규칙이 새로 생기면 문서와 검사(`rulecheck`·`stepchecks`·`number_start`)를 같이 고치고 보고한다. 검사·규칙을 바꾸면 이미 만든 조립도 전부에 돌려 결과를 확인한다. 쓰지 않는 도구·문서는 같은 작업에서 지운다.** `build`·`stepchecks`·`userdone` 검사를 풀거나 고치는 일은 사용자가 지시했을 때만 한다. 규칙·기능이 바뀌면 항목마다 판단한다: 새로 추가된 기능은 남기고, 방식이 바뀐 것은 옛 문장을 지우고 새 문장으로 덮어쓴다(정리 과정·충돌 목록·출처·"옛 문장 보관" 파일·날짜 덧붙임을 문서에 쌓지 않고, 바뀐 이유는 커밋 메시지에만 남긴다). 고치기 전에 `05_조립.md`·`SKILL.md`·`CLAUDE.md` 에 같은 말이 있는지 찾아 한꺼번에 덮어쓰고, 마스터에 없는 내용(플래그·형식·도구 사용법)은 지우기 전에 마스터로 옮긴다. 안내서 절 제목은 `get_assembly_guide` 코드(CATS·`isCore`: `★`·`작업 흐름`·`제1편`·`단계 N`)가 쓰니 바꾸면 깨지는지 본다. 규칙은 기억 파일이 아니라 저장소(이 파일)에만 둔다 — 어떤 Claude 가 와도 같은 규칙으로 일해야 한다.
- **C8 [문장] 어기게 되는 규칙은 도구가 대신 하거나 어기면 막히게 한다. 둘 다 안 되는 규칙은 지운다("지키기 쉬워야 규칙이다").**
- **C9 [문장] 조립 스크립트(`<이름>.py`)를 분석·검사하려고 돌릴 때는 `runpy.run_path("<이름>.py", run_name="probe")` 로 실행한다. `python <이름>.py`(`__main__`)로 돌리면 `<이름>_asm.json`·`_checks.json`·`_entry.js` 가 덮어써진다.** 번호별 환경변수(`HB_UPTO` 등)가 있는 스크립트는 빌드(`build.py --write`)로만 쓰고 직접 돌리지 않는다.
- **C10 [문장] 조립 스크립트는 매번 같은 결과를 내야 한다 — `python <이름>.py` 를 두 번 돌려 `_asm.json` 이 같아야 하고(같지 않으면 증거 지문이 계속 낡아진다), `A.load_links(..., relock=True)` 는 항상 `relock=True` 다(2026-10-12 드롭체커).**
- **C11 [문장] 지키기 쉬워야 규칙이다(2026-10 개선규칙 8번): 번거로워서 어기게 되는 규칙은 도구가 대신 하게 하거나 어기면 빌드가 막게 한다. 둘 다 안 되는 규칙은 지운다. 차시가 끝나면 "어느 과정에서 무엇이 빠졌고 어느 파일의 어디를 고쳤는지"를 한 번 보고한다.**

## I. DB 올리기·푸시·업로드

- **I1 [문장] 그림(책 이미지·격자·방향선·확대 눈금·hf·관찰·증명)은 만들자마자 DB(`ivs_assembly_refs`)에 올린다 — 번호를 끝내고 올리지 않는다. DB 에 올리지 않은 채 멈추거나 보고하거나 다음 일로 넘어가는 일은 없다: 그림을 만들었으면 그 자리에서 올리고, 올리지 못한 그림이 남은 채로 턴을 끝내지 않는다. "이미지 작업이 규칙 순서대로 끝났다"는 증거는 DB·화면의 그림 목록(🖼 배지)이다.** 올린 뒤 화면을 새로 불러와 🖼 배지 장수가 올린 장수와 같은지 확인한다. 틀린 배정이 그려진 실패 시도 그림은 올리지 않는다(유추한 번호의 근거 그림은 idx 3~ 로 설명과 함께). `ivs_assembly_refs` 에는 `created_at` 이 없고(`get_rows` 에 `order_by` 필수), 그림 DB 삭제는 사용자 확인 뒤에만 한다. MCP 만 쓰는 Claude 는 `get_step_refs(assemblyId, 번호)` 로 그 번호에 올라간 그림을 연다(번호 0 = 교재 맨 앞 완성품 사진, 99 = 마지막 "완성" 그림). 이미 올라간 그림이 있으면 다시 만들지 않는다.
- **I2 [문장] 푸시는 사용자가 "업로드"라고 말할 때만, 모아서 한 번 한다(요청하지 않은 업로드·푸시를 미리 하지 않는다 — 푸시마다 Vercel 빌드).** 절차: ⓪ **"업로드"라는 말을 들으면 커밋 전에 먼저 `python handoff.py <작업 이름> --아이디 <계정> --어디까지 "…" --다음 "…"` 로 `큐보/인수인계.md` 를 지금 최종 상태로 덮어쓴다(사용자 지시 2026-11-06 — 업로드 때마다 인수인계가 최신이어야 한다. 작업 이름·어디까지를 정할 수 없으면 직전 진행기록을 보고 쓰고, 애매하면 한 줄만 묻는다)** ① `git add` 로 이번 작업 파일과 `큐보/인수인계.md` 를 하나씩 지정(다른 작업의 미추적 파일·`.bak`·`_spec*` 제외) ② `git commit`(메시지 끝에 Co-Authored-By 줄) ③ `node --check app/lib/cubo-assembly-tools.js` ④ **`git push newrepo main`**(원격 이름은 origin 이 아니라 newrepo).
- **I3 [문장] 사용자가 새로 바로잡으면 이 파일(이 파일)의 해당 규칙을 덮어쓴다 — 기억 파일에만 적지 않는다. 새 PC·새 세션은 `session_start.py` → `git pull newrepo main` → `setup_new_pc.py` → 이 파일 처음부터 읽기.**
- **I4 [문장] 여러 PC·여러 계정에서 이어서 작업한다 — 저장소에 올린 것만 모든 PC 에 전달되고, 기억 파일·`.env.local`·`.claude/` 밖의 로컬 파일은 전달되지 않는다.** 그래서 ① 세션을 시작할 때 `session_start.py --아이디 <내 계정>` 으로 최신을 받고 "마지막 작업은 어느 PC·어느 아이디가 어디까지, 지금 이 PC·이 아이디가 이어받아 시작"을 사용자에게 정리해 보고한 뒤 `handoff.py <작업 이름> --아이디 <내 계정> --시작` 으로 이어받음을 기록하고(작업트리가 더러우면 받지 않으니 그 사실을 보고) ② 이어받을 상태는 `python handoff.py <작업 이름> --아이디 <작업한 계정> --어디까지 "…" --다음 "…"` 로 `큐보/인수인계.md` 의 마지막 작업 블록(파일 하나뿐)에 적는다 — 날짜·PC 이름·아이디·커밋이 같이 기록되고, 다음 번에는 이 블록을 덮어쓴다(쌓지 않는다, 이력은 git). **사용자가 "업로드"라고 하면 푸시 전에 반드시 한 번 더 덮어써 같은 커밋에 넣는다(I2 ⓪).** `session_start.py` 가 이 블록을 조립도별로 보여 준다(A12). 임시 파일(`_spec*.json`·`*.bak*`·`*_tmp.py`)은 올리지 않는다. DB 에 올린 그림·✓·❄·📷 는 PC 와 상관없이 같이 보인다.
- **I6 [문장] 표시되는 값(구멍 번호 등)을 고치라는 지시는 그 값이 보이는 모든 층(라이브 렌더·DB 에 저장된 사본)을 함께 고친다.** DB·공유 함수를 추천하거나 바꾼 뒤에는 익명 키로 막히는지 직접 시험한다. 부품을 DB 에 등록·수정한 뒤에는 묻지 않고 새로 불러와 부품 3D 창을 열어 보여 준다.
- **I5 [도구:`app/api/local-refs`·design.html `refStore`] 작업 중인 차시의 그림은 라이브 DB 에서 받지 않는다 — 개발 서버(localhost)는 `scripts/assembly-tools/refs/<이름>/`(index.json)의 파일을 바로 읽고(DB 요청 0), 저장소에 그림이 없는 차시만 DB 에서 받는다. DB 에서 받을 때는 접속한 차시의 그림만 뒤에서 이 컴퓨터(IndexedDB)에 저장해 두고, 그림마다 버전(ctid·xmin·updated_at)을 비교해 바뀐 것만 다시 받는다(사용자 2026-11-03).**

## J. 화면 조작·보고·말투

- **J1 [문장] 사용자가 보는 화면은 평소 기본 모습으로 둔다: 왼쪽 패널 펼침·1~N번·완성 번호판·카메라·관절 버튼을 요청 없이 바꾸지 않고, 패널을 접거나 관절을 토글하지 않는다.** 단 번호를 끝내기 전 카메라를 돌려 직접 보는 것(H6)은 상시 허락이며, 확인하느라 바꾼 카메라·패널·팝업은 끝나면 반드시 기본 모습(저장된 카메라)으로 되돌린다.

## A. 순서·게이트

- **A1 [도구:number_start] 큰 순서는 01 번호 등록 → 02 이미지 자르기 → 03 부품 정리 → 04 창고 정리 → 05 번호별 조립이다. 앞 과정·앞 번호가 안 끝났으면 다음으로 가지 않고, 안 한 것은 보고하지 말고 그것부터 한다.**
- **A2 [도구:number_start, `parts_sum` 켠 조립도] 03 부품 정리(1차, A2a): 모든 번호의 사용 부품을 책 그림에서 읽어 번호별 표(`USED`)로 적고 교재 LIST와 합계를 맞춘다.** "N~M번 2개 만들기"는 2배로 센다. 합이 안 맞으면 숫자를 고치지 말고 그림을 다시 보고 어느 번호를 잘못 읽었는지 찾는다. 안 맞는 부품이 남아 있으면 번호 작업을 시작하지 않는다. 번호 설명(note)의 아래 줄에 "▣ 사용 부품: 부품 개수, …"를 줄을 바꿔 한 줄로 따로 적는다(합치는 단계는 "▣ 사용 부품: 없음(합치는 단계)", 두 벌 만드는 번호는 끝에 "(2벌)", 스크립트에는 번호 → 부품 표 `USED` 를 두고 반복문으로 붙이며 이미 있는 줄은 잘라 내고 다시 붙여 중복을 막는다). 추정한 개수는 코드 주석과 보고에만 적고 note 에는 쓰지 않는다. 조립도 쪽 개수가 교재 LIST 와 다르지만 사용자가 맞다고 확인한 부품은 `Asm(..., qtyOverride={"15프레임": 6})` 로 적는다 — 화면의 "필요 부품"이 그 개수를 기준으로 보이고 책 개수는 "⚠ (책 N개)"로 알린다. 리벳은 그림 옆 "(n)" 표시 숫자 그대로 쓰고 다른 부품은 그림에서 센 값(근거가 약하면 "추정")을 쓴다. 부품 이름은 `<이름>_list.json` 의 이름과 똑같이 쓴다(LIST 이름과 DB 이름이 다르면 LIST 이름으로 적는다). 3D 모델이 없는 부품(부품 DB 에서 모델 없음으로 나오는 것)은 조립도 제외 대상이라 번호 설명에만 적고 모델 부품 수에 넣지 않으며, 그런 부품만 나오는 번호는 빈 단계로 두고 `USED` 에 "고무밴드 2 (3D 모델 없음)" 처럼 적는다(줄은 `bands`, G10). 03 을 끝내면 번호별 부품 표 / LIST 와 맞는 부품 / 안 맞는 부품과 의심 번호로 보고한다.
- **A2a [도구:build, 화면 배지] 03 부품정리는 "1차"다 — 책을 번호 순서대로 대략 훑어 모든 번호의 사용 부품을 적는 것이고, 완벽할 필요가 없다. 상세·정정은 번호 조립 중에 한다(B5).** 번호판 위 배지는 기본 "미완"이고, **모든 번호에 `▣ 사용 부품` 이 적혀 있고 부품별 합계가 교재 LIST 와 같을 때** `build.py` 가 "1차 완료"로 적는다(`prepDone.parts`). 조립하다 부품이 틀린 것을 발견하면 03 표를 고치고 이어간다.
- **A3 [문장+도구일부:build] 04 창고 정리(1차, A3a): 책을 번호 순서로 보며 번호마다 slot·history를 정한다.** ① 연달아 이어지는 번호(세트, "N~M 2개 만들기")는 같은 창고 ② 새 세트가 나오고 기존 세트가 안 보이면 새 창고 ③ "N + M" 합치기는 앞(작은 번호) 창고로 가져가 조립. 창고가 바뀌면 `history` 글, 안 보여야 할 앞 번호는 `hideMade`, "2개 만들기" 둘째 벌은 `copy_to_slot`. 창고 0 = 메인, 1~5 = 따로 만드는 자리이고 **1번은 창고 1에서 시작한다.** 그룹 이름은 "그룹 1, 그룹 2…"(원점에 가까운 쪽이 먼저, 그다음 왼쪽부터)로 쓰고 다른 이름으로 바꾸지 않는다. 창고·불러오기는 번호·설명 본문에 쓰지 않고 `history` 에만 쓴다(예: "창고 1에서 불러와서 조립 → 그룹 1"). "N~M번 2개 만들기"의 둘째 벌은 새로 만들지 않고 `copy_to_slot` 으로 복사해 다른 창고에 보관한다(같은 창고 옆에 두면 겹침 문제, 사용자 2026-10-15) — 복사본은 `until` 전까지 보관 중이고 원본과 기본 z +300 떨어져 있으며 읽기 표 부품 수에서는 빠진다(`copyOf`). 앞 번호에 사용자 ✓ 가 있으면 그 번호의 부품 데이터는 고치지 않고 새 번호에서 `hideMade` 로 숨기며, 새 창고 원점이 숨은 세트와 맞닿으면 그 부품에 `noGuide` 를 쓴다.
- **A3a [도구:build, 화면 배지] 04 창고정리도 "1차"다 — 책을 훑어 모든 번호의 작업 창고를 먼저 기록하는 것이고, 상세·정정은 번호 조립 중에 한다.** 배지는 기본 "미완"이고, **모든 번호에 slot 이 있고 창고가 바뀌는 번호마다 `history` 가 있을 때** "1차 완료"(`prepDone.slots`)로 적는다.
- **A4 [문장] 첫 번호(1번)의 부품과 새 창고(slot≥2)는 화면 가운데(원점)에 두고 시작한다 — 그 번호 부품이 차지하는 범위의 x·z 중심이 원점이다(높이 y 는 바닥 아래로 안 내려가게만, 사용자 2026-11-05).** 멀리 띄우는 오프셋 상수를 만들지 않는다. 숨은 몸과 맞닿아 검사에 걸리면 5mm 어긋나게 놓고(검사를 끄지 않는다). 위치 기억(`compute_anchors`, `<이름>_links.json`)은 같은 창고 부품끼리만 잇는다 — 새 창고 부품이 다른 창고 부품과 우연히 같은 자리에 있다고 그 뒤를 따라가지 않는다.
- **A5 [문장] 번호를 끝내면 그 번호와 바로 뒤 번호 몇 개를 화면에서 열어 창고를 확인한다 — 책에 없는 부품(몸·보관 중인 부품)이 같이 보이면 `hideMade`·`_SLOT`·`_HIST` 를 고친다.**
- **A6 [도구:number_start 일부] 번호를 시작하는 순서: ① 서버·로그인(CLAUDE.md) → ② `number_start.py <이름> N` → ③ 규칙을 처음부터 읽고 "이번 번호에서 지킬 규칙 3개"를 첫 보고에 적는다 → ④ 앞 번호까지 만든 모델·읽기 표·창고·남은 부품에서 먼저 읽는다(`pegprobe`) → ⑤ 그다음에야 책 그림 격자.** 책 그림 한 장의 격자부터 들어가지 않는다.
- **A7 [도구:build+record_check+rulecheck, 일부 문장] 번호를 끝냈다고 말하기 전에: 빌드 문제 0건 → 책↔화면 비교 증거(`record_check`) → 관찰 기록(`observe`) → 그림 DB 올림 → `rulecheck` ✅. 하나라도 안 했으면 다음 번호로 가지 않는다.** 사용자 ✓ 를 기다리지 않고(내가 증거를 남김) 다음으로 가고, ✓ 한 번호의 내용은 바꾸지 않는다.
- **A8 [도구:verify_step 일부, 대부분 문장] 번호 결과는 다음 번호 책 그림에서 확인하고, 거기 안 보이면 완성 사진(00)에서 센 값으로 비교한다.** 근거를 읽기 표 판단과정에 적는다.
- **A9 [문장] 한 번호에서 새로 알게 된 짝·배치·정정은 읽기 표 판단과정과 `큐보/조립도/<권>권/<이름>/진행기록.md`에 적고, 같은 종류의 규칙(방향·칸 세기·창고·바닥)은 다른 번호에도 한 번에 훑어 고친다.**
- **A10 [도구:number_start] 모든 조립도는 완성 사진(0번)과 방향선 그림(`00_1.jpg`) 한 세트가 있어야 번호를 시작한다.** 방향선 그림은 완성 사진에 누끼(배경 제거)와 6×6 모눈(A~F·1~6)을 얹고 앞·뒤·위·왼쪽·오른쪽 화살표와 축 표시(앞 +Z · 뒤 −Z · 위 +Y · 왼쪽 +X · 오른쪽 −X)를 붙인 그림이다(사용자 2026-10-14 "무조건 하는 규칙"). "🖼 완성 사진"에서 완성 사진과 같이 보이고, 앞바퀴·뒷바퀴 같은 방향 말이 사용자와 같은 곳을 가리키게 한다. 방향은 눈으로 그리므로 사용자 확인을 받는다(앞·뒤·위는 완성 상태 3D 위치로 확인).

- **A14 [도구:final_audit] 작업 도중에는 막히지 않고 진행한다(사용자 2026-10-16). 모든 번호를 만든 뒤 `python final_audit.py <이름> --fix` 를 한 번 돌려 빠진 것(작업 점검 블록·읽기 표 빈칸·축 fit·그림 3장·비교 증거·카메라 출처)을 한꺼번에 채우고, 남은 ☐·⚠ 는 보고한다.** 결과는 `refs/<이름>/final_audit.md` 와 마지막 번호 설명 끝 "작업 점검 전체"에 붙는다(관리자만 보임). 번호판 색: 마무리 파랑·확인 필요 주황(`kw["review"]`)·✅ 완료를 누르면 파랑.
- **A15 [문장] 번호 표(01): 교재 번호 그대로가 조립도 단계다. 맨 앞 완성품 사진 = 0, 마지막 "완성" 그림 = 99 이고 둘 다 단계로 만들지 않는다("완성" 화면은 자동으로 붙는다).** 쪽마다 어떤 번호가 있는지 왼쪽→오른쪽·위→아래로 훑어 적고, 헷갈리면 앞·뒤 쪽과 완성품 사진을 같이 본다. 눈대중으로 잡은 것은 "추정"이라 적는다. 차시 제목 글자(띄어쓰기 포함)는 조립도 `chapter` 와 똑같이 쓴다.
- **A16 [도구:build] 번호만 등록한 뼈대 단계(01)의 설명은 "(작성 전)" 으로 쓴다 — "(채우는 중)" 은 빌드가 막는다. 스크립트 끝(`A.save_links()` 앞)에 `stepchecks.apply(A, "<이름>")` 가 없으면 `build.py --write` 가 거부한다. 뼈대(작성 전) 상태로는 푸시하지 않는다.**

### P1. 과정 0·1 번호 등록 (새 조립도 시작)

**준비 (시작 전에 확인)**
- 개발 서버가 떠 있고 사용자가 로그인해 둔 화면이 있다(번호 버튼 확인 4-4 에 필요) — 켜는 법·로그인은 `CLAUDE.md` "세션을 시작할 때" 2·3번(로그인은 사용자가 하고 비밀번호는 입력하지 않는다).
- 발명학교 MCP 연결(`check_chapter_parts`, `get_textbook_page`, `run_sql`), `.env.local` 의 서비스 키(`build.py` 가 사용자 ✓ 를 읽음).
- `pip install numpy pymupdf`. 파이썬은 `PYTHONIOENCODING=utf-8` 을 붙여 실행한다(Windows). 작업 폴더 `scripts/assembly-tools`.
- 이미 만든 조립도가 있는 차시면 ✅ 완료 단계를 확인한다(`check_workspace(assemblyId)` 또는 `select step,status from ivs_assembly_status where assembly_id='<id>'`). 완료 단계는 건드리지 않는다.

**1. 차시 찾기**
1. `check_chapter_parts(volume, chapter)` → 교재 PDF 주소. (안 되면 `run_sql`: `ivs_textbooks` 는 권마다 한 행, `data.files[0].url` = PDF, `data.chapters[]` = 차시 목록, 큐보 카테고리 id `6fa8abd9-7684-47a2-bd7f-2bc9a6e3fbe6`.)
2. 교재 쪽 번호 = PDF 쪽 번호. 새 차시는 앞 차시 쪽수 뒤에서부터 PDF 를 넘겨 찾는다(목차·차시 제목 쪽을 먼저 본다). 앞 차시 쪽수는 `list_assemblies` 의 "교재 N~M쪽"으로 읽는다.
3. 차시 제목 글자는 조립도 `chapter` 와 똑같이 쓴다(규칙 A15).

**2. 쪽 이미지**
- PDF 받기: `curl -o 파일.pdf <주소>` (공개 주소). `get_textbook_page(volume, page)` 로 받아도 된다(1권 일부).

**3. 번호 표**
처음부터 끝까지 훑어(왼쪽→오른쪽, 위→아래) 쪽마다 어떤 번호가 있는지 적는다.

**4. 등록**
1. 스크립트가 없으면 `python new_assembly.py <영문이름> "<차시 제목>" <권>` (`IVS_MCP_URL` 이 없으면 `--list '{"2단블록":9}'` 로 LIST 를 준다).
2. `<이름>.py` 에 쪽 표와 번호를 적는다(투석기 예):

## D. 홀라인·격자

- **D1 [도구:holefit·rulecheck, 순서는 문장] 홀라인(구멍 격자) 맞추기가 번호 이미지 작업의 첫 단추다. 순서: ① 책 그림을 훑어 부품·초록 링·화살표 읽기(링은 색으로 검출해 중심 픽셀을 숫자로) ② 기준 부품 정하기 ③ 판 바깥 모서리 4곳을 `crop_ticks.py`(≤100×100px 확대 눈금)로 읽기 ④ `holefit.py` ⑤ `hf/NN_<라벨>.png` 를 눈으로 보고 점이 모든 구멍 한가운데에 있는지 확인 ⑥ `axes_fit` → ⑦ `refs_rect` → ⑧ 만들자마자 DB 에 올림.** 눈대중 모서리·간격 어림으로 격자나 축선을 긋지 않는다.
- **D2 [도구:verify_step '양쪽 홀라인'(18번부터)] 홀라인은 결합하는 부품과 결합되는 부품 양쪽 모두 만든다(라벨 P·U 등).** 책 링이 받는 쪽·끼우는 쪽 각각 몇 번째 구멍인지 세고 두 부품의 구멍 간격(피치)이 같은지 대조한다. 같은 구멍이라고 가정하지 않고 `recv`/`attach` 에 구멍 id 를 명시한다. 기준(베이스) = 그 번호에서 결합을 받는 부품이며, 흰 판이 잘 보인다고 흰 판을 기준으로 하지 않는다. 결합 쪽이 판이 아니라 돌기·프레임일 때 잘 보이는 판의 격자는 **카메라를 풀기 위한 격자**로만 쓰고, 결합 홀라인(끼우는 쪽 구멍·받는 쪽 돌기 칸)은 따로 센다.
- **D3 [문장] 격자 점은 구멍 한가운데에 둔다. 확대해서 모든 구멍(리벳 위 구멍 포함)에 점이 있는지 센다. 가려진 구멍(격자로 채운 연장 점)은 화면에 그리지 않고 "연장"이라 적는다(`hide_est`). 구멍 점을 손으로 같은 간격으로 채우지 않는다.**
- **D4 [문장] 구멍 위치는 숫자로 읽는다(자동 검출 → 칸·줄 번호).** 칸 번호가 몇 칸 밀릴 수 있는 번호(구멍 무늬 반복)는 책 링으로 해를 고정하고 링은 앵커로 쓰지 않고 독립 확인으로 남긴다(투영한 칸이 링에서 몇 px 인지).

- **D6 [문장] 부품의 폭(구멍 개수)은 그 부품 위, 가까운 쪽 구멍 간격으로 센다.** 다른 판의 구멍 간격이나 먼 부품의 간격으로 나누지 않는다(이번 사고: 215프레임 폭을 판 간격 47px 로 나눠 3줄로 읽었으나 가까운 쪽 간격 64px 로는 2줄). 폭·길이는 끝 모서리와 구멍 열을 한 줄씩 직접 세어 센 값으로 적는다. [새 규칙]

- **D9 [문장] 판의 한 변이 책 그림 밖으로 잘렸으면(713프레임 16번: 윗변이 그림 위쪽 밖) 안쪽으로 눌러 읽은 가짜 모서리를 쓰지 않는다 — 보이는 실제 모서리 3곳과 판 치수(칸 수)로 잘린 모서리를 이미지 밖 좌표(음수 가능)로 외삽해 `holesearch`·`holefit` 에 준다.** 모서리가 이미지 안에 있다고 가정해 눌러 읽으면 평균 3~5px 로 미달한다(16번 외삽 후 DoG 평균 1.65px·최대 3.64px 통과).

## E. 방향·카메라·축·이미지 회전

- **E1 [도구:axes_fit·rulecheck(오차 ≤2px·점 4개 이상)·pnp.fit] 카메라·축 값은 번호마다 그 번호의 격자에서 `axes_fit.py` 로 계산한다 — 앞 번호 값 복사·"같겠지" 금지.** 오차 2px 초과·phi 1.55 초과(거울 해)면 쓰지 않는다. PnP 해는 모든 점이 카메라 앞에 있는 것만 쓴다(`pnp.fit` 이 걸러 낸다 — 오차가 같아도 점이 카메라 뒤인 거울 해는 화면에서 프레임·블록이 위아래로 뒤집혀 보인다). 점이 평면에 가까워 해가 여럿이면 모델 자세를 24가지 직교 자세로 돌려 보며 카메라가 땅 위(phi<π/2)·롤이 작은 자세를 고른다(해머배틀 17번). `_axes.json` 에 `fit` 이 없으면 손으로 쓴 값이다. 카메라는 짐작(guess)으로 두지 않고 책에서 읽은 방향(가까운 쪽·화면 오른쪽·위)으로 정해 `camSrc="eye"`. 눈맞춤만으로 "맞췄다" 하지 않고 책에서 방향 3개(화살표·판 긴 변·짧은 변)의 화면 각도를 재서 모델 방향을 투영한 각도와 차이를 숫자로 본다.
- **E2 [문장] +Z 의 부호는 칸·줄 번호 순서가 아니라 오른손 법칙(X×Y=Z)으로 정한다.** theta·phi 는 측정한 X·Z 화면 각도로 계산한다(`cosφ=√(−tanαX·tanαZ)`, `tanθ=−tanαX/cosφ`).
- **E3 이미지 회전: 구멍 줄이 놓인 축(예: "X")을 `<번호>_axes.json` 의 `rotate_to` 에 적고 `refs_rect.py` 를 돌린다 — 가운데 줄·가운데 열의 방향이 그 축선과 같아지게 작은 각도로 회전만 한다(늘이기·펴기·90° 눕히기·거울 금지).** 가운데 축선은 돌지 않고 읽은 원래 화면 방향 그대로. 가장자리 줄이 4~5° 벌어지는 것은 원근이라 정상. `level: true` 는 사용자가 "회전해서 맞추라"고 했을 때 구멍 줄을 수평으로 돌린다. `no_rotate: true` 는 구멍 줄이 없는 번호(링 점만 찍는 그림)에만 쓴다.
- **E4 [문장] 번호마다 책 그림의 +X·+Y·+Z 가 화면에서 가리키는 방향을 `_axes.json` 의 `global` 에 적고(`axes_fit` 계산값), 읽기 표 '방향' 판단은 그림이 아니라 가운데 축선을 보고 한다.** 방향이 정해진 부품(DC모터·메인보드·기어)과 창고에서 꺼내 합치는 그룹은 읽기 표에 방향 카드(면 사실 = `measure_part`·`get_part_connectors`, 책 증거 = 케이블·빨간 십자·접시 머리·돌기 수)를 먼저 쓰고 놓는다. 형식: `{"global": {"X": [dx,dy], "Y": [dx,dy], "Z": [dx,dy]}, "local": [{"at": [x,y], "label": "DC모터", "X": [...], "Z": [...], "size": 45}]}` (원본 그림 화면 좌표, 오른쪽 +x·아래 +y, 안 쓰는 축은 빼도 된다). `refs_rect.py` 가 이 파일로 X(빨강)·Z(파랑)·Y(초록) 축선을 그리고 `local` 자리에도 같은 모양을 또 그린다(색은 조립 보기 화면과 같다).
- **E5 [문장] 카메라가 보는 면을 먼저 적는다: 어떤 부품의 어느 면이 카메라 쪽인지, 판이 서 있는지 눕는지, 가까운 쪽·화면 오른쪽·위가 ±X·±Y·±Z 어디인지.** 책 그림이 "판이 서 있는" 모양이면 눕힌 모델에 카메라만 맞추지 않고 모델 자세를 책과 같게 놓는다. 카메라를 땅 밑(phi>π/2)으로 보내지 않는다. 카메라 `theta` 규약: 0 = +Z 에서 봄(화면 오른쪽 +X), π/2 = +X 에서 봄(오른쪽 −Z), π = −Z 에서 봄(오른쪽 −X), −π/2 = −X 에서 봄(오른쪽 +Z). 격자·축 방향을 만든 뒤 그 그림에서 가까운 쪽·화면 오른쪽·위가 ±X·±Z·±Y 중 어디인지 읽기 표 `방향` 칸에 적고, 그 방향이 되게 `step.cam` 을 정한다.
- **E6 [문장] 서 있는 부품(아치·벽·세운 프레임)의 카메라는 세계 3D 좌표로 푼다** — `frame_fit`·`axes_fit` 는 부품이 바닥에 누운 것으로 가정해 theta·phi 가 틀린다. 한 장면의 카메라는 하나인데 부품마다 풀면 값이 다를 수 있으니 기준 부품의 값을 쓰고 차이를 판단과정에 적는다. 다리를 눕혀 만드는 번호(꼬마기사 13번)는 눕히는 변환(x 축 90°)을 코드에 적고, 서 있는 다리는 앞(+Z)에서 본다.
- **E7 [문장] 방향이 앞 번호와 전혀 달라 보이면(롤 40° 이상·거울 해) 읽은 방향이 틀렸다는 신호다 — 책에 보이는 그대로 모델을 여러 쪽으로 돌려 책 시점과 비교하고, 책 점을 모델 3D 점으로 다시 풀어 롤이 0 에 가까워지는 쪽을 고른다.**
- **E8 [문장] 번호를 시작할 때 사용자가 저장한 ❄·📷 값을 먼저 읽는다(B3).**
- **E9 [문장] 교재 그림은 거의 다 대각선 시점이다 — 구멍 수·열 번호를 세기 전에 판·팔 축이 가로가 되게 돌리고(보통 12~25°) 확대해서 읽는다.** 격자가 안 맞을 때만이 아니라 처음부터 한다.

## F. 대칭·같은 조립 둘·방향

- **F1 [문장+observe 그룹비교] 같은 조립이 둘 이상이면 "같은 방향"인지 "대칭"인지 가정하지 않는다.** 책을 확대(원본 PDF 300dpi)해서 두 벌의 같은 부분(블록의 보이는 면·리벳이 보이는 쪽·판 앞뒤·끝 돌기 쪽)을 나란히 비교한다. 같은 면이 보이면 같은 방향, 다른 면이면 대칭 — 읽기 표 '부품방향'에 어느 부분이 달랐는지 적는다. 책에서 같은 조립이 서로 다른 방향 둘로 그려졌으면 대칭(같은 조립을 반대쪽에서 본 것)이고 모델은 하나.
- **F2 [문장] 대칭(거울) 쪽은 반대편이 끼워진 그대로(거울 위치) 따르고 점수·후보 탐색으로 정하지 않는다. 한쪽을 고치면 반대쪽에도 같게 적용한다.** 대칭형이면 먼저 F9·F10 을 본다(모범 = 드롭체커).
- **F3 [문장] 합치는 번호는 놓기 전에 뒤 번호(없으면 완성 사진)를 확대해 층 순서·판 위치·블록이 어느 쪽인지·돌기가 어디로 나왔는지 적는다. 뒤 번호 구조와 안 맞으면 방향을 의심한다.**
- **F4 [문장] 방향을 확정할 수 없으면 멈추거나 묻지 않는다 — 가설을 만들지 않는다. 책 그림에 보이는 그대로(부품의 보이는 면·돌기 방향·링 위치) 모델을 놓고, 책 확대와 같은 시점에서 나란히 보며 다른 곳을 숫자로 찾아 고친다(B5 관찰 → 자기 질문 → 다시 관찰).** 점수 탐색·PnP 는 관찰로 맞춘 뒤 확인용이다.
- **F5 [문장] 판 구멍 격자 일치(holefit·mkfit3d)는 방향 증거가 아니다 — 판·블록은 뒤집혀도 격자가 맞는다. 방향은 비대칭 특징(3단블록 돌기 면·끝 돌기 쪽·리벳 머리가 보이는 쪽·DC모터 십자)의 위치로 확정한다.**
- **F6 [문장] 이상 신호(돌기가 z 로 안 들어감·블록 겹침·판 간격 부족·"책과 일부만 같다")는 ⚠ 로 적고 넘기지 않고 방향·대칭을 다시 정한다. 계산(PnP·점수 탐색)이 관찰을 대신하지 않는다.**
- **F7 [문장] 결합 해가 여러 개(구멍 무늬 반복으로 한 칸씩 밀려도 오차 0)면 책 링의 칸으로 고정하고, 위치를 구멍 개수 점수·후보 탐색으로 정하지 않는다.**
- **F8 [문장] 번호 시작 때 책 그림 속 글자(긴 쪽·리벳 홈 방향 주의·말풍선·뒤집기 화살표 등)를 먼저 읽어 반영한다.**
- **F9 [문장] 거울 변환: 대칭면이 z = c 이면 위치는 `p' = (x, y, 2c − z)`(x 거울이면 x 를 뒤집는다), 자세는 같은 부품을 돌려 놓는다 — `R' = M·R·M`(`M = diag(1,1,−1)` z 거울, `diag(−1,1,1)` x 거울).** 부품 자체를 거울로 뒤집는 것이 아니라 같은 부품을 거울 위치·거울 자세로 놓는 것이다. 부품이 스스로 거울 대칭이 아니면(135도 프레임·DC모터·메인보드 …) 거울 자세만으로는 안 되고 길이 축으로 180° 더 뒤집는다(드롭체커 `R_F135X = diag(1,−1,−1)`: 17번 둘째 팔은 7번 첫째 팔과 거울쌍이라 프레임을 뒤집어 짧은 팔이 반대쪽으로 꺾인다). 모터 면·돌기 면은 `measure_part` 로 읽고, 거울쌍으로 놓은 부품의 `R_*` 도 부품 DB 면으로 확인한다 — 모터·메인보드·기어 방향이 틀리면 뒤 번호가 다 어긋난다.
- **F10 [도구:symcheck] 대칭 쪽 검증·유추: `python symcheck.py <이름> [--축 z --중심 5] [--빠진것]` 이 거울 위치 거리가 0.00mm 인지 본다(`--빠진것` 은 반대쪽에 아직 없는 부품 = 그 부품의 거울 위치가 반대편에서 놓일 자리). 한 번호 그림만으로 안 풀리면 대칭 쪽 번호의 끼움 칸을 앵커로 쓴다: `infer_grid.py … --판 <앞번호>:<라벨> --거울 <대칭번호> 줄 --링 "x,y;…"`(링↔칸 짝은 도구가 모든 짝을 돌려 고른다).** 한쪽을 먼저 완성하고 반대쪽은 거울 위치에 같은 결합으로 만든다 — 처음부터 다시 탐색하지 않는다. 위치를 구멍 개수 점수·후보 탐색으로 정하지 않는다(드롭체커 24번: 구멍 4개 쌓인 볼트·너트 축 자리가 이겨 리벳이 너트 구멍에 끼워졌다).

## H. 6방향·관찰·증거·비교

- **H1 [도구:observe.py] 관찰의 대상은 부품 이름·개수가 아니라 결합되는 부분이다 — 링 한 개씩·화살표가 시작하는 돌기·판 구멍 칸.** 번호마다 결합 2곳 + 6방향 1곳(필요하면 그룹비교·뒤번호)을 `observe.py add` 로 책 크롭·화면 크롭(같은 시점·가까이)을 나란히 보고 기록하며, 판정이 '다르다'면 고쳐서 다시 기록한다. 도구 ✅·"비슷하다"·"같은 것 같다"는 관찰이 아니다 — 센 값과 어느 번호 그림의 어디인지를 말한다. 한 번호를 읽을 때 눈에 띄는 곳부터 보지 말고 그림을 왼쪽에서 오른쪽, 위에서 아래로 훑으며 부품 → 초록 원 → 안내선을 하나씩 적고, 그다음 ① 이 번호 부품이 교재 LIST 에 있는지 ② 부품마다 돌기 수 = 꽂히는 홀 수인지(3단블록 돌기 3 → 홀 3) ③ 홀 간격(피치 10mm)과 블록 사이 간격 ④ 판에서 비어 있어야 할 열이 비어 있는지를 차례로 잰다. `get_part_faces` 로 조립 데이터를 이름으로 뽑아 책과 대조한다.
- **H2 [문장 → 도구로 올릴 후보] 6방향(위·아래·앞·뒤·왼·오른쪽)은 크게(화면의 절반 이상) 띄워 보고 방향별 한 줄로 적는다. 작은 썸네일·한 시점만 보고 끝내지 않는다. 수정할 때마다(번호를 끝낼 때만이 아니라) 다시 한다. 찍은 화면에 책 그림 팝업 등이 덮이지 않고 모델이 보이는지 확인한다.**
- **H3 [도구:record_check] 책↔화면 비교 증거: 같은 시점 스크린샷 + 센 개수가 든 비교 한 줄(30자 이상), 스크린샷은 45분 이내(긴 경로 파일은 PowerShell 로 짧은 경로에 복사).** 번호의 조립 모양이 바뀌면 증거가 무효가 되므로 다시 비교한다. 증거는 모양을 남기는 것이지 위치를 남기는 것이 아니다 — 조립 전체가 같이 옮겨진 것(1번 원점 이동 등)은 모양 지문(`stepfp.shape_fp`, 1번 첫 부품 기준 상대 좌표)이 같아 무효가 아니다(사용자 2026-11-05).
- **H4 [문장] 검토는 "통과 확인"이 아니라 "틀린 곳 찾기"다: 뒤 번호(없으면 완성 사진)를 확대해 센 특징 표(층·부품 순서·보이는 면·머리·옆 돌기 그룹·판·블록 개수와 방향)를 먼저 쓰고 모델에서 같은 항목을 같은 방법으로 센다. "다르다"가 하나라도 있으면 끝내지 않고 고친다.** 센 특징 표와 결과는 읽기 표 판단과정과 `<이름>_via.json` 에 센 값으로 적는다. `<이름>_via.json` 형식: `{"번호": [{"step": 다음번호, "image": "NN.jpg", "book_only": true, "what": "…"}]}`. 책 격자로 환산하면 수치(열·줄)로 말할 수 있다(오토타깃 19번: 21번 책 검은 판 격자로 샌드위치 열 5·13·줄 0·1). 안 맞을 때만 규칙·도구(홀라인·카메라·돌기↔구멍)를 되짚어 원인을 찾는다.
- **H5 [도구:overlay_check, 사용은 문장] 증명: "눈으로 보니 맞다"는 증명이 아니다. 3D 가 확정된 점을 읽어 `overlay_check.py` 로 모델 상자를 책 위에 겹친 그림(`NN_3`)을 만들고 오차(px)를 본다. 읽은 방향이 둘로 읽히면 오차로 가린다.**

## K. 큐보 부품 결합규칙 — 큐보 결합 규칙의 원본은 이 절 하나다

**큐보 부품에만 적용한다.** 에이스랩·로보타미주니어·프로보는 부품 규격과 결합 방식이 달라 따로 정리한다(아직 안 함).
점검 도구: `python cubo_joint_check.py <이름|all> [번호]` — K1 의 규칙 1·2·3·4·5~10·13~16을 잰다. K0 과 K1 의 규칙 12 및 [미정] 항목은 아직 점검이 없다(규칙 11·12 는 메인보드 방향 기록이 있을 때 규칙 10 이 잰다). 리벳 결합 틈은 `joincheck.py` 도 잰다(G1).
**부품 자체의 크기·돌기·구멍 숫자는 이 절에 따로 두지 않고 부품 DB 의 상세내역(`ivs_part_catalog` 의 `data.detail`)을 기준으로 한다**(사용자 지시 2026-11-04). 부품 숫자는 상세내역에만 있고 다른 곳(이 절·조립 스크립트·문서)에는 적지 않는다. 이 절은 결합 규칙(틈·겹침·돌기·방향)만 정한다.
규칙 문장은 이 파일이 원본이다. 규칙을 바꾸면 이 파일만 덮어쓰고(옛 문장은 지운다), 도구에 올릴 수 있는 것은 `cubo_joint_check.py` 로 올린다. `[확정]` 은 사용자가 직접 말한 것, `[집계]` 는 조립도 20개에서 센 값(확인 전), `[가정]` 은 내 추정이다.
### K0. 물리법칙이 가장 우선이다 (결합 규칙 전체의 바탕)

- [확정, 사용자 2026-11-05] **모든 결합의 가장 큰 우선순위는 물리법칙이다 — 숨쉬듯이 바탕에 깔려 있는 규칙이다.** 조립도·3D 부품·결합원리 화면 모두 이 원리로 판단하고, 아래 모든 규칙은 이 위에서 읽는다. 위치를 정한 뒤에는 반드시 "어디에서 물리적으로 멈추는가, 무엇과 겹치는가"를 따져 보고, 모델이 이 원리와 어긋나면 번호가 아니라 도구·부품 모델을 고친다(예: 8볼트·12볼트 머리가 홀 테두리에 안 들어가는 크기였다).
- [확정, 사용자 2026-11-05] **면과 면은 자석처럼 붙는다 — 물리법칙을 무시하고 겹치거나 침범하면 안 된다(틈도 없다).** 홀처럼 뚫린 곳을 통과하거나 돌기가 구멍에 들어가는 것은 겹침이 아니다(T축이 기어·프레임 구멍을 지나는 것 등) — 이 규칙은 구멍이 아닌 몸통·면끼리의 겹침이다. 도구: `asmlib.py place_rest`(몸통 크기 기준으로 끝면에 닿게 놓음), `attach`/`recv`(돌기 끝이 구멍 면에 닿게 놓음).
- **부품끼리는 겹칠 수 없다.** 프레임끼리도 겹칠 수 없다(규칙 3·17). 겹침은 구멍 길이가 아니라 **실제 모양**으로 판단한다 — 부품 몸통 크기(`dims.json`·STL)와 홀 테두리(판 면 위로 솟은 고리)까지 포함한다(2026-11-05: 구멍 길이로 기어를 놓아 몸통이 홀 테두리를 파고듦).
- **구멍보다 큰 것은 지나갈 수 없다.** 대가리(볼트·너트·T축·서보고정볼트의 머리)는 프레임 홀(홀 테두리)에 맞춰서 끼워지고 통과할 수 없다 — 구멍의 좁은 곳보다 커서 지나가지 못하고 멈춘다(사용자 2026-11-04). 프레임에서는 머리가 홀 테두리에 맞춰 쏙 들어가 프레임 면과 같아진다.
- **T축은 끝까지 끼운다.** 홀 테두리가 없는 작은기어에서는 T축 머리가 기어 구멍을 지나가지 못하고 기어 윗면에 닿아 멈추며 머리가 기어 밖으로 남는다 — 남는 두께는 머리 두께(둥근 접시, 두께는 T축 STL 실측값 — 부품 상세내역에 아직 없음)이고 "2mm" 는 옛 예시였다(사용자 2026-11-04 정정). 세로·가로 모두, 띄운 모습은 그대로 두고 제자리만. 도구: `asmlib.py attach` 가 기어에 끼우는 T축을 머리 두께(`T_HEAD_OUT`)만큼 올려 놓는다. 프레임에 끼우는 T축은 도구가 아직 검증하지 못한다(눈으로 확인).
- **[확정, 사용자 2026-11-04] 축(T축)의 끝이 구멍 안에 그냥 들어가 있는 것은 결합이 아니다.** 돌기가 구멍에 들어가 있어도 꽂아 고정하는 결합(안내 화살표·안내점이 필요한 결합)은 책이 초록 링과 화살표로 보여 주는 것만이다. 길이가 긴 T축이 프레임·부시를 지나 끝이 아래 프레임 구멍에 들어가 있는 정도는 결합으로 세지 않고, 합치는 번호에서도 T축에는 합치기 안내점을 요구하지 않는다(안내는 구멍을 받는 부품이 맡는다). 도구: `check_local.js` 의 settle 검사가 T축을 건너뛴다.
- **돌기 하나는 프레임 한 장의 구멍에만 들어간다.** 돌기 길이가 판 한 장 두께쯤이라 프레임 두 장을 통과할 수 없다(규칙 5·7). 리벳은 양 끝 돌기가 각각 한 장씩 맡아 두 장을 묶는다.

### K3. 부품 연결점(돌기·구멍) — 어디에 있고 어떻게 확인하나

**원본은 DB 의 부품 상세내역(`data.detail`) 하나뿐이다 — 크기·돌기·구멍 번호·위치·방향·지름·길이·관통이 있고, 이것이 기준이다(사용자 지시 2026-11-04). 연결점 `data.connectors`(`pegs` 돌기·`holes` 구멍: `id`·`pos`·`dir`·`r` 반지름·`len`·`through`, 부품 `size`, `confidence`)는 **상세내역에서 DB 트리거가 저장 순간에 자동으로 만든다**(`supabase/part_catalog_sync_connectors.sql`) — 상세내역을 고치면 연결점이 같이 바뀌어 둘이 어긋날 수 없고, 연결점을 따로 써도 상세내역이 있는 부품은 덮인다(`set_part_connectors` 는 그런 부품을 거절한다). 안내점(`marks`·`dir`)은 이 연결점에서 `asmlib.py` 가 계산한다(조립도에 따로 적지 않는다). 연결점이 어긋나면 안내점도 어긋난다.

| 무엇 | 어디 |
|---|---|
| 원본(고치기) | DB 부품 행의 `data.detail`(돌기·구멍 목록·`크기_mm`). 고치면 `data.connectors` 가 자동으로 따라온다. 읽기는 MCP `get_part_connectors`(연결점 형태)·`run_sql`(`data->'detail'`), 화면은 설계 화면 0차시 "큐보 부품 전체 리스트" → 부품마다 🟢 연결점 버튼 |
| 부품 상세 내역(원본) | DB 부품 행의 `data.detail`: 크기, 돌기·구멍 개수와 번호·위치·방향·지름·길이·관통, 규칙 수치, 대가리·몸통 방향, 등록값이 규칙과 다른 점, 알아 둘 것(사용자 확정·STL 실측 포함). 연결점은 여기서 자동으로 만들어진다 — 돌기·구멍 목록을 고치면 같은 저장에서 연결점도 바뀐다. 돌기·구멍 목록이 없는 부품만 `connectors` 를 직접 쓴다. 크기·구멍 번호는 연결점 좌표(y 위, bbox 가운데 원점)와 같은 기준이다. |
| 조립 프로그램용 사본 | `scripts/assembly-tools/conn.json`(+`dims.json`) — `partlib.py` 가 DB 상세내역을 읽어 만든다(값을 `partlib.py` 에 따로 적지 않는다). 상세내역을 고친 뒤에는 `python partlib.py` 로 사본을 다시 만든다. N프레임도 상세내역에 있다. |
| 부품 크기 | 부품 상세내역 `data.detail` 의 `크기_mm` — 별도 크기 표는 없다 |

**확인하는 순서**
1. `check_chapter_parts(권, 차시)` — 부품마다 연결점의 `confidence`(`checked` 확인함 / `auto` 자동탐지·확인 필요 / 없음)와 면 이름 확정 여부를 본다. `auto`·없음은 번호 조립 전에 확인한다(P3 A).
2. `get_part_connectors(부품)` — DB 에 등록된 현재 값. `conn.json` 사본과 **구멍·돌기 번호(id)까지** 같은지 본다(번호가 바뀌어 있으면 스크립트가 다른 구멍을 가리킨다 — 2026-11-04 2열브라켓 h2·h3 가 DB 와 conn.json 에서 서로 바뀌어 있었다).
3. `measure_part(부품)` — 3D 모델(STL)을 재서 등록값과 ✓ 일치 / △ 차이 / ✗ 못 찾음 / ➕ 등록 안 됨으로 대조한다. **한계: 둥근 벽만 찾는다.** 십자·소켓·네모 구멍과 블록 돌기·리벳·T축·기어처럼 둥글지 않거나 홈이 있는 모양은 "못 찾음"이 나오는데, 이것은 틀렸다는 뜻이 아니다. 도형으로 만든 프레임(N프레임)은 대상이 아니다. 구멍은 홀 테두리와 안쪽 관통 구멍이 따로 잡혀 등록값(관통 한 개)과 숫자가 달라 보일 수 있다.
4. 3D 뷰어 🟢 연결점 버튼 — 돌기·구멍 개수와 위치를 눈으로 세어 본다(자동탐지 부품은 반드시).
5. 숫자 기준은 부품 상세내역(`data.detail`)이다 — 크기·구멍 지름·돌기 지름·길이는 상세내역을 읽는다. 상세내역과 다른 등록값은 부품마다 따로 보정하지 않고 한꺼번에 맞춘다.

**고칠 때 순서**: DB 부품 상세내역(`data.detail` — 연결점은 자동으로 따라온다) → `python partlib.py`(conn.json·dims.json 다시 만듦) → 그 부품이 쓰인 조립도를 `python build.py <이름>` 으로 다시 만들어 `python cubo_joint_check.py <이름>` 이 0건인지 본다. 연결점을 바꾸면 그 부품을 쓰는 모든 조립도의 결합 점검이 달라질 수 있어 범위를 먼저 센다.

### K4. 양쪽 면이 다른 부품 — A면·B면으로 따로 표시

양쪽 면의 모양이 다른 부품은 면을 구분해서 적는다. 지금은 면 이름이 모델 축(홀면 +y / −y)뿐이라 양쪽이 같은 구멍·같은 번호로 보여 어느 쪽인지 알 수 없다(부시 `h1` 이 두 면에서 같음).

- [확정, 사용자 2026-11-04] **부시·너트·T축·볼트·스프라켓은 대가리가 있는 부품으로 다룬다.** 면은 대가리 쪽과 몸통 쪽으로 나뉜다.
- [확정, 사용자 2026-11-04] **스프라켓은 넓은 톱니 부분이 대가리다.**
- [확정, 사용자 2026-11-04] **부시와 너트도 넓은 지름 부분을 대가리라고 부른다**(볼트·T축의 머리와 같은 말).
- [확정, 사용자 2026-11-04] **부시와 너트는 대가리 부분이 바깥쪽이다.**
- **대가리가 모델 어느 쪽인가**(부품 모델 축은 부품마다 다르다 — 쓸 때는 이 표로 대가리 쪽을 찾는다):

| 부품 | 대가리 | 몸통 | 근거 |
|---|---|---|---|
| 부시 | −y (넓은 지름 쪽, 바깥) | +y (좁은 지름 쪽, 판 쪽) | 이 파일 G5 |
